# factory reference

The `factory` command of the plugin (Python 3.11+, standard library; needs `git`, `claude` and, for pull request state, `gh`). Run it inside a repository: the main checkout or any task worktree. Exit codes: 0 ok, 2 usage or precondition error (one line on stderr), 1 a `claude`, `git`, `gh` or scheduler step failed or a log could not be written.

## Install
In a clone of the repository, `make wizard` does every setup step (see Setup and uninstall); with only the plugin, run `factory wizard` after installing it (in a Claude Code session the plugin's `bin/` is on the Bash tool's `PATH`, so `factory` works there). By hand, in Claude Code: `/plugin marketplace add andreiciobotar/isshoni`, then `/plugin install factory@factory`; `/rename dispatcher-<repository directory name>` and `/factory:dispatch` make the session the dispatcher. To try it for one session without installing, start `claude --plugin-dir <clone>/factory`. `gh` must be authenticated (`gh auth status`). macOS and Linux; Windows is not supported. Leads run unattended: nobody watches a lead's session (`lead_permission_mode`, see Settings).

## Tasks
A task is one slug: lowercase letters, digits and single hyphens, 3 to 40 characters, not starting with `agent-`. From it follow the worktree `.claude/worktrees/<slug>`, the branch `worktree-<slug>`, the lead's session name `<slug>`, and the spec `~/.claude/factory/specs/<repository directory name>/<slug>.md`. Specs are working papers and are never committed; they outlive the worktree.

A session belongs to a task when its `cwd` is in the task's worktree, or when it is the task's exited lead (a background session with no `pid`, named like the slug, with `cwd` at the main checkout). A task whose finished sessions are several is not held; only two or more exited sessions carrying its name at the main checkout are ("cannot tell which is its lead").

## Commands
```
factory new <slug> (--brief <text> | --brief-file <path>) [--dispatcher <session-name>] [--base <slug>]
factory status [--json] [--cached] [--max-age SECONDS]
factory clean [--dry-run]
factory state working | blocked | handed-over <deliverable>
factory ack <slug> acknowledged | dismissed
factory feedback [--json] [--status open|accepted|rejected|done] [--kind issue|decision] [--since <ts>]
factory feedback add --role <role> [--slug <slug>] [--model <model>]     # a report or items on stdin
factory feedback decide '<what>. Why: <why>'                             # 200 characters at most
factory feedback set <id> open|accepted|rejected|done [--pr <url>]       # id or a unique prefix
factory retro [<file>]                                                   # a JSON object, on stdin or in the file
factory log events|retros [--since <ts>] [--until <ts>]
factory hook                                                             # run by the plugin's hooks
factory health [--json] [--dispatcher <session-name>]
factory watch [--dispatcher <session-name>]
factory digest [--dispatcher <session-name>] [--dry-run]
factory schedule install|remove|status [--dispatcher <session-name>]
factory firing <id> acted|ignored                                        # id or a unique prefix
factory miss <text> [--slug <slug>] [--firing <id>]
factory firings [--json]
factory merge (<number>... | --all) [--dry-run] [--approved]
factory lander [<number>...] [--dispatcher <session-name>]
factory wizard [--yes] [--list] [--owner <account>] [--name <app name>]   # the whole setup walk; rerun to finish or repair
factory uninstall [--yes] [--list]                                       # remove what the wizard and the factory put here
factory env                                                              # exports that make git and gh act as the App
factory land (<slug> | --all)
```

- **`new`** starts a lead: a background session in a new worktree, with `factory/roles/lead.md` appended to its system prompt, declared `working`. The calling session must be named `--dispatcher` (default `dispatcher-<main checkout's directory name>`; set it with `/rename`), and no other session may carry that name. It refuses a slug whose worktree, branch, session or pull request (in any state) already exists (when `gh` cannot say, it warns and goes on), and a repository at its limit. `--critical` lets the task use the slots held in reserve (see Settings). `--base` stacks the task on another open task's branch.
- **`status`** prints one row per task worktree: slug, phase, declared state, branch, session, base, session state, age (`overtime` when a session whose turn has not ended is past the time limit), uncommitted changes, commits ahead and behind its base, last commit, pull request, and `stale` when the last commit and the session's start are both older than 7 days. Then the counts per phase against the ordinary limit (`in motion 3/4, reserve 1, cap 5`; `3/5` when there is no reserve), the leftover `agent-*` and outside worktrees, one line saying who acts on GitHub (`acting on GitHub as <bot login> (the factory's App)`, with `; installed on ALL repositories: narrow it at <installation url>` appended when the installation covers all of them; or `acting on GitHub with your gh login` with the reason: no App identity, the App stored but not installed, this repository not on GitHub under the App's owner, and, instead of that choice, `acting on GitHub: the stored App cannot be read: <reason>; the factory's gh calls fail until it is fixed (factory wizard)` when `app.json` is corrupt or malformed), and one `waiting on the human: <slug> <deliverable>` line per task in review. Pull request state is `unknown` without `gh`. Pull requests come from one `gh pr list --state all --limit 100` per repository (10 s at most; a branch the list lacks is `none`, except when the list came back full: then that branch is asked alone), kept in `~/.claude/factory/cache/prs-<key>.json` with the time of the last successful ask. `--cached` never contacts GitHub (no `gh`, no token) and reads that cache; `--max-age SECONDS` (default 0: always ask) asks only when the cache is older or lacks a branch; `--cached` wins. Only `status` reads and writes `cache/prs-*.json`; every other command asks GitHub afresh (`unknown` when it cannot answer). The ask, the list and any per-branch fallbacks together, is bounded at 20 s. The cache also records the last attempt and its error, so with `--max-age` a failed attempt younger than that is not repeated (its error is reported again, no `gh` call); a full list whose missing branch cannot be asked alone counts as a failed attempt. When GitHub fails or times out the cached values stay and `status` prints `pull requests as of 2m ago (GitHub: <reason>)` (also printed for cached data); without a cache the rows are `unknown`. `status --json` has `prs`: `{"as_of": <epoch seconds of the last successful ask the rows use, null when none>, "error": <one line, or null; always null with --cached>}`. `status --json` also has `reserve` (the slots of the cap held back for critical work), `identity` (the bot login, or `null` when the factory does not act as the App here) and `repository_selection` (`all`, `selected` or `null`), and its rows also carry `waited` (seconds since the task's last declared record, `null` when undeclared) and, for a blocked task, `stop_kind` and `stop_summary` (the `kind` and `summary` of the last `QUESTION`, `BLOCKED` or `OVERTIME` stop its lead sent after declaring it; `null` when there is none, and `stop_summary` is `null` for stops logged before summaries existed).
- **`clean`** removes finished tasks (session, worktree, branch) and says why it kept the rest. It never forces and keeps a task whenever anything is uncertain. A task goes only when its pull request is merged into the default branch with the local head equal to the merged head, or its state is `acknowledged` or `dismissed` with a recorded deliverable, a pull request that is not open and a head that is pushed; and in both cases nothing is uncommitted, no task is stacked on it, no session in it is unfinished and no other worktree is nested in it. It keeps a task on a detached HEAD, and one whose worktree is locked with no session (it prints the `git worktree unlock` to run). If sessions cannot be listed, or an unfinished session has no `cwd`, it removes nothing (exit 2). A dismissed branch that is not merged makes `git branch -d` refuse: reported, exit 1. Git-ignored files in a removed worktree go with it.
- **`state`** is run by a lead inside its worktree. `handed-over` takes the deliverable: a link (`scheme://...`), or a file that exists and is outside the worktree.
- **`ack`** is run by the dispatcher on the human's word, for a task that was handed over.
- **`wizard`** creates the factory's GitHub App, gets it installed and verifies it; rerun, it verifies or repairs. See Identity.
- **`env`** prints `export` lines that make `git` and `gh` act as the App, or nothing (exit 0) when no installed identity is stored; on a terminal the token is shown as `***`. See Identity.
- **`retro`** takes the task from the working directory and reads the JSON from `<file>` when one is given (exit 2 if it cannot be read), else from stdin. On success it prints `retro: stored for <slug>`; a failure prints nothing on stdout.
- **`land`** lands a handed-over task whose base moved or merged, or whose pull request conflicts, without waking its lead (see Landing without the lead).
- **`merge`** and **`lander`** take a pull request from approved to the default branch (see Merging).

## Declared state, phases and the cap
| Declared state | By | Meaning |
|---|---|---|
| `working` | `new`; the lead when it resumes | being built |
| `blocked` | the lead, before `QUESTION:`, `BLOCKED:`, `OVERTIME:` | waiting on the human |
| `handed-over` | the lead, before `DONE:` and after any later turn | the deliverable is with the human |
| `acknowledged`, `dismissed` | the dispatcher (`ack`) | the human accepted or dropped it |

A session is unfinished if it is interactive, or a background session whose turn has not ended. In `claude agents --json --all` a turn has ended when `status` is `idle` (a session stays `busy` while a background command it started still runs), or when the entry has no `status` and no `pid` and its `state` is `done` or `stopped` (the process exited, or `claude stop`). The `state` of a live session (`done`, `blocked`, `working`) is its own summary of its last turn and is not read: a lead woken by a message after its hand-over often ends `idle` with `working`. Anything else, such as `waiting`, an unknown status or an exited session with another `state`, is unfinished.

| Phase | When | Holds a slot |
|---|---|---|
| `motion` | a session is unfinished in it, or sessions cannot be listed or placed; or declared `working`; or undeclared with no open or merged pull request | yes |
| `blocked` | declared `blocked`, no session unfinished | yes |
| `review` | no session unfinished; declared `handed-over` and not merged, or undeclared with an open pull request | no |
| `merged` | no session unfinished, pull request merged | no |
| `settled` | no session unfinished, `acknowledged` or `dismissed`, not merged | no |

The cap (`worktree_cap`) counts slots per repository. Only `new` checks it, so a lead that resumes is never stopped. Nothing bounds the number in review. `reserve_percent` of the cap (rounded up, never the last slot: a cap of 1 has no reserve) is held back: `new` refuses an ordinary task once the other slots are held, and only `new --critical` may take the reserve, for a red default branch, a broken factory, or when the human says so.

## Settings
`~/.claude/factory/settings.json`, every key optional; `factory wizard` writes it with these defaults when it is missing and, from a clone, sets `monitor`. A file that is not valid JSON, or an invalid value, is an error naming the file or key.

| Key | Default | |
|---|---|---|
| `worktree_cap` | 5 | tasks holding a slot, per repository; `isshoni-tui` can edit it |
| `reserve_percent` | 10 | whole percent of the cap, rounded up, held for `new --critical`; `0` turns it off |
| `lead_model` | `fable` | |
| `lead_permission_mode` | `auto` | `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan` |
| `task_time_limit_hours` | 2 | after it `status` shows `overtime` while the lead's turn has not ended; the lead stops and reports |
| `lgtm_from_author` | `true` | `true` or `false`: whether an `lgtm` by the pull request's author counts; set `false` once the factory has its own account (see Merging) |
| `lean_start` | `true` | `true` or `false`: whether the lead, the site manager run and the lander run start with only what they use (see Lean start); `false` restores the plain command line for all three |
| `monitor` | none | the path of the monitor's `isshoni` command; the cost criteria need it (see Criteria) |

### Lean start
A bare `claude --bg` lead starts with about 53k tokens of context (measured 2026-11-14, claude 2.1.325, haiku, trivial prompt). A lean start brings that to about 26k, the site manager run from about 36k to 8k and the lander run from about 12k to 10k. The lead, the site manager run and the lander run get `--strict-mcp-config` and `--settings '{"disableBundledSkills": true, "enabledPlugins": {<id>: false, ...}}'`, where the ids are every plugin `claude plugin list --json` reports except the factory's (a name before `@` of `factory`: turning that off removes the factory's agents). If the list cannot be read, one line on standard error says so, the `enabledPlugins` key is left out and the launch goes on.

What a lead then lacks: no MCP server at all (the user's, the claude.ai connectors, the repository's `.mcp.json`); no installed plugin other than the factory, so none of their skills, agents, hooks or LSP; no bundled skills; built-in tools limited to `--tools=Bash,Read,Edit,Write,Grep,Glob,Agent,Skill,ToolSearch,SendMessage,WebFetch,WebSearch,TaskStop,Monitor`, for the lead's subagents too (so no LSP, NotebookEdit, Cron, Artifact, Workflow or AskUserQuestion). Kept: the factory plugin, the user's settings and permissions, `~/.claude/skills`, the repository's `CLAUDE.md`, the login. The site manager run also gets `--disable-slash-commands` and `--tools=SendMessage,ToolSearch` (its structured output still works, checked). The lander run gets the first two flags only; its agent file already fixes its tools. The tool list is the single-word `--tools=` form because `--tools` takes every following word and would swallow the prompt. A task that needs an MCP server or another plugin needs `lean_start` set to `false`. A limit: the tool list has no `ExitPlanMode`, so `lead_permission_mode: plan` together with `lean_start: true` is not supported (whether the lead could leave plan mode is unchecked).

## FACTORY_HOME
`FACTORY_HOME` moves everything the factory keeps under `~/.claude/factory`: the settings file, the logs and the outbox, the task state, `watch.log` and the `identity/` directory (App, key, cached tokens). Unset or empty it is `~/.claude/factory`; `~` is expanded; a relative value exits 2 with one line (a hook exits 0 and records nothing), because the hook and the schedule run in other directories. Messages that name the settings file print the real path. It does not move `~/.claude/projects` (Claude Code's transcripts), the scheduler's own files (`~/Library/LaunchAgents`, systemd units, crontab) or the spec directory the lead's rules name. The dashboard's settings editor always opens `~/.claude/factory/settings.json` (`FactorySettingsPath` in `internal/data/factory.go`), and `~/.claude/factory/deliverables/` named in the lead's rules is not moved either. The hook and `factory env` run in the session's environment and read the same variable.

`factory schedule install` with `FACTORY_HOME` set writes it into the job's environment beside `PATH` (launchd `EnvironmentVariables`, a systemd `Environment=` line, a variable before the command in cron) and hashes the home into the job's label, so a job installed under another home is a second job and never replaces the real one; it also leaves a legacy job without a hash alone. With the variable unset the label and the job are unchanged. It is meant for tests and exercises: a scratch home that cannot touch the real outbox, tasks or App.

## Messages
Leads and the dispatcher talk through Claude Code's `SendMessage`, by session name. A lead's first line starts with `QUESTION:`, `BLOCKED:`, `OVERTIME:`, `SPLIT:` or `DONE:` and its slug. The human can always `claude attach <slug>`.

## Subagents and landing
A lead works through four agents of the plugin (`factory/agents/`), each pinned to a model: `explorer` (Haiku) finds and counts, `coder` (Sonnet) implements and commits its round, `reviewer` (Opus) reviews a fixed commit range, `lander` (Sonnet) lands. The lead keeps the judgment: the spec, the design calls, what to make of a review, the quality assessment, the pull request's message and the sign-off.

The lander is given the task's base, the head the lead vouches for (the reviewed head) and two files the lead wrote beside the spec: `<slug>.pr.md` (the pull request body) and `<slug>.retro.json` (the retrospective). It fetches, merges its base into the branch when the base moved (`git merge --no-edit <remote>/<base>`, never a rebase), resolves a conflict only when it is mechanical (independent neighbouring additions; generated files, which it regenerates), regenerates goldens when told to, runs the full tests, pushes (`git push -u <remote> HEAD`, never forced), and opens or updates the draft pull request. The same run serves the first landing and every later "your base moved". Its tools are Bash, Read, Edit, Grep and Glob. It never edits code or tests to get through, never drops a side of a conflict, never merges a pull request, never rewrites history, and reports one of:

| result | means | then |
|---|---|---|
| `LANDED` | the reviewed commits are unchanged (the reviewed head is an ancestor of the pushed head), the base changed no file the task changes, no golden changed, tests pass | the lander has filed the retrospective and declared `handed-over`; the lead signs off on the report |
| `LANDED, LOOK` | pushed, but a conflict was resolved mechanically, or the base changed files the task changes, or goldens were regenerated | nothing declared; the lead reads the flagged hunks, has them reviewed when needed, then files and declares itself |
| `STOPPED` (`dirty`, `conflict`, `golden`, `tests`, `denied`, `other`) | a decision is needed; nothing pushed (`denied` can follow a push). After `conflict` the merge is aborted; after `golden` or `tests` the worktree stays on the merge commit | the lead decides, then dispatches the lander again |

The lander refuses to start unless the worktree is clean and its head is the reviewed head, and its push is plain, so it is refused when the remote branch holds a commit the head does not contain. When a stacked task's base has merged, the lead says so and the lander merges the default branch in and retargets the pull request.

`factory state` and `factory retro` take the task from the working directory, so a lander's declaration is the lead's (`role: lead`).

## Landing without the lead
`factory land <slug>` or `factory land --all` (exactly one) does the mechanics of `factory/agents/lander.md` for a task that was handed over, so the dispatcher does not wake its lead for "your base moved". Run it from the main checkout or any worktree. It prints one report in the lander's format: `## Result` (`LANDED <url>`, `LANDED, LOOK <url>` or `STOPPED <reason>`), `## Facts`, `## Needs the lead` (`none` for `LANDED`); with `--all` each report follows a `# <slug>` line, and `nothing to land` says there was none. Exit 0 when every result is `LANDED`, 1 otherwise, 2 for a task with no worktree or one not declared `handed-over` (no report). `--all` takes only the handed-over tasks whose open pull request GitHub reports `CONFLICTING`, or whose recorded base (`branch.<b>.factoryBase`) has merged while the pull request's base is not yet the default branch: a pull request that is merely behind is left alone here: the lander brings it up to date when it merges it (the approval survives a clean merge of the default branch, see Merging), and the merge refuses a pull request that is `behind`. A named slug always lands.

It checks, in this order, before changing anything: (1) the task's sessions: they cannot be listed, one has no `cwd` and is unfinished, or one in the worktree is interactive or not finished is `STOPPED busy`, and nothing else is done or declared; (2) `git status --porcelain` not empty is `STOPPED dirty`; (3) after `git fetch`, a branch that is not `worktree-<slug>` or is the default branch, a pull request that is not open, or a local head that is not `<remote>/<branch>` and the pull request's head is `STOPPED other`. The reviewed head is taken to be the head that is at once local, pushed and on the open pull request.

The scripted path uses no model. The target is `<remote>/<recorded base>` while that base counts, else `<remote>/<default branch>` (a recorded base that merged: the pull request is retargeted). A target already in the head's history changes nothing but the pull request's base. Otherwise `git merge --no-edit <target>`, never a rebase: the reviewed commits are not rewritten; `make test` in the worktree (`LAND_TEST_TIMEOUT`, 1800 s; the test command exists only when the first of `GNUmakefile`, `makefile`, `Makefile` has a `test:` rule, so a `test` directory does not count, and included files and rules naming several targets are not read; without one it is `STOPPED tests` ("no `test:` rule in <makefile>" or "no Makefile"), since nothing can say green; no other test command is known); the sessions again (this second check exists only on the scripted path: once a lander session has started, no further look is taken, and a lead woken meanwhile is excluded only by the plain push); `git push <remote> HEAD:<branch>`, never forced, a fast-forward by construction; the retarget; a pull request comment (`Merged <target> at <sha> into the branch by factory land, without the task's lead: <old> -> <new>. The reviewed commits are unchanged.`, then overlap, conflicts, regenerated files, tests and the result; never `lgtm`, and a `gh pr comment` is neither a review nor a comment whose whole body is `lgtm`, so it cannot count as an approval). It never runs a golden command or edits a file: a stale golden is a failing test.

When the merge conflicts it is aborted (`git merge --abort`) (the worktree is back at the old head) and a short run of the lander starts in the worktree (`LAND_TIMEOUT`, 1800 s): `claude -p --agent factory:lander --plugin-dir <plugin> --model sonnet --permission-mode dontAsk [--strict-mcp-config --settings <json>, see Lean start] --allowedTools Read Edit Grep Glob "Bash(git *)" "Bash(make *)" "Bash(gh pr view *)" "Bash(gh pr edit *)" "Bash(factory state working)" --output-format json <brief>`. The permission is fixed, not the setting `lead_permission_mode`: with nobody watching, `auto` let its classifier deny a forced push once. `dontAsk` denies everything not listed: every `gh` other than `pr view` and `pr edit` (checked: a session with this argv was refused `gh pr merge 1` and `gh pr comment 1 --body lgtm`, and the fake `gh` recorded neither), and every shell command that is not `git`, `make` or `factory state working` (the Edit tool edits files). `Bash(git *)` is not narrowed: that the lander pushes only the task's branch, and only plainly, rests on its rules and on the script settling the outcome from the task branch on the remote, not on the allowlist. A denial is `STOPPED denied`. The pattern form `Bash(git *)` matched as written. A golden command that is not `make ...` is therefore a `denied` stop: a limit. The tool list is passed before `--output-format` because `--allowedTools` takes every following word. The brief gives the slug, the base and its remote, the old head as the reviewed head, whether the base merged, no title, body or retrospective, no hand-over, the files the branch changes as the goldens it may regenerate, and that file-writing shell commands and other `gh` commands are denied. The script, not the model, settles the outcome from the remote: a branch head that moved is `LANDED, LOOK` (a conflict was resolved) whatever the model said, with the comment, and the report's `## Needs the lead` ends with ``the conflict resolution: `git show --remerge-diff <new head>` ``; one that did not is `STOPPED <the lander's reason>`, or `other` when the reply cannot be read, the run failed or timed out, or the lander said `LANDED` without pushing. The printed report is the lander's, with the settled result and without its `## Factory feedback` section. What the form was found to do (claude 2.1.325; `--output-format stream-json --verbose` shows it): `--agent factory:lander` with `--plugin-dir` applies the agent's prompt, its model (Sonnet, also without `--model`) and its tool list (the init message names `Bash`, `Read` and `Edit`; no `Write`); hooks of the run carry the payload's `agent_type`, so `tags()` records `role: "lander"` with no change to it; an `Edit` is refused under `~/.claude/` paths as a sensitive file (a scratch repository there cannot be edited), not under a repository's `.claude/worktrees/`; `ANTHROPIC_LOG=debug` makes `claude` log on standard output, so `run` leaves it out of the run's environment.

| Result | When | State after |
|---|---|---|
| `LANDED` | the base did not move, or moved with an empty overlap; tests pass; pushed; the pull request is open against the target | nothing declared: `handed-over` stays |
| `LANDED, LOOK` | pushed, but the base changed a file the task changes, or the lander resolved a conflict | `working` (`role: lander`) |
| `STOPPED busy` | see (1) above | nothing declared |
| `STOPPED busy` | a lead that turned busy at the second check: the worktree is on the merge commit, unpushed | `working` |
| `STOPPED dirty`, `other`, `tests`, `denied`; `conflict`, `golden` (from the lander) | as above; the last 40 lines of a failing or timed-out `make test` (the worktree stays on the merge commit, unpushed); a failed fetch, abort, push (a remote branch that moved meanwhile is refused as a non-fast-forward) or `gh` step; the hunks, golden diff or denied step the lander reports | `working` |

A branch that holds a merge commit (an earlier landing) lands like any other. A merge that fails without a `CONFLICT` line (a hook, say) is aborted and is `STOPPED other` with git's output, with no model run. A push GitHub refuses with ``without `workflows` permission`` is `STOPPED denied`, nothing pushed, and "Needs the lead" is the one command for the human (see the `.github/workflows/` paragraph under Identity). `working` is declared before the push of a `LANDED, LOOK`, before the lander session starts and at a busy second check, so a kill or crash in between cannot leave the task looking handed over. After a lander run that pushed nothing and did not stop with a readable `STOPPED` (it timed out, exited non-zero, or its reply could not be read) the report adds HEAD, whether anything is uncommitted and whether a merge is in progress (`MERGE_HEAD`) from git; a failing fetch after the run is `STOPPED other`. `run` kills only the direct child: a command the lander had in flight can outlive a timeout. `STOPPED other` can follow a push (the retarget or the comment failed; the comment is posted even when the retarget failed, and both errors are reported): the report then says `pushed`. One task takes up to about 30 minutes (the tests or one lander session, never both); `--all` takes the tasks one after another; so the dispatcher starts it in the background.

How the landing keeps history, and its one exception. The reviewed commits are never rewritten, so a proof replaces the range-diff: `git merge-base --is-ancestor <reviewed head> HEAD` (the reviewed head is in the pushed history), and `git show --remerge-diff <merge>` (git 2.36 or later) prints what the merge added by hand: nothing for a clean merge, exactly the conflict resolution otherwise. A mechanical rename is still proved on trees (the inverse mapping applied to the result gives an empty diff against the base). There is no squash, which would break stacks: `git log --first-parent` on the default branch reads one line per pull request; proof commits and their reverts stay. History is rewritten in one case only: a pushed commit holds something that must not stay published (a secret, personal data, a huge binary). The lead does not rewrite: it reports `BLOCKED:` naming the commit, and you rewrite and force-push, and rotate the secret.

What can refuse a landing step (counted 2026-11-14 from 270 transcript files and the event log):

| Refused by | Count that day | Now |
|---|---|---|
| the auto-mode classifier, on a forced push ("Destructive or Unwanted Actions") | 2 of 20 forced pushes (17 went through) | no forced push exists in the path; plain `git merge`: 67 calls, 0 classifier refusals |
| GitHub, ``without `workflows` permission`` | 1 of the 20 forced pushes | `STOPPED denied` with the one command for you; a merge bringing in the base's workflow changes is accepted |
| worktree isolation, on compound commands and heredocs | about 9 (`factory retro <<EOF` 3, chained `factory land` probes 4, compound `git checkout` 1, `git merge` 1) | one plain command per call; `git rebase` 60 calls, `git fetch` 103, `gh pr create|edit|ready` 62, `factory state` 76: 0 refusals |

`BLOCKED:` messages that day: 2, both at the landing push.

A `working` task is not mergeable (`handover` stop) and holds a slot until its lead has looked and declared `handed-over` again. The dispatcher messages the lead on `LANDED, LOOK` and on every `STOPPED` other than a first-check `busy`, including the busy that left an unpushed merge commit, pasting the report; on a first-check `busy` it does nothing and runs `land` again when the lead's turn has ended. A lead that gets such a report declares `working`, acts on it as on a lander's report and declares the hand-over again.

Who acts: with an App installed (see Identity), the script's `gh` calls (the pull request read, the retarget, the comment) get the App's token through `run`, as the merge step's do, and its `git fetch`, `git merge` and `git push` run with the exports of `factory env` (the App's token for git, its name and email as author and committer; a failed mint stops the land at its first fetch with `STOPPED other`, "no App token", before anything is fetched, merged or pushed). The lander session of a conflict gets the same exports from the `SessionStart` hook, which `claude -p --agent factory:lander` fires like any session in a task worktree (checked with a stand-in for `factory env`: `git config` in that session saw its exports, with no denial under the allowlist). So the push, the comment and the merge commit are the bot's; with no App they come from your login. A fresh approval is still the human's.

Limits. Busy is told from the session list at two moments: when it starts and after the tests; a lead woken after the second look is not excluded, and only the plain push keeps the remote safe: it is refused when the lead pushed meanwhile. Listing sessions failing counts as busy. The task's pull request must be open; the old head must equal the pushed one; `--all` makes no mergeability retry (`UNKNOWN` is not conflicting).

Metric: dispatcher messages to a lead after its first hand-over, per landed task. In the events log a dispatcher message is a `PostToolUse` event with `tool_name` `SendMessage`, `role` `other` and `to` the lead's name (the slug); count those of a slug whose `ts` is after the first `handed-over` record of that slug in the task state log, and divide by the number of tasks that landed in the period (`factory log events --since <ts>`).

## Stacked tasks
`new --base <slug>` branches the worktree from the base task's branch and records it in `git config branch.worktree-<slug>.factoryBase`; the pull request targets that branch. The record is never cleared: `status` stops showing a base once it has merged into the default branch, and `clean` stops treating a merged task as stacked. When a base merges, a lead still working on top of it has its lander merge the default branch in (the `base-merged` criterion flags it), and a task already handed over is landed by `factory land`; `merge` retargets a stacked pull request itself when its turn comes.

## Site manager
A job runs `factory watch` every 2 minutes (`WATCH_INTERVAL`), output appended to `~/.claude/factory/watch.log`. It follows the dispatcher's life; `factory schedule install|remove|status` are for manual control. Each tick does two things:

- **The cheap part (every tick).** With no task working, blocked or handed over whose worktree is still there, it does nothing and makes no `gh` call, so an idle repository costs nothing. Otherwise one `gh pr list` (20 s timeout; on a failure it prints `notice: <why>`, or `comments: <why>` when nothing is handed over, and the tick goes on) reads the open pull requests with their reviews and comments, and that one snapshot serves three consumers in this order: the comment forwarder (`watch_comments`); the draft flags (`sync_drafts`), when a task is handed over or a task's pull request is ready for review while its task is not; and the approval notice, when a task is handed over. The draft sync builds its picture from the snapshot (one `claude agents` listing and local git per task, no further `gh pr list`), so a tick with k handed-over tasks makes 1 + (the number of their pull requests whose head matches, one `gh pr checks` each) `gh` calls, plus a `gh pr ready` per flag that changes: a green handed-over pull request turns ready within about two minutes. A pull request is a candidate for the notice when it belongs to a task declared handed-over, is not a draft, and has an `APPROVED` review or an `lgtm` comment (only from an owner, member or collaborator), stamped with the newest such time. This is only a prefilter; `factory merge --approved` decides. Candidates whose `<head>:<stamp>` is not what `lander.json` holds as noticed start one lander run for all of them (see Merging); when another run holds the lock the tick skips silently and records nothing. It is at most 30 GraphQL requests an hour per repository for the list.
- **Health (when 30 minutes, less 60 s of slack, have passed since the last health run, kept in `lander.json`).** Everything below: the session list, the criteria, the site manager, the digest.

- **Label.** `com.claude.factory.watch.<repository directory name>-<8 hex of the sha256 of the main checkout's path>`: two folders with one name get two jobs. The job runs in the main checkout with the dispatcher's session name (`--dispatcher`, default `dispatcher-<repository directory name>`).
- **Backends**, chosen at run time: launchd on macOS (`~/Library/LaunchAgents/<label>.plist`); elsewhere a systemd user timer when `systemctl --user` works (`<label>.service` and `<label>.timer` under `$XDG_CONFIG_HOME/systemd/user`, `~/.config` by default); else one line in the user's crontab ending in `# <label>`; else `install` exits 2. `install` prints `installed <label> (<backend>)`, `remove` prints `removed <label>` or `nothing installed: <label>`, `status` prints whether the job is present and loaded. On systemd the timer stops when you log out of every session unless `loginctl enable-linger` is on; `install` says so when it is not.
- **PATH.** The job gets a minimal `PATH`, baked at install: the directories of `git`, `gh`, `claude` and the running Python, then the system directories. `install` fails with `<tool> is not on PATH` when one is missing. Rename the dispatcher, or move a tool, and install again.
- **Start.** The plugin's hook (no model, no prompt) installs the job when a session that is named `dispatcher-<repository directory name>` and works in the repository starts, resumes or sends a prompt and there is none loaded. For a session that is not the dispatcher, in a main checkout without the job, that check costs about 0.2 s per prompt (`git worktree list`, the scheduler's status, `claude agents --json --all`). `/rename` fires no hook, so the job appears at the next prompt after it. On startup and resume it replaces the job, so after a plugin update the job moves to the new copy at the dispatcher's next start or resume; the superseded copy stays on disk for 14 days. A dispatcher under another name (`--dispatcher boss`) is not followed: run `factory schedule install --dispatcher boss`.
- **Stop.** When a dispatcher session ends (a `/clear` is not an end) and no other live one of the repository remains, the hook removes the job. A crash fires no hook, so a health tick that finds no live dispatcher session removes the job itself. Both keep the job while a task is declared handed-over, so that an approval still merges; the health tick removes it once none is. Such a tick starts no site manager; with live tasks it notifies once that the dispatcher is missing, and it keeps the job one more tick when it could not judge that.
- **Legacy.** On macOS `install` and `remove` also drop the job of the earlier label `com.claude.factory.watch.<repository directory name>` when its working directory is this repository.
- Install from the main checkout or the installed plugin: a job installed from a task worktree breaks when the worktree is removed.
- `remove` by hand lasts until the next prompt of a live default-named dispatcher, which installs the job again.
- `tools/walk.sh` walks this whole life with the real scheduler, stub `claude` and `gh` and a throwaway repository; CI runs it on Linux (systemd, then cron), on macOS and in the container. It installs a real job, so outside CI it wants `WALK=1`. `WALK_CRON=1` hides systemd so that cron is chosen; `WALK_DAEMON=1` leaves each cron tick to the cron daemon (the job's schedule becomes every minute) instead of running the job's line by hand.

`health` evaluates the criteria and prints what fires now; it writes nothing, except that a slow or failed `gh` call is logged to `gh-YYYY-MM.jsonl` (any command does). The health part of `watch` does the same without running a model, logs each new firing, and only when there is something new to send starts one headless Sonnet run (no shell, no file tools, 10 minute timeout, about $0.15) under `factory/roles/site-manager.md`. `factory` starts every `claude` child (the lead, the site manager run, the lander run, `claude agents`, `claude rm`) without `ANTHROPIC_LOG` in its environment, since with `ANTHROPIC_LOG=debug` `claude` logs to the standard output that is read as JSON. The run gets the evidence in its prompt and either messages the dispatcher (first line `ESCALATION: <repository directory name>`) or suppresses the firing with a reason. `always` firings cannot be suppressed. Nothing is escalated twice while its condition lasts; a suppression is looked at again after two hours. `dispatcher-missing` becomes a desktop notification instead (`notify-send` on Linux; without a notification service, or when it fails, a `notify: ...` line in the watch log) and holds everything else back until a dispatcher exists. Either way the firing is recorded as escalated by `watch`, so the human hears once.

Criteria are `factory/criteria.json`, one entry per line: `name`, `escalate` (`always` or `judgment`), `threshold`, `what` and optionally `job` (`watch`, the default, or `digest`: see Digest). `health` and `watch` evaluate the `watch` entries only. Delete a line to turn one off; an unknown name or a bad value is an error (exit 2). A criterion whose inputs cannot be read fires nothing and is printed as `not evaluated: <name>: <why>`.

| Criterion | Escalate | Threshold | Fires when |
|---|---|---|---|
| `past-limit` | always | | a lead is working past the time limit |
| `ci-red-default` | always | | a workflow's newest decisive run on the default branch did not succeed |
| `dispatcher-missing` | always | | tasks are live and not exactly one unfinished session carries the dispatcher's name |
| `quiet` | judgment | 20 min | a lead whose turn has not ended wrote nothing and committed nothing for that long |
| `ended-undeclared` | judgment | 10 min | a lead's session ended with no hand-over or block declared |
| `blocked-unanswered` | judgment | 30 min | a task has been `blocked` that long |
| `handover-unacknowledged` | judgment | 24 h | a task was declared `handed-over` that long ago and is still in `review` |
| `review-loops` | judgment | 3 | a task had that many reviewer dispatches since it started |
| `wrong-model` | judgment | | a lead or subagent ran on a model other than the one pinned for its role |
| `ci-red-handover` | judgment | | a handed-over pull request has a failing check |
| `deep-stack` | judgment | 3 | a task's stack, counting the task itself, is deeper than that |
| `merged-not-cleaned` | judgment | 2 h | a task was merged or settled that long ago and not cleaned |
| `lgtm-blocked` | always | | a lander run stopped on a pull request the human approved and it is still open at the head it stopped on; subject `#<number>/<kind>` (see Merging) |
| `base-merged` | always | | a lead is still working (pull request neither merged nor open against the default branch) on a base that has merged, and its worktree lacks that merge commit |
| `cost-outlier` | judgment | 3 | a working or blocked task has cost more than that many times the median landed task |
| `lead-heavy` | judgment | 85 % | a working or blocked task that has cost at least the median landed task has more than that share of its cost in the lead's own session |

Finished tasks (a merged pull request, or declared `acknowledged` or `dismissed`) are skipped by `quiet`, `ended-undeclared`, `blocked-unanswered`, `review-loops`, `wrong-model`, `deep-stack` (as the task that fires; it still counts in a stack above it), `cost-outlier` and `lead-heavy`. `past-limit` is not: a session running past the limit spends money whatever its pull request says.

The two cost criteria read the monitor, not the plugin: set `monitor` in the settings to the path of `isshoni` and each `health` or `watch` runs `isshoni sessions --json` once (7 seconds over all transcripts on the author's machine; 120 seconds at most). Without the setting, or when the monitor fails, they print `not evaluated`. The median is over this repository's tasks that have a merged pull request and a cost above 0; with fewer than 5 there is no median and they are `not evaluated`. The monitor's price file sets the currency. The thresholds come from this repository's 23 landed tasks (median 6.52, p75 10.48, p90 15.35, max 19.08, so 2.93 times the median): `cost-outlier` at 3 times the median would have fired on none of them. The lead's own share of cost (`main_pct`) had median 78.6, p90 88.3, max 90.5, and 54.7 to 82.2 among the 12 that cost at least the median; 85 is just above what those 12 showed. A task in its first minutes shows 100 % in the lead, which is why `lead-heavy` needs a cost of at least the median.

The dispatcher closes the loop: `firing <id> acted|ignored` on each escalation, `miss` for a problem that was not escalated (`--firing` when it had fired and was suppressed). `firings` lists the log, then precision `acted/(acted+ignored)` and recall `acted/(acted+missed)`.

`firings-YYYY-MM.jsonl` records carry only `ts`, `repo` and one of: a firing (`id`, `criterion`, `escalate`, `slug`, `subject`, `detail`); a decision (`id`, `decision`: `escalated` or `suppressed`, `reason`, `by`: `site-manager` or `watch`); an outcome (`id`, `outcome`); a clearing (`id`, `cleared: true`); a miss (`miss`, `slug`, `firing`); a digest marker (`digest`: the slugs of the tasks the digest covered), which has no `id`.

### Digest
A digest answers where a task's money goes. It is a set of findings computed by a script from `isshoni anatomy --json` (the monitor's per-task cost anatomy), then worded and filtered by the same headless Sonnet run as `watch` (`Job: digest`), which messages the dispatcher (first line `DIGEST: <repository directory name>`, then a `Tasks:` line naming the tasks landed since the last digest, then one line per finding it kept) or sends nothing. A finding is a criterion with `"job": "digest"` in `criteria.json`: it is logged as an ordinary firing, decided by the site manager, closed by the dispatcher with `factory firing <id> acted|ignored` and counted by `firings`. A finding describes one window, not a lasting condition, so the digest marks its firings cleared when it ends, and then writes the marker.

- **Window.** The tasks of this repository that have a merged pull request (`worktree-<slug>`) and a cost above 0, oldest merge first. The current ones merged after the last digest's marker (with no digest yet, the newest 5); the baseline is every one before them. With fewer than 5 in the baseline, or none current, a finding is `not evaluated`.
- **Cadence.** `watch` makes a digest when the last marker is at least 24 hours old (or there is none), the repository has `digest` entries, and at least 5 tasks have landed since the last one. So: at most one a day, none until 5 more have landed. The anatomy only moves when tasks land, a median needs 5 of them (the number the cost criteria use), and the reader's attention is the cost being managed. A tick inside the 24 hours costs nothing; one past them runs `isshoni anatomy --json` once (about 10 seconds on the author's machine) to count what landed, and a digest that is sent costs one Sonnet run (about $0.15). It does nothing when the tick has no dispatcher or fired `dispatcher-missing`. Without `monitor` in the settings, or when the monitor fails, it prints one `digest skipped: <why>` line per due tick and records nothing. A marker is written when at least one finding was evaluated, even if none fired. If the run is unusable, no marker is written, the firings are cleared, the command exits 1 and the next due tick tries again.
- **`factory digest`** makes one now whatever the cadence, and `--dry-run` prints the findings and the `not evaluated` list as `health --json` does, logging nothing and starting no model.

| Finding | Threshold | Fires when |
|---|---|---|
| `mix-shift` | 5 (points) | the share of total cost of one token class (`input`, `output`, `cache_write_5m`, `cache_write_1h`, `cache_read`), current against baseline, moved by at least that many points; the class that moved most |
| `dearest-task` | 1.5 (times) | the dearest current task cost more than that many times the baseline's median task; names the role that explains most of it |
| `role-growing` | 20 (percent) | a role in at least 3 current and 3 baseline tasks has a median context per call, or median number of own tool calls per task, that much above the baseline's |
| `version-shift` | 20 (percent) | at least 3 current tasks ran a plugin version no baseline task ran, and their median task cost, the lead's share of cost or the lead's median context moved by more than that, up or down |
| `lead-authoring` | 50 (percent) | the lead made a product-code or test write (`written.product` or `written.tests` calls above 0 in its anatomy block) in that percent or more of the current tasks; names them and compares with the baseline. Not evaluated with a monitor that reports no `written` |

To turn the digest off, delete the five `"job": "digest"` lines of `criteria.json`, or one of them to drop that finding. Without `monitor` in the settings it is skipped. A sixth finding is one line in `criteria.json`, one function and one entry in `CRITERIA`.

## Merging
A model, the lander (`factory/agents/lander.md`, Sonnet), takes a pull request from "the reviewer approved" to the default branch: it keeps the pull request mergeable when the base moves (`factory land`) and merges it when the human approves. Scripts are its narrow tools and the thing that notices an approval. The site manager only watches and escalates. Three scripts:
- **`factory merge`** merges pull requests with no model. It merges only what is mechanical and stops at the first thing that is not. `factory merge <number>...` and `--all` (every open pull request whose task is handed over; the others print `#N skipped: <why>`; with none left, `nothing to merge`) are the caller vouching for the human's word. `--approved` makes GitHub's own records the gate: each pull request is merged only when it holds a valid approval, read at that moment. `--approved --all` merges every handed-over pull request that is approved and prints `#N skipped: <why>` (not approved, or a stale approval) for the others; only an approved one that then fails its merge stops the run. One command merges at most one pull request, so the next approved one stops `behind` (see the `behind` blocker).
- **`factory lander [<number>...]`** is the one way a merging lander starts (the dispatcher, the noticing tick, the human). Numbers are on the human's word; with none it takes the open pull requests approved on GitHub (`nothing approved`, exit 0, when there are none), ignoring what was noticed before. One run per repository at a time (`fcntl.flock` on `lander-<repository>-<8 hex>.lock` in `~/.claude/factory/`; held: `a lander run is already going; run it again when it ends`, exit 1).
- **The noticing tick** (see Site manager) starts the same run for what was approved since the last tick.

**The approval.** Two kinds count:
  - *An approving review.* Per login, the newest review that is not comment-only (`COMMENTED`, `PENDING`) is its verdict, so a later `CHANGES_REQUESTED` or a dismissal withdraws an approval and a later comment-only review does not. An `APPROVED` verdict counts when it is on one of the pull request's approved heads (below); one on another commit is a `stale` blocker. Of several approvals, one on an approved head is preferred, then the newest.
  - *An `lgtm` comment.* Its whole body, trimmed, in any case, is `lgtm`, and it was created after the branch last moved off the approved heads (GitHub's activity feed for the branch, 30 entries: the oldest of the consecutive newest pushes that left it on an approved head; the newest must be the head). Review bodies do not count. An `lgtm` can approve a pull request whose review is on an older commit; the `lgtm` rules then decide.
- **A draft never starts a lander run** (the notice does not take one as a candidate), but the draft flag itself is not a gate: under `--approved` hand-over plus green checks on an approved, up-to-date head is, and a draft that passes them is marked ready (`gh pr ready`) and merged, as with the human's word. The tick's draft sync can put a pull request back to draft while its checks are pending; that does not stop its merge.
- **Who may approve**, for both: a login whose GitHub `user.type` is `User` (a bot never), with `admin` or `write` permission on the repository, and not the pull request's author. The exception: an author's `lgtm` counts while `lgtm_from_author` is `true` (the default); an author's review never does.
- **An approval survives a clean merge of the default branch.** The lander brings a pull request up to date by pushing a merge of the default branch, which moves the head after the approval. `approved_heads` starts at the head (after the `git fetch` made for that pull request), and while a commit has exactly two parents, its second parent is an ancestor of `<remote>/<default>` (the pull request's own base is not asked: it can be retargeted after the approval), and `git merge-tree --write-tree` of the parents prints the commit's own tree, it steps to the first parent. The commits visited are the heads an approval may sit on. Any other commit on top (a conflict resolution, a new commit) makes the approval stale: the human approves again. If git cannot answer, the set is just the head.

**Nothing technical tells the human's approval from one an agent posts when they share a login.** What is decided, per identity of the pull request's author:
- *The factory's App* (see Identity): the lead's pull requests are authored by the bot, so your approving review counts (GitHub does not let you approve your own pull request, which is why it could not with one account) and so does your `lgtm` (you are not the author). Nothing the bot posts counts: its comments and reviews have `user.type` `Bot`. A mechanism, and `lgtm_from_author` has no effect on it.
- *A second account of its own* (a regular user with write access): it looks like the human. Set `"lgtm_from_author": false` in the settings once the factory has such an account; its `lgtm` stops counting while another user's still does.
- *Without an identity* (your own `gh` login, the fallback): `lgtm_from_author` stays `true`, and the `lgtm` from the author rests on a rule written into every role file: no agent ever posts one, and none ever approves a pull request.

Per pull request, bottom-up through a stack (a pull request based on another selected one goes after it). Each check that fails is a blocker with a kind:

| Kind | Blocker |
|---|---|
| `fork` | its head is in another repository |
| `handover` | no task worktree has its head branch; or the task is not in phase `review`; or the worktree's head is not the pull request's head |
| `behind` | the invariant: a pull request is merged only when its head already contains the current tip of the default branch (`git fetch` for each pull request, never one fetch shared by a command) and its checks are green on exactly that head; otherwise `<remote>/<default branch>`'s tip is not an ancestor of its head. Both modes; in `--approved --all` a stop like any other. One command merges one pull request: whatever follows it is `behind` (not attempted, once a stop ends the run; in a dry run every pull request after the first that would merge prints `would stop`), because the merge moved the default branch. Several ready pull requests are therefore merged one at a time, each brought up to date (`factory land <slug>`) and re-checked by CI first: N ready pull requests cost about N-1 extra CI runs. A stacked pull request whose base merged is `behind` too until it holds the merge commit. If the repository later requires "branch up to date" in branch protection, GitHub enforces the same invariant and a refused merge (a `merge` stop with gh's message) is retried the same way. If git cannot answer it is `pending` |
| `base` | its base is neither the default branch nor the head of a pull request merged into it |
| `ci` | no checks, a failed or cancelled check, or no passed check |
| `pending` | a check is still running; GitHub has not computed mergeability after 5 asks 3 seconds apart; the base's pull request cannot be read |
| `conflict` | it conflicts with its base |
| `unapproved` | (`--approved` only) no valid approval on GitHub |
| `stale` | the head changed after the approval (a review on a commit that is not an approved head, or an `lgtm` older than the last change off the approved heads): a fresh one is needed |
| `head-time` | (`lgtm` only) the activity feed does not name the pull request's head, so when it changed cannot be told |
| `merge` | a `gh` step failed |

Then it retargets the pull request onto the default branch when its base is a merged one (`gh pr edit --base`), marks a draft ready (`gh pr ready`; only a fallback, `watch` has normally done it, see below) and merges with a merge commit, pinned to the head it checked (`gh pr merge --merge --match-head-commit`). Merge commits keep branches stacked on it valid; squash would not. After any merge it runs `clean` and fast-forwards the main checkout (`git pull --ff-only <remote> <default>`) when it is on the default branch; a failure prints `main checkout not updated: <why>` and does not fail the merge (`clean` does not pull it).

The draft flag of a task's pull request follows its recorded state: ready for review exactly when the task is handed over, its head is the pull request's head and its checks pass (the test `merge` uses), otherwise a draft. `factory state working|blocked` and a landing that declares `working` put it back to draft at once (`gh pr ready --undo`, result ignored); every `watch` tick (the 2-minute one) sets the rest, before the approval notice: a handed-over pull request turns ready up to one tick after its checks go green, and a ready one whose head moved or whose checks fail goes back to draft. The first tick after this rule existed sets every open task pull request from its recorded state (the migration). Pull requests from forks and without a task, and tasks that are settled or merged, are left alone. `status` agrees: a `review` row whose pull request is a draft shows `pr_draft` and prints `waiting on checks`, not `waiting on the human`, and the dashboard does not list it as waiting.

- `merge` prints `#N merged <url>`, or `#N stopped: <reason>` and `#M not attempted` for the rest; exit 0 when everything merged, 1 on a stop or a failed step, 2 for a number that is not an open pull request. `--dry-run` changes nothing, checks every pull request (the approval too) as if the earlier ones had merged, and prints `#N would merge` or `#N would stop: <reason>`; mergeability of a pull request that would first be retargeted is not checked.
- **`factory lander` run.** In the main checkout it starts `claude -p --agent factory:lander --plugin-dir <plugin> --model sonnet --permission-mode dontAsk --allowedTools <MERGE_TOOLS> --output-format json <brief>` (`MERGE_TIMEOUT`, 3600 s) with `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS` at 2400000 in its environment, since a `factory land` inside it runs the full tests. The brief starts `Merge run.` and lists the repository, each pull request (number, head and base branch, task and its lead's session name or `no task`, and how it is approved: `on the human's word: merge with factory merge <n>` or `approved on GitHub: merge with factory merge --approved <n>`) and who started the run: `The dispatcher started this run: do not message it.` when numbers were given, else the dispatcher's session name, or that none is alive.
- **`MERGE_TOOLS` is the enforcement.** `Read`, `Grep`, `Glob`, `SendMessage`, `ToolSearch`, `Bash(factory merge --approved *)`, `Bash(factory land *)`, `Bash(factory status *)`, `Bash(factory status)`, `Bash(gh pr view *)`, `Bash(gh pr checks *)`, `Bash(gh pr list *)`, `Bash(gh run view *)`, `Bash(sleep *)`, and, for each number the caller passed on the human's word, the exact `Bash(factory merge <n>)`. The human's word reaches the lander as a permission the script builds from its own arguments, never as text. By the allowlist the lander cannot: merge an unapproved pull request (`factory merge <n>` for a number not given is denied, and `--approved` checks GitHub), approve or comment (so never post an `lgtm`), merge anywhere but the base (`factory merge` retargets and merges; there is no `gh pr merge`), force-push or push at all (no `git`), or edit code or tests (no `Edit`). By rule only (`factory/agents/lander.md`): touching only the pull requests given, the order (a stack bottom-up, otherwise by number), and what counts as mechanical inside the nested `factory land`. `MERGE_TOOLS` is the whole permission set only while no user, project or local settings file adds `permissions.allow` rules: `claude -p` loads those too. The run's `PATH` has this `factory`'s directory first (the schedule's `PATH` holds only git, gh, claude and Python), so a nested `factory land` finds `factory`, `claude`, `git` and `gh`.
- **Result.** The reply's `## Result` has one line per pull request, `#N merged <url>` or `#N stopped <kind>: <evidence>`; the script prints them, then `lander: <turns> turns, $<cost>, <seconds> s`. A pull request that is no longer open after a run that failed prints `#N merged <url>` (a timeout must not report a merged pull request as stopped). A pull request with no line, or every other one when the run failed or its reply could not be read, prints `#N stopped other: the lander gave no line for it` (with `timed out`, `exited <rc>` or `its reply could not be read`). Exit 0 when everything merged, else 1. Kinds: `unapproved`, `stale`, `behind`, `ci`, `pending`, `conflict`, `tests`, `handover`, `base`, `other` (the same kinds `lgtm-blocked` carries in its subject `#<n>/<kind>`). With no live dispatcher the script notifies the human of each stop (as for `dispatcher-missing`); with one, the lander escalates it itself and the script records the stop's `lgtm-blocked` firing as already escalated (`by` `lander`), so the health run does not send it again.
- **`lander.json`** (`~/.claude/factory/lander-<repository>-<8 hex>.json`, written whole and atomically): `noticed` (`{"<n>": "<head>:<approval stamp>"}`; after a run only the run's own pull requests are rewritten, each as its head after the run with the stamp read before it, so a head the lander moved does not start a second run while an approval that came during the run, or on another pull request, starts the next one), `stopped` (`{"<n>": {head, kind, text, ts}}`, dropped when the pull request closes or merges) and `health` (when health last ran). `lgtm-blocked` fires from `stopped`, subject `#<n>/<kind>`, for pull requests still open at the recorded head; deleting it from `criteria.json` silences the escalation, not the merging. To turn merging on an approval off, remove the schedule; while a default-named dispatcher session lives, its next prompt installs it again, so there is no lasting off switch short of ending the dispatcher.
- **Moving to the new behaviour.** The installed schedule keeps its old interval (30 minutes) until it is installed again: `factory schedule install` from the main checkout (or a dispatcher's next start or resume, which replaces the job). Nothing here does it for you.
- **A lander run blocks its tick.** The tick that starts a run waits for it (up to `MERGE_TIMEOUT`, an hour); the ticks meanwhile find the lock held and skip silently. Installing the schedule again (a dispatcher session start, `factory schedule install`) kills the run in flight; the next tick takes the pull requests up again, since they were not recorded as noticed.
- `clean` keeps the worktree the running plugin lives in: leads started by it load their plugin from there.

## Comments on a pull request
Each `watch` tick notices new reviews, plain comments and (for a pull request with a new review) comments on lines, on the open pull requests of tasks, and forwards what **the human** wrote to the task's lead, verbatim.
- **The human** is a `User` account (an App with write access is not one) whose association is `OWNER`, `MEMBER` or `COLLABORATOR` and whose repository permission is `admin` or `write`, from GitHub's records, never from comment text. A bot, and anyone else, is logged and not forwarded; third-party tools and other authors are not handled yet. An `APPROVED` review, an `lgtm` comment (the merge path owns them) and a `COMMENTED` review with no body (its line comments are the content) are logged, not forwarded.
- **Forwarding**: one batch file per task per tick, `~/.claude/factory/comments/<slug>-<UTC time>.md`, the comments quoted in fenced blocks, marked as data. A headless Haiku run (`claude -p`, about $0.01 and 3 s; it sees only the recipient's name and one fixed line, never comment text) sends `PR COMMENTS: <slug>: <k> new from the human on #<n>: read <path>` to the lead's session. When the lead's session is gone or the message could not be delivered, the dispatcher gets it once, as `PR COMMENTS: <slug> (not delivered to its lead): ...`; failing that, a desktop notice names the file. The batch file is the durable copy; there is no retry.
- **How soon**: one tick, the watch interval. **Cost**: no GitHub call without a task working, blocked or handed over; one `gh pr list` per tick; one more call per pull request with a new review; one Haiku run per batch; nothing on a quiet day.
- **Where**: `comments-YYYY-MM.jsonl` logs every new item once (`ts`, `repo`, `slug`, `pr`, `id`, `url`, `kind`, `author`, `association`, `author_kind`, `decision`, `to`, `batch`; no text). What was seen is in `comments-<repo>-<hash>.json` in the store. The first run after install records what is there and forwards nothing.
- **Limits**: an edited comment is not seen again; `gh pr list` returns at most the first 100 reviews and comments of a pull request; a pull request with no task worktree is ignored.
- **A hostile comment** can cause a log line and nothing else: only an author with write access is ever forwarded, and no comment text reaches a prompt or the session of a lead directly (the lead reads the file, which says it is data).

## Setup and uninstall
`factory wizard` (or `make wizard`, which takes `ARGS="..."`) walks the steps below in order and can be rerun: every run evaluates every step from the top, skips what is done and prints one line for each (`done:`, `did:`, `skipped:`, `needs you:`). A required step that cannot be completed stops the run, prints what to do and `Then run the wizard again.` and exits 1; an optional step that is declined or cannot run prints one line and the run goes on. It exits 0 when every required step is done and no step failed, else 1. Without a clone (only the installed plugin) the dashboard and cost steps are `skipped`.

| Flag | Meaning |
|---|---|
| `--yes` | accept every offer without asking. Without it an offer prints `question [y/N]` and reads one line from stdin; anything but `y` or `yes` is no, and so is end of input: no answer is never consent, so a non-interactive run (no terminal on stdin) declines every offer unless it has `--yes` |
| `--list` | print each step and its state, change nothing; it runs only the read-only commands `gh auth status`, `claude auth status` and `claude plugin list --json`, and calls no network API |
| `--owner`, `--name` | the GitHub App step: see Identity |

1. **dependencies** (required): `git`, `gh`, `claude` and `openssl` on `PATH`, Python 3.11+, `gh auth status` succeeding and `claude auth status` saying `loggedIn`. It installs nothing; it lists everything missing at once with what to do.
2. **dashboard** (optional, clone only): `bin/isshoni-tui` exists. Offers `make build`; needs Go.
3. **plugin** (required): `factory@factory` is in `claude plugin list`. Otherwise adds the marketplace `andreiciobotar/isshoni` (when no marketplace named `factory` exists) and installs the plugin. A `factory` marketplace from another repository is never replaced: it stops and says so.
4. **settings** (required): `settings.json` exists and is valid. Missing, it is written atomically with the defaults (every key but `monitor`). An existing file that does not parse or validate is never overwritten: it stops with the error and the path.
5. **cost criteria** (optional, clone only): `monitor` names an existing file. Offers to set it to `<clone>/bin/isshoni`, keeping every other key (unknown ones too); a `monitor` that points at a missing file is replaced and the line says what it pointed at. Run from a task worktree it is skipped: that path disappears with the worktree.
6. **GitHub App** (optional): see Identity. A failure here is printed, the run goes on to the summary and exits 1.

The summary lists each step's state and says that the site manager starts with the dispatcher session and stops with it (the plugin's hook installs and removes its job), so nothing is installed for it. A live dispatcher session installs that job again and recreates the home with its logs, so end dispatcher sessions before uninstalling. When every required step is done it prints the two commands to start working, and when the run changed nothing, `Nothing to do: everything is set up.`

`factory uninstall` (or `make uninstall`) removes what the wizard and the factory put on the machine. `--list` says what each step would remove and does nothing; `--yes` confirms every step. Each step says what it found and what will be lost, then asks, then acts; a step with nothing to remove says so, and running it twice is safe. It deletes only on positive evidence that the thing is the factory's; everything else is kept and named in the final list. In order:

1. **schedules**: the watch jobs of this home, for every repository (launchd, systemd or cron). Under another `FACTORY_HOME` a job is this home's when it records that `FACTORY_HOME`; otherwise when it records none. A job of another home, or a file that is not a factory job, stays.
2. **GitHub App**: uninstalls the App's installation (`DELETE /app/installations/<id>` as the App; `404` is "already uninstalled"), then prints and opens the App's settings page: only you can delete the App itself (Advanced, Delete GitHub App). A failed call is reported and the run goes on.
3. **plugin**: `claude plugin uninstall factory@factory` and `claude plugin marketplace remove factory`, the plugin (user scope) when installed, then the marketplace `factory`, whenever that marketplace is `andreiciobotar/isshoni`; a `factory` marketplace from another source is kept with the plugin.
4. **home**: the factory's own names in `FACTORY_HOME` (settings, logs, specs, deliverables, `identity/`, `dashboard/` with the keys of the dashboard over SSH, `watch.log`), each path named before it asks. Anything else is kept and listed, and the directory is removed only when it is then empty.
5. **dashboard binary** (clone only): `bin/isshoni-tui`.

The home is removed only by its known names; under a `FACTORY_HOME` other than `~/.claude/factory` a directory holding anything else is left whole and named, since a mis-set variable must not delete a stranger's files. It exits 0 unless a step failed, and ends with what it left: Claude Code's own transcripts and settings (`~/.claude/projects`), your repositories with their task worktrees and `worktree-*` branches (`factory clean` or `git worktree remove`, before the plugin is gone), the clone, git, `gh`, Go and Claude Code, the App on GitHub until you delete it, and whatever a step declined or kept.

## Identity
`factory wizard [--owner <account>] [--name <app name>]` (or `make wizard`) offers, as its last step, a GitHub App of its own for the factory. Once it is installed, the factory acts on GitHub as that App (see How the identity is used); with no identity stored, or an App stored but not installed, every command acts with your `gh` login, and `factory status` says which. It needs `openssl` on the `PATH` (it signs the App's JWT) and a browser.

First run, with nothing stored:
1. The owner is `--owner`, else your own account (`gh api user`); when that cannot be read it exits 1 naming `--owner`. Pass `--owner` for an organization (`make wizard ARGS="--owner NAME"`). GitHub says whether it is a user or an organization; the App is created under it. The offer is a question first ("Give the factory its own GitHub identity ... Two confirmations in your browser."); no answer is no.
2. The wizard starts a small web server on `127.0.0.1` (a port the OS picks), prints its address and opens it. The page sends GitHub an App manifest named `isshoni-lander-<owner>` cut to 34 characters (an App name is unique across GitHub and 34 characters at most; `--name` sets another, and one longer than 34 exits 2 instead of being cut; you can edit the name on GitHub's confirmation page, the wizard reads the real slug back). **Confirmation one**: create the App. GitHub redirects back to the wizard, which exchanges the code for the App's credentials. It waits 10 minutes, then exits 1 with nothing stored (GitHub creates the App when you confirm, so if you did, delete it on your apps settings page before running again; a failed exchange says the same). Over ssh, forward the printed port (`ssh -L PORT:127.0.0.1:PORT`).
3. The private key and `app.json` are stored at once. **Confirmation two**: install the App on the repositories you choose, on the page the wizard opens; it first says to choose "Only select repositories" and pick the ones the factory works in, because with "All repositories" the bot can write to every repository of the owner. It polls for 10 minutes; on timeout the App stays stored and the next run resumes here.
4. It signs a JWT, mints an installation token, lists the repositories the token reads, looks up the bot user, and prints the App, the bot login, the repositories and how to remove it (`factory uninstall`, or `make uninstall` in the clone). With "All repositories" it prints the count instead of the names, a `WARNING:` line naming the installation page where to narrow it, and that the tokens the factory hands out reach only one repository either way (see How the identity is used). The token is never printed or stored.

Permissions the App asks for, and why:

| Permission | Level | Why |
| --- | --- | --- |
| Contents | write | push a task branch; merge a pull request (the merge endpoint is under Contents) |
| Pull requests | write | open, edit, mark ready and comment on pull requests |
| Checks, Commit statuses | read | `gh pr checks` |
| Actions | read | `gh run list`: health reads CI on the default branch |
| Metadata | read | implicit |

Left out on purpose: `workflows` (so the bot cannot change CI: a branch touching `.github/workflows/` must be pushed by you, see below; with it, a confused lead could push a workflow that reads every repository secret and mints a write token, merging its own pull request: it would remove your merge gate) and `issues`. No webhook is active.

Files, in `~/.claude/factory/identity/` (mode 0700):
- `key.pem` (0600): the App's private key. Never printed or logged.
- `app.json` (0600): `app_id`, `slug`, `client_id`, `html_url`, `owner`, `owner_type`, and once verified `installation_id`, `installation_url`, `repository_selection` (`all` or `selected`, refreshed on every run), `bot_login`, `bot_id`, `bot_email` (`<bot_id>+<slug>[bot]@users.noreply.github.com`).

Rerun with an identity stored: it never creates a second App, `--owner` naming another account exits 1 (one identity per machine), and `--name` exits 1 (the wizard does not rename). A `key.pem` without `app.json` exits 1 before any call, naming the `rm -r` to run. It sets looser modes back to 0600/0700 and says so; reports a missing `key.pem` (exit 1); reports when GitHub no longer knows the App or its key was revoked (exit 1, files untouched); opens the install page when the App is not installed; exits 1 when the installation sees no repositories, naming the page where to choose some; otherwise verifies, refreshes `app.json` (slug, URL, bot login, id and email come from GitHub's answer) and prints the report, exit 0. A failure that means the App is broken (key missing, App gone) prints the undo lines.

To rename the App, change its name on its GitHub settings page (there is no API for it), then run `make wizard` (or `factory wizard`): it reads the new slug from GitHub, records it with the bot's login and email, and prints `renamed: <old slug> -> <new slug>`. The App id, its key and the installation stay; `factory env` does not need the wizard, since no token depends on the name. Commits already made under the old name keep it in git and stay attributed to the bot on GitHub (same account id). Running leads use the new name at their next command (see below).

Headless machine: on Linux without `DISPLAY` or `WAYLAND_DISPLAY` the wizard does not open a browser (it would start a text browser in the terminal); it only prints the URL. GitHub redirects the browser to `127.0.0.1`, so opening that URL on another machine works only with the port forwarded (`ssh -L PORT:127.0.0.1:PORT`). Otherwise run the wizard on your laptop, then copy the directory (`scp -rp ~/.claude/factory/identity HOST:.claude/factory/`, or mount it into the container) and run `factory wizard` there: it verifies and prints the report.

### How the identity is used
An identity stored by an earlier wizard has no `repository_selection`: run `factory wizard` again to record it (and after narrowing the installation on GitHub).

Who acts as the App: lead sessions and their subagents (pushes, fetches, `gh`, and commits authored and committed as `<bot_login> <bot_email>`), and the script's own `gh` calls (`status`, `new`, `health`, `watch`, `merge`, `digest`, `land`; `land`'s `git fetch`, `merge` and `push` also act as the App). Only in a repository whose `origin` is on GitHub and belongs to the App's owner (the accepted forms are `https://[user@]github.com/<owner>/<repo>[.git][/]`, `git@github.com:<owner>/<repo>[.git]` and `ssh://git@github.com/<owner>/<repo>[.git]`, the host in any case; any other form, an ssh port included, means no identity and your login is used): elsewhere, or in a repository of another owner, there is no acting identity (`factory env` prints nothing, `gh` gets no token, `status` says so) and the `gh` login is used. Not the dispatcher's own shell or your terminal; `eval "$(factory env)"` gives any shell in such a repository the same identity.

Mechanism. `factory env` prints these exports (every value shell-quoted; when stdout is a terminal `GH_TOKEN` is shown as `***`, so `eval "$(factory env)"` keeps working and a bare run leaks nothing):

| Variable | Value |
| --- | --- |
| `GH_TOKEN` | an installation token |
| `GIT_AUTHOR_NAME`, `GIT_COMMITTER_NAME` | the bot login |
| `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_EMAIL` | the bot email |
| `GIT_TERMINAL_PROMPT` | `0` |
| `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n`, `GIT_CONFIG_VALUE_n` | four config entries: an empty `credential.https://github.com.helper` (drops every helper configured before, such as the keychain or `gh auth git-credential`), then a helper that answers `x-access-token` and `$GH_TOKEN` (read from the environment when git calls it; the token is not in the config), and `url.https://github.com/.insteadOf` for `git@github.com:` and `ssh://git@github.com/` (ssh remotes of github.com are used over https) |

The plugin's `SessionStart` hook (`factory hook`) appends one line, `eval "$(<path of factory> env)"`, to the file named by `CLAUDE_ENV_FILE`, which Claude Code runs as shell code before every Bash command. It does so for a lead session (a session in a task worktree, not a subagent's start), once (the line is not added twice), whether or not an identity is stored: running the wizard takes effect in running leads at their next command, and removing the identity undoes it. The dispatcher and any session outside a task worktree get no line. "A task worktree" is read from the path alone: any session whose project directory is `<repository>/.claude/worktrees/<name>` (a name not starting with `agent-`), in any repository where the plugin is enabled, whether or not `factory new` made it; the exports then apply when that repository's `origin` belongs to the App's owner and the App can reach it. When the owner matches but the installation does not cover the repository, git and gh fail in that session (`GH_TOKEN=unavailable`) rather than fall back to you. So with the App installed on all repositories, worktree sessions in your other repositories also commit and push as the bot, while sessions in a main checkout stay you. The script's own `gh` calls get `GH_TOKEN` in the child's environment; its `git` calls are local except `land`'s fetches, merge and push, which run with the exports of `factory env` (see Landing without the lead).

Tokens last one hour at GitHub and are scoped to the repository the command runs in: the mint asks for `repositories: [<name of origin>]`, so the token reaches that repository only, whatever the installation covers. A repository the installation does not cover is refused by GitHub (422): the message says `the App is not installed on <owner>/<name>: add it at <installation url>`, and `factory env` fails closed as for any mint failure. The token is cached per repository in `identity/token-<name>.json` (0600) and minted again when under 15 minutes remain, so every Bash command starts with at least 15 minutes, which is more than a foreground command may run (10 minutes). Limits: a background command that outlives its token; a session started before plugin 0.5.0 has no hook line (restart the lead); `GIT_CONFIG_*` variables set by the caller are replaced; only `github.com`.

Secrets. The token is in the environment of the lead's shell commands: an agent can read it. It reaches only the repository the command runs in, with the permissions in the table, and it expires. The identity is a default, not a boundary: the dispatcher session still acts with your login, and a lead's shell can still reach your own `gh` login or keychain by unsetting the variables, so the rule that no agent posts `lgtm` or approves a pull request stays. The key never leaves `identity/`, is read only by `openssl` when a token is minted, and no role is told where it is.

Failure. When an identity applies (installed, and this repository on GitHub under the App's owner) but anything goes wrong finding it or minting the token (a refused mint, GitHub 422 for a repository the installation does not cover, a corrupt or malformed `app.json`), `factory env` prints one line with the reason on stderr, exits 1, and still prints the lock-down: `GH_TOKEN=unavailable`, `GIT_TERMINAL_PROMPT=0` and the four `GIT_CONFIG_*` entries (so `git` cannot reach your credential helper or your ssh key for github.com), plus the bot's author and committer variables when the identity itself could be read. Each command then shows the reason and `git` and `gh` fail with an authentication error; in a lead session they never fall back to your login. A corrupt or malformed `app.json` locks down every repository where `env` runs, not only the App owner's, because the owner cannot be read. When no identity applies, it prints nothing.

`.github/workflows/`: GitHub refuses the App's push of a branch whose own commits change a workflow file, with a message that holds ``without `workflows` permission``. The push is tried and the refusal recognised by that text (no check predicts it). It normally comes at the task's first landing: the lander stops `denied`, the lead (who knew from planning, by its rules) sends `BLOCKED:` with the command, and the dispatcher passes you one line. `factory land` stops `denied` the same way. The one command, from your own terminal: `git -C <main checkout>/.claude/worktrees/<slug> push -u origin HEAD`, never a force; then tell the dispatcher, and the lander opens or updates the pull request. A merge that only brings the base's workflow changes into a branch is accepted (probed 2026-11-14 on a real repository as the App), so a task that does not itself touch workflows never meets the refusal. Workflow changes are rare (1 of about 45 pull requests on 2026-11-14).

Checked with a real App, read-only: a token minted for one repository reaches that repository only although the installation covered all (another repository of the owner answers 404); `gh pr view --json statusCheckRollup,reviews`, `gh pr list`, `gh pr checks`, `gh run list`, the `collaborators/<login>/permission` and `activity` reads, and GraphQL `viewer` (the bot) all answer; the credential helper authenticates `git push --dry-run`.

Proven as the App: `gh pr create`, `gh pr ready` and `gh pr ready --undo` (both exit 0 when the flag already has that value). Not yet proven, the first real task will show: `gh pr edit --base` and `gh pr merge --match-head-commit` as the App; a real push and the bot showing as author on GitHub; that the lander's later push of an already pushed head succeeds; branch protection that restricts who may push or merge (the App must be allowed there).

Undo: `factory uninstall` uninstalls the App and removes `identity/`; you delete the App itself (`https://github.com/settings/apps/<slug>/advanced`, or `https://github.com/organizations/<owner>/settings/apps/<slug>/advanced`; no API deletes an App).

## In a container
[container.md](container.md) runs the factory on an always-on Linux host: an image with Claude Code, `gh`, git, Python and Go (`docker/`), all state in one host directory, a non-root user, CPU and memory limits. The site manager's job uses the cron backend there, run by supercronic because a container has neither systemd nor a root cron; the rules above hold unchanged. `isshoni host add` sets it up from a laptop over SSH (the tooling lives in `~/.isshoni` in the container). The same page lists the command's steps, what a lead in `auto` mode could damage, and how the factory's GitHub identity gets into the container.

## Known limits
- Nothing caps what a lead spends; the time limit is checked by the lead between subagent runs.
- A message that a base moved still wakes a lead that is working: it passes it to its lander. A handed-over task is landed by `factory land` without its lead; what the lander may do rests on its rules and its tool list, not on a mechanism: Bash can do anything the session may, and the scripted path trusts the session list to tell a lead that is running. When a stacked task's base was squash-merged by hand, the merge brings the base's old commits back as conflicts: `land` stops on a conflict, and the lead sorts it out (the factory merges with merge commits, so its own stacks merge clean).
- A worktree made by hand under a slug used before inherits that slug's last declared state.
- A store nobody writes to is never pruned. A month file and `watch.log` have no size limit.
- The monitor adds up the cost of a reused slug, so a task started under an old slug looks dearer than it is. A model the monitor has no price for understates the cost.
- Merging: without an identity (the author's own account) the author's `lgtm` rests on a rule, not a mechanism (see Merging). A `CHANGES_REQUESTED` review by a different login does not block a merge. The author comparison and the bot test rest on GitHub's `user.type` and login. Checks are not rerun after a retarget, and GitHub does not test the merge result: mergeable means no conflict. A pull request with no task worktree is a `handover` stop; the human merges it. At most 100 open pull requests are seen. An `lgtm` during a running check is the lander's to wait for. Lander runs are serialised by a lock; a plain `factory merge` is not, so when it and a lander merge at once the second `gh pr merge` fails and is reported.
- The site manager's thresholds are first guesses; `quiet` reads file times, so a lead waiting on a long command looks quiet; a run that dies after sending may escalate the same firing again next tick. A site manager run is read as one JSON document on `claude`'s standard output.
- Two repositories whose directories share a name share a spec folder and a default dispatcher name.
- Identity: the private key itself can mint a token for any repository of the installation, so a narrow installation ("Only select repositories") is still the real boundary, not the scoping of the tokens handed out; during a GitHub outage each lead command waits for the mint attempt (up to 30 s) once the cached token is within 15 minutes of expiry (a cached token that has not expired is used when the mint fails); one per machine; `workflows` is not granted; only `github.com`; a background command can outlive its token; a lead started before plugin 0.5.0 has no hook line; `GIT_CONFIG_*` set by the caller is replaced. See How the identity is used, including what only a real run proves.
