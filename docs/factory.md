# factory reference

The `factory` command of the plugin (Python 3.11+, standard library; needs `git`, `claude` and, for pull request state, `gh`). Run it inside a repository: the main checkout or any task worktree. Exit codes: 0 ok, 2 usage or precondition error (one line on stderr), 1 a `claude`, `git`, `gh` or scheduler step failed or a log could not be written.

## Install
In a clone of the repository, `make wizard` does every setup step (see Setup and uninstall); with only the plugin, run `factory wizard` after installing it (in a Claude Code session the plugin's `bin/` is on the Bash tool's `PATH`, so `factory` works there). By hand, in Claude Code: `/plugin marketplace add andreiciobotar/isshoni`, then `/plugin install factory@factory`; `/factory:dispatch` makes the session the dispatcher, whatever it is called. To try it for one session without installing, start `claude --plugin-dir <clone>/factory`. `gh` must be authenticated (`gh auth status`); the wizard offers GitHub's optional `gh stack` extension. macOS and Linux; Windows is not supported. Leads run unattended: nobody watches a lead's session (`sessions.lead_permission_mode`, see Settings).

## Tasks
A task is one slug: lowercase letters, digits and single hyphens, 3 to 40 characters, not starting with `agent-`. From it follow the worktree `.claude/worktrees/<slug>`, the branch `worktree-<slug>`, the lead's session name `<slug>`, and the spec `~/.claude/factory/specs/<repository directory name>/<slug>.md`. Specs are working papers and are never committed; they outlive the worktree.

A session belongs to a task when its `cwd` is in the task's worktree, or when it is the task's exited lead (a background session with no `pid`, named like the slug, with `cwd` at the main checkout). A task whose finished sessions are several is not held; only two or more exited sessions carrying its name at the main checkout are ("cannot tell which is its lead").

## Using it on your own repository
It needs a git repository with an `origin` on GitHub, `gh` authenticated, the plugin, and a session that runs `/factory:dispatch`. CI checks may have any name. Nothing is configured and nobody is asked for a test command: each lead finds how the repository runs its full tests, as an engineer would (its instructions, README, CI workflow, manifest, Makefile), runs it once and states it for its task with `factory commands test '<command>'` (a golden command likewise with `factory commands golden '<command>'`; it may hold several steps, it is run with `sh -c`). The factory records it in the repository's git config beside the task's base, `branch.<branch>.factoryTest` and `branch.<branch>.factoryGolden`, so it goes with the branch. `factory commands` prints what a task resolves to. A repository with no tests is stated with `factory commands test none`: the landing then runs nothing, says `NO TESTS WERE RUN: none found in this repository` in its report and its pull request comment, and still pushes.

**Setup of a fresh worktree.** A repository whose checkout needs more than `git checkout` (dependencies, a build, an untracked file) declares one command, in its own git config and not in a file a pull request can change: `git config factory.setup '<command>'`, run in the main checkout. With it set, `factory new` makes the worktree itself (without `--base`: `git fetch <remote> <default>`, then `git worktree add --no-track -b worktree-<slug>` from `<remote>/<default>`; with `--base` as before), runs `sh -c '<command>'` in it with `factory new`'s own environment and a limit of 90 s (`SETUP_TIMEOUT`), writes its output to `~/.claude/factory/specs/<repository directory name>/<slug>.setup.log` (mode 0600), prints `setup: succeeded` or `setup: failed (exit N), see <log>` (`timed out after 90 s` for a timeout), and starts the lead whatever the outcome: a failed setup never removes the worktree. The lead's first message names the command, the outcome and the log. The build's tech lead and the lander's brief carry the command too, so a scratch copy or an isolated worktree is made ready the same way. With no key, or an empty one, nothing changes.

It does not assume a language, `make`, the name of a check, or a default branch called `main` (it reads `origin/HEAD`, and uses `main` only when that is unknown). It does need a clone of this repository for the dashboard and the cost criteria (`paths.monitor`). `factory rerun` names only Go and unittest failures: the failed checks of any other runner get no re-run.

## Commands
```

factory build <slug> [--note <text>] [--dispatcher <session-name>]      # start the tech lead on the build (run in the task's worktree)
factory status [--json] [--cached] [--max-age SECONDS]
factory clean [--dry-run]
factory state working | blocked [human|dispatcher|<slug>[,<slug>...] [--paused]] | handed-over <deliverable>
factory overrun '<text>'                          # a lead over its limit, or stuck, asks the site manager for time (run in the task's worktree)
factory commands [test|golden] [<command>|none]   # a lead states its task's test or golden command; without a value, prints it
factory ack <slug> acknowledged | dismissed
factory close <slug> --reason <text> [--superseded-by <slug>]            # the dispatcher drops a task that will never finish; the site manager's `closed` decision does the same
factory feedback [--json] [--status open|accepted|rejected|done] [--kind issue|decision] [--since <ts>]
factory feedback add --role <role> [--slug <slug>] [--model <model>]     # a report or items on stdin
factory feedback decide '<what>. Why: <why>'                             # 200 characters at most
factory feedback set <id> open|accepted|rejected|done [--pr <url>]       # id or a unique prefix
factory retro [<file>]                                                   # a JSON object, on stdin or in the file
factory log events|retros|reviews [--since <ts>] [--until <ts>]
factory hook                                                             # run by the plugin's hooks
factory ops-hook                                                         # run by the plugin's hooks: gates and records the ops explorer's MCP calls
factory ops start <name> "<goal>" --every <duration> --until <duration|UTC time> --budget <usd>   # the human only, in their own terminal
factory ops list [--json]
factory ops stop <name>
factory health [--json] [--dispatcher <session-name>]
factory watch [--dispatcher <session-name>]
factory digest [--dispatcher <session-name>] [--dry-run]
factory review [--run]                                                   # the kaizen review: decide if one is due and, when it is, run it; --run is the detached form the watch tick starts
factory schedule install|remove|status
factory dispatcher [--json]
factory dispatcher register
factory firing <id> acted|ignored                                        # id or a unique prefix
factory miss <text> [--slug <slug>] [--firing <id>]
factory firings [--json]
factory pauses                                                           # the churning tasks the queue paused
factory lead <slug> '<message>'                                          # queue a message for a task's lead; the next tick delivers it, bringing a lead the harness retired back
factory merge (<number>... | --all) [--dry-run] [--approved]
factory lander [<number>...] [--dispatcher <session-name>]      # merge everything that is ready, here and now
factory lander --window <minutes>                                # the human's word for every handed-over pull request; 0 closes it
factory wizard [--yes] [--list] [--owner <account>] [--name <app name>]   # the whole setup walk; rerun to finish or repair
factory uninstall [--yes] [--list]                                       # remove what the wizard and the factory put here

factory land (<slug> | --all)
factory tech-lead <slug> <number> <evidence> [--dispatcher <session-name>]   # started by the lander's loop; usable by hand
factory overlap <old base> <old head> <target>                           # what both sides changed, and whether anyone must look
factory scratch <commit>                                                 # a new directory with that commit's files (no .git); prints its path (run in a worktree; needs Python 3.11.4 or later)
factory rerun <number>                                                   # re-run a red check once when the failure looks like a flake (a held pull request: on the human's word)
factory unblock <number> [--by <text>]                                   # release a pull request the queue holds as not-ours
```

- **`new`** starts a lead: a background session in a new worktree, with `factory/roles/lead.md` appended to its system prompt, declared `working`. The calling session must be the repository's dispatcher (see How the dispatcher is found). It refuses a slug whose worktree, branch, session or pull request (in any state) already exists, and one whose branch is on the remote (`git ls-remote`; when `gh` or the remote cannot say, it warns and goes on), and a repository at its limit. `--critical` lets the task use the slots held in reserve (see Settings). `--base` stacks the task on another open task's branch. The first line of the brief that starts with `Expected size:` (any case) gives the task's size: the first of `small`, `medium`, `large` on it (a whole word, any case); with none, the task has no size. A size sets the task's time limit (see Settings) and the lead is told it in minutes (`Your time limit is 45 minutes.`). After the session has started the size is recorded in the branch's git config, `branch.<branch>.factorySize` (a failure warns and does not fail the command; `git branch -D` removes it with the task), and in the `TaskStarted` event.
- **`status`** prints one row per task worktree: slug, phase, declared state, branch, session, base, session state, elapsed time (for a task in motion `41m / 45m`, the elapsed time against its limit, in minutes with zero minutes dropped: `1h30m`, `2h`, `0m` under a minute; any other task shows the age alone), its size (`small`, `medium`, `large`, or `-`), `overtime` when the task is in phase `motion` and a session whose turn has not ended is past its limit (the one deadline: the task's start plus its limit, after an extension the `until` of the site manager's last decision; a task so extended shows `(+20m site-manager)` after `41m / 65m`, the minutes granted since the task started, and an ask made past the limit leaves the limit grown by more than 20 minutes: it counts from the decision), `nearing` when such a session is past `NEARING_PERCENT` (75) of its limit (a display flag that wakes nobody: a task not declared `working`, or past its limit, is not `nearing`), uncommitted changes, commits ahead and behind its base, last commit, pull request, `stale` when the last commit and the task's start are both older than 7 days, `paused <age>: waits <slugs>` and `prioritized <age>` for a paused or prioritized task, `kept: <reason>` for a task whose work is over (merged, settled, closed or a report) that `clean` keeps, the `keep_rule` text, including a session at work or a task stacked on it, and `held <age>: <criterion> <decision>` for a task the site manager is deliberately holding (below). Then the counts per phase against the ordinary limit (`in motion 3/4, reserve 1, cap 5`; `3/5` when there is no reserve), the leftover `agent-*` and outside worktrees, one line saying who acts on GitHub (`acting on GitHub as <bot login> (the factory's App)`, with `; installed on ALL repositories: narrow it at <installation url>` appended when the installation covers all of them; or `acting on GitHub with your gh login` with the reason: no App identity, the App stored but not installed, this repository not on GitHub under the App's owner, and, instead of that choice, `acting on GitHub: the stored App cannot be read: <reason>; the factory's gh calls fail until it is fixed (factory wizard)` when `app.json` is corrupt or malformed), and one `waiting on the human: <slug> <deliverable>` line per task in review. Pull request state is `unknown` without `gh`. Pull requests come from one `gh pr list --state all --limit 100` per repository (10 s at most; a branch the list lacks is `none`, except when the list came back full: then that branch is asked alone), kept in `~/.claude/factory/cache/prs-<key>.json` with the time of the last successful ask. `--cached` never contacts GitHub (no `gh`, no token), runs no `lsof` and asks no remote, and reads that cache (a closed task not kept by an earlier rule then has `kept` = ``closed, but open files and the remote were not checked; `factory status` (without --cached) checks them``); `--max-age SECONDS` (default 0: always ask) asks only when the cache is older or lacks a branch; `--cached` wins. Only `status` reads and writes `cache/prs-*.json`; every other command asks GitHub afresh (`unknown` when it cannot answer). The ask, the list and any per-branch fallbacks together, is bounded at 20 s. The cache also records the last attempt and its error, so with `--max-age` a failed attempt younger than that is not repeated (its error is reported again, no `gh` call); a full list whose missing branch cannot be asked alone counts as a failed attempt. When GitHub fails or times out the cached values stay and `status` prints `pull requests as of 2m ago (GitHub: <reason>)` (also printed for cached data); without a cache the rows are `unknown`. `status --json` has `prs`: `{"as_of": <epoch seconds of the last successful ask the rows use, null when none>, "error": <one line, or null; always null with --cached>}`. `status --json` also has `reserve` (the slots of the cap held back for critical work), `identity` (the bot login, or `null` when the factory does not act as the App here) and `repository_selection` (`all`, `selected` or `null`), and its rows also carry `size` (`small`, `medium`, `large` or `null`: the recorded one), `limit` (the task's limit in seconds from its start, always set, extensions included), `extensions` (a list of `{minutes, by, reason, decided, from, until}`, empty when none; `from` is null for an extension of the old rule), `nearing` (a boolean; `overtime` is against `limit`), `kept` (the `kept:` reason, computed once per row and read by the `merged-not-cleaned` fact; `null` when the task's work is not over or nothing keeps it; a sentence saying so when sessions cannot be listed or placed), `kept_elsewhere` (a boolean: the reason is somebody else's wait, a session at work or a task stacked on it), `held` (`{criterion, decision, since, reason}` of the newest non-cleared firing on the task's slug with criterion `ended-undeclared` or `merged-not-cleaned` and decision `suppressed` or `escalated`, `since` when it was decided; `null` when there is none; a held task is never `overtime` or `nearing`) and `waited` (seconds since the task's last declared record, `null` when undeclared) and, for a blocked task, `waits_on` (the recorded name, `human` when none was given; `null` for every other state), `stop_kind` and `stop_summary` (the `kind` and `summary` of the last `QUESTION`, `BLOCKED` or `OVERTIME` stop its lead sent after declaring it; `null` when there is none, and `stop_summary` is `null` for stops logged before summaries existed).
- **`clean`** removes finished tasks (session, worktree, branch) and says why it kept the rest. It never forces and keeps a task whenever anything is uncertain. A task goes only when its pull request is merged into the default branch with the local head equal to the merged head, or its state is `acknowledged` or `dismissed` with a recorded deliverable, a pull request that is not open and a head that is pushed, or it is a handed-over report (see Reports), or its state is `closed` and its work is held elsewhere (see Closed tasks); and in every case nothing is uncommitted, no task is stacked on it, no session in it is unfinished and no other worktree is nested in it. One exception to the session rule: when the task is declared `handed-over` or settled and its pull request is merged, an exited background session (no `status`, no `pid`) does not hold it whatever its `state` says, and `clean` removes it through that session (`claude rm <session id>`); an interactive session, a background session with a process, and a task declared `working` or `blocked` still hold it. It keeps a task on a detached HEAD, and one whose worktree is locked with no session (it prints the `git worktree unlock` to run). If sessions cannot be listed, or an unfinished session has no `cwd`, it removes nothing (exit 2). A dismissed branch that is not merged makes `git branch -d` refuse: reported, exit 1. Git-ignored files in a removed worktree go with it.
- **`state`** is run by a lead inside its worktree. `handed-over` takes the deliverable: a link (`scheme://...`), or a file that exists and is outside the worktree.
- **`overrun`** is run by a lead inside its worktree, once, past its limit or when the task is not converging (text: what is done, what is left, why it is slow, what it would do with more time; one argument, not empty, cut at 1000 characters). It logs an `overrun` firing for the task and prints that the site manager decides within a tick and that the answer arrives as `SITE MANAGER: <slug>`. It declares no state and messages nobody. A task with an undecided ask refuses a second one (exit 1). See Site manager, Overruns and stopped runs.
- **`pauses`** lists each pause of the churning rule (see Merging, Churning tasks): slug, start, minutes or `still paused`, the tasks it waited for, the queue's send-backs before and after it and how its priority ended; then totals. It reads the `TaskPaused`, `TaskPrioritized` and `TaskPrioritizedEnd` events and the lander's send-back rows, nothing else.
- **`ack`** is run by the dispatcher on the human's word, for a task that was handed over and whose pull request is `none` or `closed` (a link deliverable, a pull request closed unmerged). It refuses (exit 2, nothing written) when the pull request is `open` (its approval and merge end the task), `merged` (`clean` ends it) or `unknown` (its state cannot be read). A report with a file deliverable needs no `ack` (see Reports).
- **`close`** is run by the dispatcher, from anywhere in the repository, for a task the human tells it to drop. It prints `closed <slug>: <reason>`, then `removed <slug>` or `kept <slug>: <why>` (exit 0: a kept task is not a failure). It refuses (exit 1, nothing written) a live task (see Closed tasks below), a slug that is not a task worktree, a task declared `handed-over`, `acknowledged` or `dismissed` (`ack` is its path when the pull request is `none` or `closed`; it refuses an `open` or `merged` one, which the approval and merge, or `clean`, end), an empty reason and a `--superseded-by` naming the task itself. The site manager's `closed` decision goes through the same function.
- **`wizard`** creates the factory's GitHub App, gets it installed and verifies it; rerun, it verifies or repairs. See Identity.
- **`env`** prints `export` lines that make `git` and `gh` act as the App, or nothing (exit 0) when no installed identity is stored; on a terminal the token is shown as `***`. See Identity.
- **`retro`** takes the task from the working directory and reads the JSON from `<file>` when one is given (exit 2 if it cannot be read), else from stdin. On success it prints `retro: stored for <slug>`; a failure prints nothing on stdout.
- **`land`** lands a handed-over task whose base moved or merged, or whose pull request conflicts, without waking its lead (see Landing without the lead). It is for use by hand: merging no longer goes through it, and a waiting branch is updated only by the lander in its turn.
- **`tech-lead`** runs a tech lead on a pull request that came back from the merge queue, in the foreground (see Tech lead). The lander's loop starts it detached.
- **`scratch <commit>`** is run in a worktree (or any repository) by an agent that needs another commit's files, such as a reviewer running tests on a base SHA. It makes a new directory with `tempfile.mkdtemp` (prefix `scratch-`) under `$CLAUDE_JOB_DIR/tmp` when that variable is set (`tmp` is created if missing), else under the system temporary directory, fills it with the tree of `<commit>` as `git archive` gives it (any commit-ish git resolves here), and prints its absolute path alone on stdout. The copy has no `.git`: it is not a repository or a worktree, and the command never runs `git worktree` or touches the index, the working tree or a ref. It needs no store, task or GitHub. An unresolvable commit, or a directory outside a repository, exits 1 with git's message on stderr, nothing on stdout, and no directory left behind. It deletes nothing else: the job's scratch folder is removed with the job.
- **`merge`** and **`lander`** take a pull request from approved to the default branch (see Merging).

## Declared state, phases and the cap
| Declared state | By | Meaning |
|---|---|---|
| `working` | `new`; the lead when it resumes | being built |
| `blocked` | the lead, before `QUESTION:` or `BLOCKED:` (or, on a `SITE MANAGER` line saying the ask was passed to the human, `factory state blocked human`); the site manager's script, for a task it pauses on the human (`paused`, role `site-manager`: `factory build` refuses until the lead declares `working`; a pause on the human is never released by the script); the optional argument says whom it waits on: `human` (the default), `dispatcher` or the slug of another open task of the repository (anything else, or its own slug, is refused and writes nothing); recorded as `waits_on` only when given | waiting on the human, the dispatcher or that task; only a task waiting on the human is in the dashboard's band |
| `handed-over` | the lead, before `DONE:` and after any later turn | the deliverable is with the human |
| `acknowledged`, `dismissed` | the dispatcher (`ack`) | the human accepted or dropped it |
| `closed` | `close`; the site manager's `closed` decision (role `site-manager`) | declared dead without a hand-over; carries `reason` and, optionally, `superseded_by`. `state` and `ack` refuse it; a lead that comes back declares `working` and the newest record wins |

A session is unfinished if it is interactive, or a background session whose turn has not ended. In `claude agents --json --all` a turn has ended when `status` is `idle` (a session stays `busy` while a background command it started still runs), or when the entry has no `status` and no `pid` and its `state` is `done` or `stopped` (the process exited, or `claude stop`). The `state` of a live session (`done`, `blocked`, `working`) is its own summary of its last turn and is not read: a lead woken by a message after its hand-over often ends `idle` with `working`. Anything else, such as `waiting`, an unknown status or an exited session with another `state`, is unfinished, except that for a task whose work is over (declared `handed-over` or settled, pull request merged) an exited session is not read at all: its `state` is a model's summary (a handed-over lead may end calling itself `blocked`), and the declared state and the pull request decide.

| Phase | When | Holds a slot |
|---|---|---|
| `motion` | a session is unfinished in it, or sessions cannot be listed or placed; or declared `working`; or undeclared with no open or merged pull request (never for a task declared `handed-over` or settled whose pull request is merged: that is `merged` whatever its sessions are) | yes |
| `blocked` | declared `blocked`, no session unfinished | yes |
| `review` | no session unfinished; declared `handed-over` and not merged, or undeclared with an open pull request | no |
| `merged` | pull request merged and no session unfinished; or the task is declared `handed-over` or settled and its pull request is merged, whatever its sessions are | no |
| `settled` | no session unfinished, `acknowledged`, `dismissed` or `closed`, not merged | no |

The cap (`limits.worktree_cap`) counts slots per repository. Only `new` checks it, so a lead that resumes is never stopped. Nothing bounds the number in review. `limits.reserve_percent` of the cap (rounded up, never the last slot: a cap of 1 has no reserve) is held back: `new` refuses an ordinary task once the other slots are held, and only `new --critical` may take the reserve, for a red default branch, a broken factory, or when the human says so.

## Settings
`~/.claude/factory/settings.toml` (`$FACTORY_HOME/settings.toml`), one commented file; every key is optional and a missing key has its default. The kaizen review is on by default once this is installed (`kaizen.review_hours = 1`): it costs about 2 USD a run at the measured rate, with a ceiling of 3 USD, and is turned off with `factory settings set kaizen.review_hours 0`. `factory wizard` writes it with every key, its default and a comment when it is missing and, from a clone, sets `paths.monitor`; edit a line and save, nothing is reinstalled. A syntax error, or a value of the wrong type or range, is an error naming the file, the line and the key (`settings.toml line 12: limits.worktree_cap must be an integer of at least 1`). A table or key it does not know is reported once on standard error and ignored.

`factory settings set <table.key> <value>` changes one line in place: every other byte of the file (comments, order, blank lines, a trailing comment on the line) is kept, a key missing from its table is added at the end of the table, a missing table or file is created (the file as the wizard writes it). It checks the value, then checks that the new file differs from the old only in that key, and replaces the file atomically through a symlink; otherwise it fails with the file untouched ("edit the file by hand", for a multi-line value). It prints `set <key> = <value>` or `unchanged`. The wizard's cost step, `isshoni host` and the dashboard's `c` key use it; nothing else edits it in place (the wizard writes the shipped text when the file is missing, and the migration writes it once).

| Key | Default | |
|---|---|---|
| `limits.worktree_cap` | 5 | tasks holding a slot, per repository; `isshoni-tui` can edit it |
| `limits.reserve_percent` | 10 | whole percent of the cap, rounded up, held for `new --critical`; `0` turns it off |
| `limits.task_time_limit_hours` | 2 | the ceiling of every task's time limit and the limit of a task without a size; a size sets a limit of 45 (`small`), 90 (`medium`) or 120 (`large`) minutes, never above this. After the limit `status` shows `overtime` while the lead's turn has not ended; the lead stops and reports. The task's start is the `TaskStarted` event `factory new` writes, so elapsed time, limit and extension total survive a lead's session ending, being retired or resumed (without that event, the session's start) |
| `limits.extension_minutes` | 60 | a positive number: the most the site manager may add to one task's limit in total (the sum of its `extended` decisions since the task started); a decision that would exceed it is not applied and the ask goes to the human |
| `sessions.lead_permission_mode` | `auto` | `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan`; also the mode of the lander of `factory land` and of the tech lead |
| `sessions.lean_start` | `true` | `true` or `false`: whether the lead, the site manager run, the lander run, the tech lead run and the kaizen review run start with only what they use (see Lean start); `false` restores the plain command line for all five, but for the attribution setting (the review session keeps `--strict-mcp-config` either way) |
| `sessions.dispatchers` | unset | a list of session names; `isshoni host add` sets it and the served dashboard's `d` key reads it; the factory script reads nothing from it |
| `kaizen.review_hours` | 1 | the kaizen review's period in hours; `0` turns it off (see Kaizen review) |
| `kaizen.issues_repo` | empty | `owner/name`: where the review posts its proposals; empty means nothing is fetched or posted |
| `ops.tools` | unset | a list of MCP tool names the ops explorer may call (see Reading production) |
| `merging.lgtm_from_author` | `true` | `true` or `false`: whether an `lgtm` by the pull request's author counts; set `false` once the factory has its own account (see Merging) |
| `paths.monitor` | unset | the path of the monitor's `isshoni` command; the cost facts and the digest need it |

The model of every role is a line of `[models]`: an alias (`fable`, `opus`, `sonnet`, `haiku`) or a full id (`claude-...`). Whether an id exists is not checked (`claude` does not say until it makes a request): a value that is neither an alias nor shaped `claude-` followed by letters, digits, dots and hyphens, either with an optional bracketed suffix such as `[1m]`, is an error at the next command that reads it.

| Key | Default | Takes effect |
|---|---|---|
| `models.dispatcher` | `fable` | advice only: the human starts the dispatcher, and a session the factory did not launch uses the agent files' pins |
| `models.lead` | `fable` | at the next `factory new` (`new --lead-model <m>` overrides it for that task; the model used is recorded in `TaskStarted`) |
| `models.explorer`, `models.coder`, `models.reviewer` | `haiku`, `sonnet`, `opus` | the explorer for the next lead started, the coder and reviewer at the next build run (the lead and the build run are each launched with `--agents`, one `factory:<role>` entry per file in `factory/agents/`: its description, body, tools and skills, and this model), which shadows the plugin's agent of the same name; a frontmatter key other than `name`, `description`, `model`, `tools` and `skills`, or an agent file without a `models` key, is an error |
| `models.ops_explorer` | `haiku` | for the next lead, build run or tech lead run started (the agent file `ops-explorer.md`; a file's key is its stem with `_` for `-`) |
| `models.ops_watch` | `sonnet` | the next look of an ops watch: the judge, which reads only through the ops explorer (see Watching production) |
| `models.lander` | `sonnet` | the build run's lander as above, and the headless run of `factory land` at its next run (merging itself is a script and uses no model) |
| `models.kaizen_review` | `fable` | the next kaizen review run |
| `models.site_manager` | `opus` | the next `watch` tick or digest. A settings file that names `sonnet` keeps Sonnet; `factory settings set models.site_manager opus` moves it |
| `models.courier` | `haiku` | the next tick that carries a comment |
| `models.tech_lead` | `opus` | the tech lead's next run, and every task's build run (see Tech lead, Team mode); it is not one of the lead's subagents: no `--agents` entry, and not in `TaskStarted.models` |

The `model:` line in each agent file stays as the fallback for a session the factory did not launch; a test keeps it equal to the default above. `wrong-model` compares what a subagent ran on with the models the task was started with (`TaskStarted.models`; a task started before that was recorded is compared with the current file), and the lead with `lead_model`. The monitor (`isshoni`'s warnings) has no task record and compares with the current file.

An older install kept `settings.json`. The first factory command that finds `settings.toml` missing and `settings.json` present checks the JSON as before and writes the TOML with its values in place (`lead_model` becomes `models.lead`, `tech_lead_model` becomes `models.tech_lead`, `monitor` becomes `paths.monitor`, `dispatchers` becomes `sessions.dispatchers`), reading it back first so that a file that would not round-trip is an error and nothing is written. It says so on standard error, naming any key it did not carry. `settings.json` is left where it is, untouched: a machine runs several versions at once (the installed plugin, a checkout, a lead's worktree) and an older one reads only the JSON. Nothing ever writes or deletes it. From then on the TOML is the only file this version reads; while the JSON also exists, a key whose value differs between the two is named in one line on standard error per command (`settings.json (read only by older versions) differs from settings.toml in worktree_cap; ...`; none from a hook), so a setting changed in one file is not seen by the other version until you change both. Delete `settings.json` once every checkout and the installed plugin are on this version. Invalid JSON is an error when it is migrated and a reported (not fatal) line after. The dashboard reads a `settings.json` beside a missing `settings.toml` until then.

### Lean start
A bare `claude --bg` lead starts with about 53k tokens of context (measured 2026-11-14, claude 2.1.325, haiku, trivial prompt). A lean start brings that to about 26k, the site manager run from about 36k to 8k and the lander run from about 12k to 10k. The lead, the site manager run and the lander run get `--strict-mcp-config` and `--settings '{"disableBundledSkills": true, "enabledPlugins": {<id>: false, ...}}'`, where the ids are every plugin `claude plugin list --json` reports except the factory's (a name before `@` of `factory`: turning that off removes the factory's agents). If the list cannot be read, one line on standard error says so, the `enabledPlugins` key is left out and the launch goes on.

What a lead then lacks: no MCP server at all (the user's, the claude.ai connectors, the repository's `.mcp.json`); no installed plugin other than the factory, so none of their skills, agents, hooks or LSP; no bundled skills; built-in tools limited to `--tools=Bash,Read,Edit,Write,Grep,Glob,Agent,Skill,ToolSearch,SendMessage,WebFetch,WebSearch,TaskStop,Monitor`, for the lead's subagents too (so no LSP, NotebookEdit, Cron, Artifact, Workflow or AskUserQuestion). Kept: the factory plugin, the user's settings and permissions, `~/.claude/skills`, the repository's `CLAUDE.md`, the login. The site manager run also gets `--disable-slash-commands` and `--tools=SendMessage,ToolSearch` (its structured output still works, checked). The lander run gets the first two flags only; its agent file already fixes its tools. The tool list is the single-word `--tools=` form because `--tools` takes every following word and would swallow the prompt. A task that needs an MCP server or another plugin needs `sessions.lean_start` set to `false`. A limit: the tool list has no `ExitPlanMode`, so `lead_permission_mode = "plan"` together with `lean_start = true` (in `[sessions]`) is not supported (whether the lead could leave plan mode is unchecked).

Attribution. Every session the factory starts (the lead, the build and tech lead runs, the site manager, the lander, the ops watch, the courier, the kaizen review, and the dispatcher `docker/start` revives and `isshoni host add` starts), lean or not, gets `--settings '{"attribution": {"commit": "", "pr": "", "sessionUrl": false}}'` (`ATTRIBUTION_OFF`, built by `session_flags`; lean start adds its keys to the same JSON). The harness's own trailer in commits and line in pull request bodies are then off, whatever the user's or the repository's settings say (only a managed policy overrides the command line); the bot identity and the git author are the record. A limit: a dispatcher a human starts by hand with `/factory:dispatch` is the human's own session and keeps their settings. `python3 factory/tests/live_attribution.py` shows a real headless build run's commit and pull request body without either line.

## Reading production: the ops explorer
`factory:ops-explorer` answers a question about a running system (logs, metrics, traces) from MCP servers and returns evidence file paths with short excerpts. The lead, the tech lead of a merge run and the tech lead of a build run can dispatch it, as can any session started with `--agents` from `agent_definitions`. It holds the tools `Read`, `Grep`, `Glob` and the servers below: no `Bash`, `Write`, `Edit`, `Agent` or `SendMessage`. The sessions that dispatch it keep `--strict-mcp-config` and hold no MCP tool.

`ops.tools` in `[ops]` lists the MCP tools it may call, read-only ones only, each `mcp__<server>__<tool>` or `mcp__<server>__*` (a server's every tool). Unset by default: no MCP tools. Anything else, a `*` anywhere but as the whole tool part included, is an error at the next command that reads the settings. A server whose own name contains `__` cannot be listed.
```toml
[ops]
tools = ["mcp__metrics__query"]
```
Where the servers come from: for each server name in the list, the first of local scope (`~/.claude.json`, `projects.<main checkout>.mcpServers`), project scope (`.mcp.json` of the main checkout) and user scope (`~/.claude.json`, `mcpServers`) that has it (`claude mcp add`; for an OAuth server, log in once interactively, and the stored login is reused). The definition is passed on in the `--agents` entry of the ops explorer as written, so it appears on the session's command line: keep secrets out of it (OAuth, or environment references). A server found nowhere is skipped with one line on standard error (`factory: ops.tools names server <name>, which is not configured here (claude mcp add)`). A tool list on the agent cannot hold back the tools of an inline server, so the gate below is what keeps it read-only.

`factory ops-hook`, registered in the plugin's `hooks.json` as `PreToolUse` and `PostToolUse` on `mcp__.*`, does nothing for any other agent, except that a gate that cannot start or does not answer within its deadline blocks the call whoever makes it.
- Before a call, an MCP tool that is on `ops.tools` is allowed; any other is denied with `<tool> is not on ops.tools: the ops explorer is read-only`. A failure in the gate (unreadable settings, an unparsable payload) exits 2, which blocks the call. A hook that outlives the harness's timeout does not stop the call (observed 2026-11-15, Claude Code 2.1.325: the call ran), so the gate answers first: it gives itself 5 s (`OPS_HOOK_DEADLINE`) and then exits 2 with `factory: ops-hook ran out of time: the call is blocked, or its result was not saved: do not use it`, and the harness waits 60 s. The `PreToolUse` command ends `|| exit 2`, so a gate that cannot start blocks too (a command that is not found exits 127, which the harness does not treat as a block: observed, without `|| exit 2` the call ran). What remains: if the gate has not armed its deadline within 55 s of its start (interpreter start, compile, imports: about 0.1 s measured), the harness's 60 s run out first and the call runs (inferred from the timeout observation above, not probed).
- After a call, the hook writes `$FACTORY_HOME/deliverables/<slug>/evidence/<UTC timestamp>-<tool>-<last 8 characters of the tool use id>.json` (`session-<session id>` instead of the slug outside a task), the folder `0700` and the file `0600`: `{"ts", "server", "tool", "input" (the query and its time range), "response" (as received), "agent_id", "session_id"}`. The model is told the path (`Evidence saved: <path>`), or that the evidence was not saved and the result is not to be used. The files are never committed. A call that failed leaves none.

Limits. MCP only: a source reachable only by a command line is out of reach. The list is the human's judgment of what is read-only; the factory does not inspect a tool. With `sessions.lean_start = false` the dispatching session keeps whatever servers the user has. How to read production (server, dataset, time field, query language) belongs in the repository's `CLAUDE.md`, `AGENTS.md` or `CLAUDE.local.md` (uncommitted, for a public repository); the ops explorer says so when it finds nothing there. `factory/tests/live_ops_explorer.py` proves the boundary against real servers (by hand, a scratch `FACTORY_HOME`).

## Watching production: the ops watch
A human-started, periodic look at a running system. It has no worktree and no write tool, and never messages a lead, opens a task or comments; only the script informs.
```
factory ops start <name> "<goal>" --every <duration> --until <duration|UTC time> --budget <usd>
factory ops list [--json]
factory ops stop <name>
```
- **`start`**: `<name>` is `[a-z0-9][a-z0-9-]*` and new. A duration is `90s`, `10m`, `6h` or `2d`; `--until` is also a UTC time (`2026-11-15T15:00:00Z`); all three options are required and positive. `--until` is the hard end; the goal may name an earlier one ("done once X"). It refuses when `CLAUDECODE` is set (`only the human starts a watch: run this in your own terminal`): that is a guard against a role doing it by habit, not a security boundary. It refuses when `ops.tools` resolves no server for the repository. It records the repository, makes the first look due at once, installs the watch job when the repository has none (an installed one is never replaced) and prints the notes path. No role starts a watch: when work needs watching after a merge, the dispatcher gives the human the command.
- **`stop`** works from anywhere, a session included.
- **`list`** prints one row per watch, newest first: name, state (and verdict), the last look (age, outcome, what it saw), the next look, spent of the budget (`+N unpriced` when a look reported no cost), the notes path. `--json` prints `{"watches": [...]}` with `name`, `repo`, `goal`, `state`, `verdict`, `started`, `until`, `every_seconds`, `ticks`, `missed`, `last_look` (`{ts, outcome, saw, late_seconds}` or null), `next_look`, `spent_usd`, `unpriced_ticks`, `budget_usd` and `notes`.
- **States**: `watching`, `alarmed` (looks go on), `ended` (with a verdict: `met`, `not-met` or `inconclusive`), `stopped`, `out-of-budget`.

**A look.** The two-minute `factory watch` tick runs the looks that are due, first, under a lock of its own (`ops`): the watch lock is held for the lander's whole loop, which can last until the next health run, and the loop gives the looks a turn on each of its passes. A look is one fresh headless session (`models.ops_watch`, `--permission-mode dontAsk`, `--strict-mcp-config`, `--tools=Agent` allowed only for `factory:ops-explorer`, `--setting-sources ""`, at most 15 turns (`OPS_TICK_TURNS`), at most `min($0.50, what is left of the budget)` (`OPS_TICK_BUDGET`), 300 seconds (`OPS_TICK_TIMEOUT`)) that reads only by dispatching the ops explorer and answers `{outcome: fine|alarm|done|could-not-look, saw, verdict, checks}`. The first look turns the goal into four checks (`read`, `fine`, `alarm`, `done`); the script stores them once and later looks apply them as written. Its prompt holds the goal, the times, whether this is the final look, the checks and the last 20 entries of the notes (so a look's context is bounded). The script, not the model, decides the rest: a look that has no evidence file (the explorer's hook writes one per successful call), no usable output or no checks is `could-not-look` whatever the model said; `alarm` is sticky (the looks go on) and informs once; `done`, or the first look at or after `--until`, ends the watch (`inconclusive` when the end time came without a verdict backed by evidence); a spent budget ends it `out-of-budget`. A cost the session did not report is kept as unpriced, not as 0; the cap it ran under counts against the budget (`reserved_usd` in `watch.json`, the sum of those caps, not in `ops list --json`), so a watch whose looks never report a cost still ends `out-of-budget`. A due look runs before the lander's pass in its loop, so a merge can wait for it (up to the look's timeout plus the dispatcher line).

**Files**, in `$FACTORY_HOME` (folders `0700`, files `0600`): `ops/<name>/watch.json` (the state, written only by the script), `ops/<name>/notes.md` (the goal, start, end, every and budget; then the `## Checks`; then one line per look `- <time> <outcome>: <saw> [evidence: <n> file(s) in <folder>]`, and lines for missed looks and state changes), and `ops-YYYY-MM.jsonl` (one record per look: `ts`, `repo`, `watch`, `tick`, `outcome`, `saw`, `cost_usd` (null when unpriced), `seconds`, `turns`, `session`, `evidence`, `late_seconds`; one per gap: `outcome: "missed"`, `count`, `from`, `to`). The evidence stays where the ops explorer's hook puts it, `deliverables/session-<session id>/evidence/`.

**Late and missed looks.** A look runs when the tick comes; launchd does not start a tick while the last one runs, so a look can be late while the lander drains, and a machine that sleeps or is off runs none. A tick that finds a look `n` intervals late (an interval is the longer of `--every` and the two-minute tick) runs one look, records `n` looks missed (note, record, `missed` in the list) and does not catch up. `--every` below two minutes is not faster than the tick. An active watch keeps the repository's watch job when no dispatcher is left.

**Informing** (the script, one line, `OPS WATCH <name>: <event> - <saw or reason> (notes: <path>)`, `saw` cut to 200 characters; a notification service failing leaves a `notify:` line in `watch.log`):

| Event | List, notes, record | Desktop notification | Dispatcher (one `courier` message, only with a live dispatcher session; a failure is printed, not retried) |
|---|---|---|---|
| alarm (the first of a run of them) | yes | yes | yes |
| ended, with the verdict | yes | yes | yes |
| out of budget | yes | yes | yes |
| could not look | yes | the first of a run | no |
| missed looks | yes | no | no |
| stopped by the human | yes | no | no |

Limits carried over from the ops explorer: MCP only; a failed call leaves no evidence, so a look that could read nothing shows as `could-not-look`, and so does one whose gate ran out of time, since that blocks the call (see Reading production). `factory/tests/live_ops_watch.py` runs a watch end to end against a stdio server of its own (by hand, a scratch `FACTORY_HOME`, a fake scheduler).

## FACTORY_HOME
`FACTORY_HOME` moves everything the factory keeps under `~/.claude/factory`: the settings file, the logs and the outbox, the task state, `watch.log` and the `identity/` directory (App, key, cached tokens). Unset or empty it is `~/.claude/factory`; `~` is expanded; a relative value exits 2 with one line (the `hook` command exits 0 and records nothing; `ops-hook` exits 0 for other agents and exits 2, which refuses the call, for the ops explorer), because the hook and the schedule run in other directories. Messages that name the settings file print the real path. It does not move `~/.claude/projects` (Claude Code's transcripts), the scheduler's own files (`~/Library/LaunchAgents`, systemd units, crontab) or the spec directory the lead's rules name. The dashboard's settings editor always opens `~/.claude/factory/settings.toml` (`FactorySettingsPath` in `internal/data/factory.go`), and `~/.claude/factory/deliverables/` named in the lead's rules is not moved either (the ops explorer's evidence files do follow `FACTORY_HOME`). The hook and `factory env` run in the session's environment and read the same variable.

`factory schedule install` with `FACTORY_HOME` set writes it into the job's environment beside `PATH` (launchd `EnvironmentVariables`, a systemd `Environment=` line, a variable before the command in cron) and hashes the home into the job's label, so a job installed under another home is a second job and never replaces the real one; it also leaves a legacy job without a hash alone. With the variable unset the label and the job are unchanged. It is meant for tests and exercises: a scratch home that cannot touch the real outbox, tasks or App.

## Messages
Leads and the dispatcher talk through Claude Code's `SendMessage`, by session name; a lead asks `factory dispatcher` for the dispatcher's current name before each message. A lead's first line starts with `QUESTION:`, `BLOCKED:`, `SPLIT:` or `DONE:` and its slug; a lead over its limit does not message the dispatcher but runs `factory overrun` (see Site manager). The dispatcher also receives `SITE MANAGER: <slug>` lines (information, one line, no action), `PAUSED:` lines (a task paused for the human) and `ESCALATION:` lines from the site manager's script. The human can always `claude attach <slug>`.

### A lead the harness retired
Claude Code retires a background session that has sat at its prompt for 60 minutes (its daemon's sweep; `~/.claude/daemon.log` has `bg retire <id>: idle-prompt, idle 60m`): the process ends, the conversation is kept, no `SessionEnd` hook fires. `claude agents --json --all` then lists it with no `pid` and no `status` (`state` is the last turn's summary, `cwd` is the main checkout), and `SendMessage` by name answers "No agent named '<slug>' is reachable". The idle count is wall-clock, so a sleep counts: after a wake expect every lead that was waiting to be retired at once. No tick runs during a sleep and the first after it delivers what was recorded meanwhile (staged, not yet proven by a real sleep).

Every line the script sends a lead (`forward`) is first recorded in the lead outbox, `outbox-YYYY-MM.jsonl` (`id`, `ts`, `repo`, `slug`, `line`; later records of the same `id` add `tries` with `why` (the reason of the failed try) or `end`: `delivered` or `dispatcher`), then delivered by `reach_lead`. A live lead (the listing row has a `pid`) gets one courier send per line. A retired one gets `claude --bg --resume <sessionId> <the lines joined by newlines>`, run in its worktree with no other flag: the session wakes with the options it was saved with (rules, tools, agents, permission mode), and any flag makes the harness start a copy instead. The resume counts when it exits 0 and prints `backgrounded · <the session's own id>`; a copy is stopped and counts as failed. The pending rows of a slug are always delivered together, oldest first, so a lead brought back gets everything it missed.
- Delivered: `forward` returns `lead`.
- A live lead the courier could not reach, or no session named the slug: the dispatcher gets `<HEAD>: <slug> (<why>): <line>` and the row ends `dispatcher`. `<why>` is `not delivered to its lead: <the courier's reply or error, first line>` or `its lead is gone: no session named <slug>`.
- A retired lead that could not be resumed (`its lead is gone: resume failed: <first line of the output, or timed out, or started a copy>`): the row stays pending, `forward` returns `queued`, and nobody is told yet. Each tick, `drain_outbox` (at the start of `watch_tick`, so on every tick, the lander loop's included, and on ticks where the site manager is not consulted; a failure in it is printed and the tick goes on) tries again. After the third failed try of a slug (`forward`'s is the first) its pending rows end `dispatcher` and the dispatcher gets one line, `<HEAD>: <slug> (<why>): <n> line(s) not delivered, oldest first: <line> | <line>`, else a desktop notice. `<HEAD>` is `LEAD GONE` when `why` starts `its lead is gone:` and `NOT DELIVERED` when it starts `not delivered to its lead:` (the lead has a live session: send it the lines by name); a live lead's line queued by `factory lead` waits in the outbox the same way, since `forward` hands a live lead's own line to the dispatcher on its first failure. Each failed try of a tick is printed, so it lands in `watch.log`: `outbox: <slug>: try <n> failed: <why>`; a notice to the dispatcher that fails prints `outbox: not delivered to the dispatcher <name>: <why>` (or why none was found) and falls to the desktop notice. `factory log outbox` prints the rows. The site manager's row of a task has `messages` for the rows queued since its declared state that are pending or ended `dispatcher`: `queued` (age), `tries`, `why`, `end`, never the line. The task keeps its declared state.
- A task declared `closed`: its lead is never reached or resumed, by `forward` or by the drain. Its pending rows end `dispatcher` at once and the dispatcher gets one line, `LEAD GONE: <slug> (its task is closed): <n> line(s) not delivered, oldest first: <line> | <line>`. `factory lead` refuses it: `<slug> is closed`.
- A retired lead with nothing pending is not resumed.

`factory lead <slug> '<message>'` is for the dispatcher, whose `SendMessage` by name fails on a retired lead. It records the message and prints `queued for <slug>: the next tick delivers it`; it refuses a slug that is not a task of the repository. It delivers nothing itself: the resume runs only in the factory's own unattended processes (the scheduled tick and the detached runs that call `forward`), because the permission classifier refuses it in a model's shell.

After a sleep, two lines show what happened: `grep 'bg retire' ~/.claude/daemon.log | tail` lists the retirements at wake, and `tail ~/.claude/factory/outbox-$(date -u +%Y-%m).jsonl` shows the rows and how each ended (a row with an `end` is done; none, pending).

### How the dispatcher is found
`/factory:dispatch` runs `factory dispatcher register`: it stores the calling session's id in `~/.claude/factory/dispatcher-<repository directory name>-<8 hex>.json` (`root`, `session`, `since`; one file per repository, written atomically) and installs the watch job. A second session that registers takes over (the last one wins): the command says which session it took over from and the skill sends that session one message. Every sender resolves the id to the session's name when it sends, so a rename changes nothing. The resolver, in this order:
1. The registered session, while it has a process (idle counts), in any directory.
2. Otherwise (no registration, or that session is gone), the old way: the one unfinished session named `dispatcher-<repository directory name>` working in the repository. `--dispatcher <name>` on `new`, `health`, `watch`, `digest`, `lander` and `tech-lead` replaces that name, and means nothing else.
3. The session found must have a name that no other running session carries. With none, or a shared one, there is no dispatcher and the reason says so (`dispatcher-missing`).

`factory dispatcher` prints the current name (exit 1 and the reason on stderr when there is none), from the main checkout or any task worktree; `--json` prints `{"root", "session", "name", "registered"}`, `registered` false meaning it was found by the old name. The ending of a dispatcher session does not delete the registration: a resumed session keeps its id. `/clear` gives the session a new id, so run `/factory:dispatch` again after it.

## Subagents and landing
A task's build works through four agents of the plugin (`factory/agents/`), each on the model its line in the settings names (by default Haiku, Sonnet, Opus and Sonnet): `explorer` finds and counts, `coder` implements and commits its round, `reviewer` reviews a fixed commit range, `lander` lands. The tech lead dispatches all four; the lead's tools refuse all but the explorer. The lead keeps the judgment: the spec, the design calls, what to make of a review, the quality assessment, the pull request's message and the sign-off.

The lander is given the task's base and the reviewed head; a build run adds a title and a one-line body only for a branch with no pull request. It fetches, merges its base into the branch when the base moved (`git merge --no-edit <remote>/<base>`, never a rebase), resolves a conflict only when it is mechanical (independent neighbouring additions; generated files, which it regenerates), regenerates goldens when told to, runs the full tests, pushes (`git push -u <remote> HEAD`, never forced), and opens or updates the draft pull request. The same run serves the first landing and every later "your base moved". Its tools are Bash, Read, Edit, Grep and Glob. It never edits code or tests to get through, never drops a side of a conflict, never merges a pull request, never rewrites history, and reports one of:

| result | means | then |
|---|---|---|
| `LANDED` | the reviewed commits are unchanged (the reviewed head is an ancestor of the pushed head), the base changed no file the task changes, or `factory overlap` said `verdict: safe`, no golden changed, tests pass | the tech lead goes on and reports it in the hand-over; the lead declares the hand-over |
| `LANDED, LOOK` | pushed, but a conflict was resolved mechanically, or `factory overlap` said `verdict: look`, or goldens were regenerated | nothing declared; the tech lead reports it under `### Ran`, and the lead reads the flagged hunks in its assessment |
| `STOPPED` (`dirty`, `conflict`, `golden`, `tests`, `denied`, `other`) | a decision is needed; nothing pushed (`denied` can follow a push). After `conflict` the merge is aborted; after `golden` or `tests` the worktree stays on the merge commit | the tech lead resolves what is mechanical, else stops with `question` or `stopped`, then dispatches the lander again |

**The overlap rule** (`Overlap` in `factory/lib/factory_core.py`, the one owner; `factory overlap <old base> <old head> <target>`, run in the task worktree, prints it and exits 0; it is what a build run's lander runs, while `factory land` does not apply it and still reports `LANDED, LOOK` on any overlap). Diffs are taken with `--no-renames`, so a rename is a delete and an add. A shared file is one both sides changed since the old base. It needs a look when it is not `M` on both sides (added, deleted or renamed on one side), when it is code, or when it is prose and the two sides' hunks are close. Prose is decided by path alone: a `.md`, `.rst` or `.txt` file (any case) whose name starts with `README` or that sits under a `docs` or `doc` directory; everything else is code, including `factory/agents/*.md`, `factory/roles/*.md`, `SKILL.md` and `CLAUDE.md`. For prose the distance is the smallest number of unchanged old-base lines between a base hunk and a task hunk (`git diff -U0`; a pure insertion after line `a` sits at `a+1`..`a`); `PROSE_GAP` (10) or more is safe. No hunks on either side (binary, mode change) needs a look. The output is `overlap: <file> (<reason>[, not looked at]); ...` or `overlap: none`, `verdict: safe|look`, and for each file that needs a look its reason and both sides' diffs (default context, 40 lines at most each). The lander puts the `overlap:` line in the Facts and a `look` verdict is `LANDED, LOOK` with those blocks as "Needs the lead". A resolved conflict, regenerated goldens or a look always give `LANDED, LOOK`. What the rule does not catch: documentation that states one fact in two places more than ten lines apart, one changed by each side; documentation whose text depends on code the base changed; anything in a file the rule calls prose that acts as a rule. There is no setting for the distance or the prose list.

The lander refuses to start unless the worktree is clean and its head is the reviewed head, and its push is plain, so it is refused when the remote branch holds a commit the head does not contain. When a stacked task's base has merged, the lead starts a build run, whose lander merges the default branch in and retargets the pull request.

`factory state` and `factory retro` take the task from the working directory. A lander runs neither `factory state` nor `factory retro`: the script that starts it declares `working`, and the lead files the retrospective and the hand-over.

## Landing without the lead
`factory land <slug>` or `factory land --all` (exactly one) does the mechanics of `factory/agents/lander.md` for a task that was handed over, so the dispatcher does not wake its lead for "your base moved". Run it from the main checkout or any worktree. It prints one report in the lander's format: `## Result` (`LANDED <url>`, `LANDED, LOOK <url>` or `STOPPED <reason>`), `## Facts`, `## Needs the lead` (`none` for `LANDED`); with `--all` each report follows a `# <slug>` line, and `nothing to land` says there was none. Exit 0 when every result is `LANDED`, 1 otherwise, 2 for a task with no worktree or one not declared `handed-over` (no report). `--all` takes only the handed-over tasks whose open pull request GitHub reports `CONFLICTING`, or whose recorded base (`branch.<b>.factoryBase`) has merged while the pull request's base is not yet the default branch: a pull request that is merely behind is left alone here: the lander brings it up to date when it merges it (the approval survives a clean merge of the default branch, see Merging), and the merge refuses a pull request that is `behind`. A named slug always lands.

It checks, in this order, before changing anything: (1) the task's sessions: they cannot be listed, one has no `cwd` and is unfinished, or one in the worktree is interactive or not finished is `STOPPED busy`, and nothing else is done or declared; (2) `git status --porcelain` not empty is `STOPPED dirty`; (3) after `git fetch`, a branch that is not `worktree-<slug>` or is the default branch, a pull request that is not open, or a local head that is not `<remote>/<branch>` and the pull request's head is `STOPPED other`. The reviewed head is taken to be the head that is at once local, pushed and on the open pull request.

The scripted path uses no model. The target is `<remote>/<recorded base>` while that base counts, else `<remote>/<default branch>` (a recorded base that merged: the pull request is retargeted). A target already in the head's history changes nothing but the pull request's base. Otherwise `git merge --no-edit <target>`, never a rebase: the reviewed commits are not rewritten; the test command in the worktree, `sh -c <command>` (`LAND_TEST_TIMEOUT`, 1800 s). The command is the one stated for the task (`branch.<b>.factoryTest`, see Using it on your own repository), else the one the last task handed over here was stated with (`factory.lastTest`, written by `factory state handed-over`: a starting point, not configuration), else `make test` when the first of `GNUmakefile`, `makefile`, `Makefile` has a `test:` rule (so a `test` directory does not count, and included files and rules naming several targets are not read). With none of these it is `STOPPED tests` with a message that tells the lead to state it (`factory commands test '<command>'`, or `none`), since nothing can say green. Stated `none` runs nothing, and the facts and the comment say `NO TESTS WERE RUN: none found in this repository`; the sessions again (this second check exists only on the scripted path: once a lander session has started, no further look is taken, and a lead woken meanwhile is excluded only by the plain push); `git push <remote> HEAD:<branch>`, never forced, a fast-forward by construction; the retarget; a pull request comment (`Merged <target> at <sha> into the branch by factory land, without the task's lead: <old> -> <new>. The reviewed commits are unchanged.`, then overlap, conflicts, regenerated files, tests and the result; never `lgtm`, and a `gh pr comment` is neither a review nor a comment whose whole body is `lgtm`, so it cannot count as an approval). It never runs a golden command or edits a file: a stale golden is a failing test.

When the merge conflicts it is aborted (`git merge --abort`) (the worktree is back at the old head) and a short run of the lander starts in the worktree (`LAND_TIMEOUT`, 1800 s): `claude -p --agent factory:lander --plugin-dir <plugin> --model <models.lander> --permission-mode <`sessions.lead_permission_mode`> [--strict-mcp-config, see Lean start] --settings <json> --allowedTools Read Edit Grep Glob "Bash(git *)" "Bash(make *)" "Bash(gh pr view *)" "Bash(gh pr edit *)" "Bash(factory overlap *)" --disallowedTools <the deny list> --output-format json <brief>`. The permission is the setting `sessions.lead_permission_mode` (default `auto`), the same as a lead's: the lander runs the repository's tests, whatever they need, with nobody to answer a prompt, so the allow list only pre-approves and `auto`'s classifier decides what is not listed. The deny list (`ROLE_DENIED`, shared with the tech lead) is `gh pr merge*`, `gh pr review*`, `gh pr comment*`, `gh pr ready*`, `gh api*`, `gh repo*`, `PUSH_DENIED` (the push forms in "What every started session is refused", Team mode), `git rebase*`, `git commit --amend*` and `git worktree*`. `Bash(git *)` is not narrowed: that the lander pushes only the task's branch, and only plainly, rests on its rules, on the deny list's guard against the obvious forms (`git -c k=v push` and the other spellings in that bullet are not matched by it), on the script settling the outcome from the task branch on the remote, and on the default branch's protection. A denial is `STOPPED denied`. If `sessions.lead_permission_mode` is a mode that prompts (`manual`), a headless run cannot answer and the command is denied. Checked on this machine with `python3 factory/tests/live_land.py --model` (a few cents): in a repository with no Makefile and `./check.sh` as the stated test command, the headless lander resolved a mechanical conflict, ran `./check.sh` and ended `LANDED, LOOK`, no `gh pr merge|review|comment` reached `gh`, and a run told to try `gh pr merge 1` and `git push --force origin HEAD` had both refused (`permission_denials` names them). The tool lists are passed before `--output-format` because `--allowedTools` and `--disallowedTools` take every following word. The brief gives the slug, the base and its remote, the old head as the reviewed head, whether the base merged, no title or body, the files the branch changes as the goldens it may regenerate, a line with the test and golden commands (`The test command is <command | none: ... | not stated: find how this repository runs its tests and run that>. The golden command is <command | none>.`), and that it edits files with the Edit tool, that `gh` other than `pr view` and `pr edit` is not its to run, and that merging, reviewing, commenting, forced pushes, rebases, amends and `git worktree` are denied. The script, not the model, settles the outcome from the remote: a branch head that moved is `LANDED, LOOK` (a conflict was resolved) whatever the model said, with the comment, and the report's `## Needs the lead` ends with ``the conflict resolution: `git show --remerge-diff <new head>` ``; one that did not is `STOPPED <the lander's reason>`, or `other` when the reply cannot be read, the run failed or timed out, or the lander said `LANDED` without pushing. The printed report is the lander's, with the settled result and without its `## Factory feedback` section. What the form was found to do (claude 2.1.325; `--output-format stream-json --verbose` shows it): `--agent factory:lander` with `--plugin-dir` applies the agent's prompt, its model (the configured `models.lander`, Sonnet by default; the agent file's Sonnet without `--model`; `--model` wins when it differs, checked with `--model haiku`: the session ran on Haiku) and its tool list (the init message names `Bash`, `Read` and `Edit`; no `Write`); hooks of the run carry the payload's `agent_type`, so `tags()` records `role: "lander"` with no change to it; an `Edit` is refused under `~/.claude/` paths as a sensitive file (a scratch repository there cannot be edited), not under a repository's `.claude/worktrees/`; `ANTHROPIC_LOG=debug` makes `claude` log on standard output, so `run` leaves it out of the run's environment.

| Result | When | State after |
|---|---|---|
| `LANDED` | the base did not move, or moved with an empty overlap; tests pass; pushed; the pull request is open against the target | nothing declared: `handed-over` stays |
| `LANDED, LOOK` | pushed, but the base changed a file the task changes, or the lander resolved a conflict | `working` (`role: lander`) |
| `STOPPED busy` | see (1) above | nothing declared |
| `STOPPED busy` | a lead that turned busy at the second check: the worktree is on the merge commit, unpushed | `working` |
| `STOPPED dirty`, `other`, `tests`, `denied`; `conflict`, `golden` (from the lander) | as above; the last 40 lines of a failing or timed-out test command (the worktree stays on the merge commit, unpushed); a failed fetch, abort, push (a remote branch that moved meanwhile is refused as a non-fast-forward) or `gh` step; the hunks, golden diff or denied step the lander reports | `working` |

A branch that holds a merge commit (an earlier landing) lands like any other. A merge that fails without a `CONFLICT` line (a hook, say) is aborted and is `STOPPED other` with git's output, with no model run. A push GitHub refuses with ``without `workflows` permission`` is `STOPPED denied`, nothing pushed, and "Needs the lead" is the one command for the human (see the `.github/workflows/` paragraph under Identity). `working` is declared before the push of a `LANDED, LOOK`, before the lander session starts and at a busy second check, so a kill or crash in between cannot leave the task looking handed over. After a lander run that pushed nothing and did not stop with a readable `STOPPED` (it timed out, exited non-zero, or its reply could not be read) the report adds HEAD, whether anything is uncommitted and whether a merge is in progress (`MERGE_HEAD`) from git; a failing fetch after the run is `STOPPED other`. `run` kills only the direct child: a command the lander had in flight can outlive a timeout. `STOPPED other` can follow a push (the retarget or the comment failed; the comment is posted even when the retarget failed, and both errors are reported): the report then says `pushed`. One task takes up to about 30 minutes (the tests or one lander session, never both); `--all` takes the tasks one after another; so the dispatcher starts it in the background.

How the landing keeps history, and its one exception. The reviewed commits are never rewritten, so a proof replaces the range-diff: `git merge-base --is-ancestor <reviewed head> HEAD` (the reviewed head is in the pushed history), and `git show --remerge-diff <merge>` (git 2.36 or later) prints what the merge added by hand: nothing for a clean merge, exactly the conflict resolution otherwise. A mechanical rename is still proved on trees (the inverse mapping applied to the result gives an empty diff against the base). There is no squash, which would break stacks: `git log --first-parent` on the default branch reads one line per pull request; proof commits and their reverts stay. The one exception to the no-rebase rule is the script's, never a session's or a role's: for the members of an open GitHub stack of factory branches it rebases and force-pushes them (`gh stack rebase`, `gh stack push`, in a clone of its own, as the bot) when GitHub refuses the stack as behind or the stack is not linear, after every member's diff is shown unchanged (see GitHub stacks). Every session, role and pull request outside a stack keeps the rule. History is otherwise rewritten in one case only: a pushed commit holds something that must not stay published (a secret, personal data, a huge binary). The lead does not rewrite: it reports `BLOCKED:` naming the commit, and you rewrite and force-push, and rotate the secret.

A `working` task is not mergeable (`handover` stop) and holds a slot until its lead has looked and declared `handed-over` again. The dispatcher messages the lead on `LANDED, LOOK` and on every `STOPPED` other than a first-check `busy`, including the busy that left an unpushed merge commit, pasting the report; on a first-check `busy` it does nothing and runs `land` again when the lead's turn has ended. A lead that gets such a report declares `working`, starts a build run (`factory build --note`) and declares the hand-over again.

Who acts: with an App installed (see Identity), the script's `gh` calls (the pull request read, the retarget, the comment) get the App's token through `run`, as the merge step's do, and its `git fetch`, `git merge` and `git push` run with the exports of `factory env` (the App's token for git, its name and email as author and committer; a failed mint stops the land at its first fetch with `STOPPED other`, "no App token", before anything is fetched, merged or pushed). The lander session of a conflict gets the same exports from the `SessionStart` hook, which `claude -p --agent factory:lander` fires like any session in a task worktree (checked with a stand-in for `factory env`: `git config` in that session saw its exports, with no denial under the allowlist). So the push, the comment and the merge commit are the bot's; with no App they come from your login. A fresh approval is still the human's.

Limits. Busy is told from the session list at two moments: when it starts and after the tests; a lead woken after the second look is not excluded, and only the plain push keeps the remote safe: it is refused when the lead pushed meanwhile. Listing sessions failing counts as busy. The task's pull request must be open; the old head must equal the pushed one; `--all` makes no mergeability retry (`UNKNOWN` is not conflicting).

Metric: dispatcher messages to a lead after its first hand-over, per landed task. In the events log a dispatcher message is a `PostToolUse` event with `tool_name` `SendMessage`, `role` `other` and `to` the lead's name (the slug); count those of a slug whose `ts` is after the first `handed-over` record of that slug in the task state log, and divide by the number of tasks that landed in the period (`factory log events --since <ts>`).

## Tech lead
A handed-over pull request that the lander's loop cannot ship (it conflicts with the default branch, or its checks are red once it is up to date) is not sent to its lead. The task is declared `working` and the pull request goes back to draft; then `factory tech-lead <slug> <number> <evidence>` starts detached, one run per come-back.

- **What it gets.** A fresh headless session (`claude -p`, model `models.tech_lead`, Opus by default) in the task's worktree, with `factory/roles/tech-lead.md` appended to its system prompt, the plugin loaded, `FACTORY_ROLE=tech-lead` in its environment (the factory's own tests clear it), and a prompt with the slug, the pull request, the evidence, the spec's path, the default branch and remote, the head it came back at and the notes of earlier runs on this pull request. The `coding-taste` skill follows the role file and holds the review words. It is a top-level session whose coder and reviewer are its direct subagents.
- **Tools.** Read, Edit, Write, Grep, Glob, Agent, Skill, ToolSearch, and Bash pre-approved for `git *`, `make *`, `gh pr view|diff|checks *` and `gh run view *`; the permission mode is `sessions.lead_permission_mode` (default `auto`), so what is not listed (the repository's test command, whatever it is) is decided by its classifier, and a mode that prompts (`manual`) denies it in a headless run. Denied: `git push`, force push, rebase, `commit --amend`, `git worktree`, `gh pr merge|review|comment|ready` and `gh api`, `gh repo` (`ROLE_DENIED`), `git push*` and `gh run rerun*` (it may not re-run checks until green: the only re-run is `factory rerun`'s): the session resolves and commits, the script pushes. Dispatched subagents are under the same rule. The deny list is a guard against the obvious forms (`git -C . push` is not matched by it), not a boundary: the backstops are the script's checks, which run before its own push, and the default branch's protection. The prompt gives the task's test and golden commands as stated (`factory commands`); with none stated the tech lead finds the command itself, and a refused step is a reason to stop and escalate.
- **Bound.** 30 minutes and 5 USD per run, constants in `factory/lib/factory_core.py` (`TECH_LEAD_TIMEOUT`, `TECH_LEAD_BUDGET`), not settings. On the 30 minutes the claude child's whole process group is killed.
- **Outcomes.** The model answers `resolved` or `escalate` with a note of five lines at most; the script decides the outcome:
  - `resolved`: the checks below pass and the script's push of HEAD to the pull request's branch (`git push <remote> HEAD:refs/heads/<branch>`, as the factory's identity like its other git writes) succeeds. Order: checks, push, comment, `techlead` record, hand-over. The script comments `Tech lead: <note>` and, as a new paragraph, `Back in the merge queue.` on the pull request (a failed comment is recorded as `noted: false` and stops nothing), declares the task `handed-over` with the pull request's URL, and messages nobody. The lander's loop takes it from there: it tests approval, base and checks again before it merges.
  - `resolved` with nothing changed: a run that answers `resolved` and leaves HEAD where it came back needs nothing pushed, but only if the script reads all of this itself (a command that fails or times out is the fact failing): the checks below except the head one; `git fetch <remote>` works and `<remote>/<default>` as fetched is an ancestor of HEAD; `gh pr view` says the pull request is `OPEN` with `headRefOid` equal to HEAD; and the queue's own test of the checks (`checks_stop`) finds them passing. Then the record is `resolved` with equal `head_before` and `head_after` (so a later red at that head goes to the lead, not to another run), the task is handed over as above and the comment is `Tech lead: nothing to change, back in the merge queue: every check is green on <head>, which contains <default> at <tip>. <note>`. If one fact fails it is `stopped` with that fact as the reason (`<remote>/<default> is not merged in`, `the pull request's head is not the worktree's`, `failed or cancelled checks: <names>`, `checks are still running`, `git fetch <remote> failed: <error>`, or what `gh` could not read).
  - `escalated`: the model says the resolution is a behaviour question. The task stays `working`; the script comments `Tech lead: stopped, the lead decides. <note>` and sends the lead's session (brought back if the harness retired it; else the dispatcher's, else the human) `TECH LEAD: <slug>: #N came back from the merge queue (<evidence>) and is yours: <note>. ...`, with the worktree's head, whether it is clean and whether it is pushed (the local `<remote>/<branch>` ref equals HEAD).
  - `stopped`: the same as `escalated`, with the reason in place of the note: `reached 30 minutes`, `reached 5 USD`, `ended without an answer` (non-zero exit or no parsable answer), `the run failed: <error>` (any step of the run after it took its lock: the pull request read, a declare, the launch), or, for a `resolved` answer, the check that failed or `git push failed: <git's message>` (a rejected push, for example when the remote branch moved); for those the line to the lead is `<reason>. <note>`. A failed step never leaves the task `working` with nobody told; a failure after the model ran keeps its session id and cost in the record, and a failure of the hand-over itself leaves a `resolved` record followed by a `stopped` one.
- **Checks, all in the worktree, for `resolved`, before the script pushes and as of the start of the run.** `git status --porcelain` is empty; the branch is the pull request's; the head it came back at is an ancestor of HEAD; `<remote>/<default>` as the script read it before the launch is an ancestor of HEAD (a commit that lands on the default branch during the run does not matter: the lander judged the conflict against that ref, and the ref itself moves when anything fetches); the spec file's sha256 is unchanged. A resolution need not commit: see "resolved with nothing changed". Nothing unchecked is published by the script. Not checked: a weakened or deleted test (the role file forbids it and a reviewer looks at logic): a known limit.
- **One at a time.** A per-task lock (`tech-lead-<slug>` beside `lander.lock`): a second run for the task fails with `a tech lead run is already going` and writes no record (it is not a come-back). A second conflict later on the same pull request is a new run, whose prompt carries the earlier notes.
- **The fallback.** The run is not started, an `unstarted` record says why, and the lead is sent the `LANDER:` line as before, when the spec file or the worktree is missing, a run is going, the process cannot start, or the evidence is red checks at the very head a tech lead resolved, pushed or left as it was (so a red pull request does not loop between the tech lead and the queue).
- **Comments.** Two, one when the pull request leaves the queue and one when it returns. `send_back` posts `Merge queue: back to draft: <evidence>. Started: a tech lead run.` or, when no run started, `... Told: the lead|dispatcher|human.` (a paused task too; a failed comment is printed and stops nothing). The run's end comment is the return line, described above. A lead that hands over itself after a stop posts nothing.
- **Observing.** `~/.claude/factory/tech-lead.log` holds the output of every detached run; the `techlead` log (see Logs) has one record per come-back; the pull request carries the note; `events` give the session's role `tech-lead`, not `lead`, through `FACTORY_ROLE`.
- **Turning it off.** There is no switch. Make `send_back` skip its `tech_lead_start` call, or leave a task without its spec file: it then always goes to its lead.

## Worktree isolation and a worker's Bash call
A Bash call refused with `This session is isolated in the worktree <path>` is refused by Claude Code's worktree isolation, not by a factory hook (the only `PreToolUse` hook matches `mcp__.*`). Its command-shape check cannot be turned off or narrowed by a setting, and it covers every subagent of an isolated session. The owner can report the `$CLAUDE_JOB_DIR` case (rows A20 to A22) through `/feedback`; anything else means not isolating sessions, which the factory relies on.

The lead and its explorers are isolated. A build run (as first started: a headless session in the worktree's directory) and its coder, reviewer, explorer and lander were not, until they were started with `--worktree` (see Isolation to the worktree). The table's two columns are those two conditions. In the second, the one that held for them before, nothing but the role line keeps git inside the worktree. That line, which begins `- Keep git in this worktree`, is the same in `factory/agents/{coder,explorer,reviewer,lander}.md`, `factory/roles/lead.md` and `.claude/agents/{coder,explorer,reviewer}.md`, and `tests/test_repo.py` holds the eight together.

What the short line says (the 2026-11-17 table below measured it). The check reads the whole text of the call, and `git` inside another word counts (`.gitignore`, `github.com`: P22, P25). Refused: a call that names git and holds a value filled in as it runs (`$?`, `$CLAUDE_JOB_DIR` or any `$NAME`, `$(...)`, a backtick, a loop variable: P3, P10, P22, P28, P38); a heredoc with an unquoted delimiter whose body names git (Q1, Q3); a heredoc that writes a file after `&&` (`mkdir -p d && cat > f <<'EOF'`), with git or without (P29, R2); R1, R3 and R4 show that `;` before a heredoc, and `&&` before a heredoc fed to a command, passed. Accepted: plain commands with literal values, also chained or piped (P4 to P7, P12, P24, P33); a heredoc that is the whole call, its delimiter quoted, whatever its body (P13 to P15, P18, P19, Q2). So a variable is printed once and its value typed, and anything longer goes in a script file run as one command (P16, P17). `HOME=`, `GIT_DIR`, `-C` and a `cd` to another checkout are refused by design (P39). Another branch is read with `git show <branch>:<path>`. A command's exit code is read from the Bash result, which carries `Exit code N` for a failure and no such line for 0 (P1, P2); `; echo $?` beside git is refused (P3). Another commit's files are copied with `factory scratch <commit>`.

## Team mode
Since 2026-11-15 every task runs as a lead and a tech lead sharing the work ("team mode" is the only mode; there is no switch). The task's `TaskStarted` event always carries `mode`, always `team`: a record for `isshoni kaizen --modes`, which compares these tasks with those started before.

- **Who does what.** The lead (Fable) writes the spec, decides, assesses and reports; its system prompt is `roles/lead.md`. A tech lead (Opus, headless, in the task's worktree) runs coders, reviewers, explorers and the lander, and hands the lead a written hand-over; its prompt is `roles/tech-lead-build.md`, followed by the `coding-taste` skill, which holds the review words.
- **The lead's tools.** The launch always adds `--disallowedTools` for `Agent(factory:coder)`, `Agent(factory:reviewer)`, `Agent(factory:lander)`, `Agent(coder)`, `Agent(reviewer)`, `Agent(general-purpose)` and `Agent(claude)` (`LEAD_DENIED`, which also holds `PUSH_DENIED` and `Bash(gh pr merge*)`, `Bash(gh pr review*)`, see the next bullet): the lead can dispatch only the explorer. A repository's own agent types are not named, so only the rules hold them back.
- **What every started session is refused.** `PUSH_DENIED` (in `ROLE_DENIED`, `BUILD_DENIED` and `LEAD_DENIED`; the tech lead's list holds `ROLE_DENIED`) refuses `git push` and `git -C <dir> push` with a delete (`--delete`, `-d`, a `:branch` refspec), a force (`--force`, `--force-with-lease`, `-f`, a `+` refspec), `--mirror` or `--prune`; plain pushes (`git push -u <remote> HEAD`, `<sha>:refs/heads/<branch>`) run. `BUILD_DENIED` and `LEAD_DENIED` also refuse `gh pr merge` and `gh pr review`. A deny rule is not a security boundary (Claude Code's documentation): `git -c k=v push`, `sh -c '...'`, an absolute path to git, combined short flags such as `-qd` and a refspec built from a shell variable are not covered. Rerun the check against the installed Claude Code, after an upgrade especially: `python3 factory/tests/probe_push_deny.py` (a local bare remote, about 25 `claude -p` calls on haiku, not part of `make test`; one line per command, exit 1 on a mismatch).
- **`factory build <slug> [--note <text>]`.** Run by the lead in its worktree. It refuses without the spec or the worktree, or while a run holds the lock `tech-lead-<slug>`; else it starts a detached run (output in `~/.claude/factory/tech-lead.log`), prints `tech lead started for <slug>; ...` and returns. The lead ends its turn and is woken by `TECH LEAD: <slug>: build run <n> <outcome>[: <reason>]. Read <hand-over> (the last section).` The task stays `working`: the script declares no hand-over, nor does the tech lead.
- **The run.** A fresh headless session (`claude -p`, model `models.tech_lead`, the subagents on the models of `[models]` as the lead's launch passes them (`--agents`), the lead's `sessions.lead_permission_mode`, the lead's tools, `FACTORY_ROLE=tech-lead`) whose prompt gives the slug, the spec's path, the base branch (the default branch, with a note, when the recorded base has merged) and remote, the hand-over file and whether it exists, the lead's `--note` and the task's stated size. `BUILD_DENIED` is denied: `PUSH_DENIED`, `gh pr merge`, `gh pr review`, rebase, `commit --amend` and `git worktree` (see "What every started session is refused"). Bounds: 90 minutes and 15 USD (`BUILD_TIMEOUT`, `BUILD_BUDGET`), constants, not settings. Time in a run counts against the lead's task limit. It answers `built`, `question` or `stopped` with a hand-over text.
- **Checks.** For `built` the script checks that the worktree is clean, on the task's branch, the spec's hash unchanged and an open pull request (or the end of a report task, below); a failed check, or `reached 90 minutes`, `reached 15 USD`, `ended without an answer`, makes it `stopped` with that reason. Exit 0 for `built`, else 1. Any other failure after the lock is a `stopped` section, record and line, like these. When GitHub cannot say whether there is a pull request the reason is `cannot check for a pull request on <branch>`.
- **The hand-over file.** `~/.claude/factory/specs/<repository>/<slug>.handover.md`, beside the spec; each run appends `## Run <n>: <outcome> (<UTC time>, <cost or unpriced> USD, <minutes> min, head <sha7>)`, a `Reason:` line when there is one, and the tech lead's text, or `No hand-over was written.` The text has the headings `### Result`, `### Rounds`, `### Defects` (`caught_by: what`, with `caught_by` one of `tests`, `reviewer`, `tech-lead`, `ci`), `### Ran`, `### Not verified`, `### Decisions`, `### Questions`, `### Frames` and `### For the lead's eye`. A later run reads it; no session is resumed.
- **Records.** Each run writes a `techlead` record with `kind` `build` (see Logs). The merge-time tech lead above still resolves what comes back from the queue; whatever comes back to the lead (a moved base, a stop, a `LANDER:` line, a comment), before or after hand-over, goes through `factory build --note`, and after hand-over the lead declares only `factory state handed-over` on `built`. The tech lead gives the lander a title and body only for a branch with no pull request, so a later run leaves the lead's body alone.
- **Comparing.** `isshoni kaizen --modes` prints, per stated size, the medians of cost, lead share, lead calls and time to hand-over, the first-pass count, review rounds and defects for tasks before the team (`single`) and since (`team`): different tasks on different days, so a difference is a hint, not a measurement. The dispatch skill holds the criteria for keeping the team.
- **Tasks started before.** A task started `single` finishes as it started: nothing after launch reads the mode, its lead keeps the rules and tools it was launched with, and `state`, `commands`, `retro`, `feedback` and `land` do not look at it. Its `TaskStarted` says `single` (or nothing), so kaizen files it as `single` for good.

### Report tasks
A task whose deliverable is findings, not a change, runs through the same team and lands nothing. Its files are `~/.claude/factory/deliverables/<slug>/report.md`, `evidence/` (saved query results, the ops explorer's included: see Reading production) and `scripts/` (what computes each figure). `factory build` accepts `built` when there is no pull request, `report.md` exists and the branch has no commit its base lacks; otherwise it stops. **Reports.** A report task declared `handed-over` with no pull request and a recorded deliverable that is an existing file outside its worktree leaves the board at hand-over, without `ack`: `clean` removes it once its sessions are finished (the usual rule, not the exited-session exception) and nothing is uncommitted or unpushed. A link or a missing file stays for `factory ack <slug> acknowledged`, and `merged-not-cleaned` names it only once acknowledged, if clean then keeps it. A follow-up is a new task. The dashboard shows `see deliverable` and the file's name in the pull request column.

## Stacked tasks
`new --base <slug>` branches the worktree from the base task's branch and records it in `git config branch.worktree-<slug>.factoryBase`; the pull request targets that branch. The record is never cleared: `status` stops showing a base once it has merged into the default branch, and `clean` stops treating a merged task as stacked. When a base merges, a lead still working on top of it starts a build run, whose lander merges the default branch in (the `base-merged` criterion flags it), and a task already handed over is landed by `factory land`; `merge` retargets a stacked pull request itself when its turn comes.

**GitHub stacks.** The pull requests of a stack also show as a GitHub stack, so the reviewer gets stack navigation and checks judged against the trunk. The stack is derived on every `drain` pass from the open pull requests' base and head refs, right after the snapshot: a chain starts at a pull request based on the default branch, and each next one is based on the head of the one below. Two pull requests on one head (siblings) end the chain, a fork pull request never joins, and a chain of one is no stack. A chain is stacked only when every member is this factory's (a local task worktree is on its head branch and, once recorded, the recorded number); a chain with any other pull request in it is left alone, including an append to an existing stack. The pass only creates a stack or appends to one (`gh api` `repos/{owner}/{repo}/stacks`, header `X-GitHub-Api-Version: 2026-03-10`, through the bot's `gh`); a failure prints one `lander: stacks:` line and landing goes on. `gh stack` (GitHub's extension, v0.3.0 or later; `factory wizard` offers it, step 6) must be installed: the rebase below runs it.

*The stack path.* `merge_one` reads the open stack of the pull request (`stacks?pull_request=<n>`; unreadable is a `merge` stop). When the pull request is the bottom of an open stack (its first open member; a stack with one open member counts), the stack lands with one call or not at all; a pull request in no stack, and an upper member (it stops `base` while its base is open), take the path described under Merging. Every member is read fresh and gated, bottom to top, before any call: not a fork; handed over; approved (the member the caller names by the human's word is held to the word, every other member needs GitHub's own approval: a stop `unapproved` or `stale`); for an upper member, no `base_ref_changed` event on its timeline (read once per upper member per pass) later than its approval (`stale`: `its base changed after its approval`); its base is the default branch (the bottom) or the head of the member below; checks green. `mergeability` and the check that the head holds the default branch's tip are not applied: GitHub decides at the call. The first member that fails stops the whole stack with its kind; the reason of a member other than the one asked about starts `stack member #<m>: `, so the queue does not blame the bottom's task for another member's red check. A member that is not this factory's stops `handover` (it has no task worktree). Then git decides whether the stack is linear (each member's head has the one below as an ancestor). Linear: draft members are made ready, every head is read again (`its head changed during the pass` is `pending`), and one `PUT repos/{owner}/{repo}/pulls/<top>/merge-async` (`merge_method` merge, `merge_action` direct_merge, `sha` the top's head) merges every open member up to the top. The answer is `202`; anything else is a `merge` stop with GitHub's message (`Pull request head branch was modified.` when the head moved). The script polls the returned `uuid` every 2 s for at most 60 s (`STACK_POLL`, `STACK_WAIT`): `merged` lands every member (one `merged` queue record each, one `#N merged <url>` line each, `factory merge` does not try the others again); still pending at the bound is `pending` (`was accepted and has not finished (<uuid>)`); `failed` is a `merge` stop carrying GitHub's text (`merge-async on #<top> failed: <text>`), unless the bottom is behind the default branch, which is then rebased. GitHub may still merge the stack afterward: a later pass that calls while that request is pending gets GitHub's `409` as a `merge` stop, and the members GitHub merged meanwhile have no `merged` queue records and no `release_named`, and their priority ends only at the next drain (`end_priorities`); `clean` still removes the merged tasks. Not linear: rebased first, with no call. A dry run never calls and never rebases: it prints `would merge`, or the stop `stack`: `its stack would be rebased first: #<m> is not on top of #<below>`.

*The rebase* runs in a clone of its own (a temporary directory, removed whatever happens; never a task's worktree), as the bot, with each `gh stack` command limited to 300 s. It checks out the stack, requires `gh stack view --json` to list the members' branches in order and each `origin/<branch>` to be the head that was gated, runs `gh stack rebase` (a failure, exit 3 for a conflict, is a stop `stack` and nothing is pushed), compares each member's patch ids (`git patch-id --stable` over `git log -p -U0`, so an edit of the default branch next to a hunk is no change, and merge commits, which a rebase drops, carry no patch) before and after (`patch_ids`, `diff_changed`; a difference, or git unable to say, is a stop `stack`: `its diff changed in the rebase; nothing pushed`), reads each remote head again with `git ls-remote` (a head that moved since its approval was checked is a stop `stack`, nothing pushed), and runs `gh stack push`. It logs one `rebased` queue record per member and the pass ends `pending` (`its stack was rebased onto <default> in this pass (<why>): it merges on a later pass, on green heads`); nothing else happens in that pass. The kind is `stack`, never `behind` or `conflict`, which would send the bottom's worktree to `update_branch`. `stack` has no row of its own in the stop policy: the dispatcher is told at once, with no polling. The next pass gates the new heads from GitHub's records. The exception to the no-rebase rule is stated under "How the landing keeps history, and its one exception".

*Two windows stay open, by design.* Between the second read of the heads and GitHub's own merge the members below the top are not pinned by `sha`; and between the last `git ls-remote` and the push inside `gh stack push` a commit a writer pushed is overwritten (it does not land). After a rebase the gate passes on GitHub's own record, which moved each review to the new head when the diff was equal; what it does when a force-push changes the diff was not observed. The task worktrees are not touched: after a rebase each is behind a rewritten branch, so the next pass stops each member `handover` (`worktree head is not the pull request's head`) and the drafts go back to draft until the worktrees follow GitHub; that is not yet built. GitHub refuses `gh pr edit --base` on a stack member, and its synchronous merge does not support stacks, so a member outside the stack path (an upper member whose base merged, a retarget by `factory land`) is still unstacked first (`unstack`, which removes every unmerged member); the next pass re-forms what is left once its bottom targets the default branch. A dissolve that fails, or that leaves locked members (HTTP 200), is a stop. To undo by hand: `gh api -X POST -H "X-GitHub-Api-Version: 2026-03-10" repos/{owner}/{repo}/stacks/<number>/unstack`; the next pass forms it again while the chain holds.

## Isolation to the worktree
Claude Code isolates a session to one worktree only when the session is started with `--worktree <name>` from the main checkout (`MAIN`): a `claude -p` started with its working directory already in a worktree (`WT`) is not isolated. The harness then refuses a command that runs git in another checkout (`git -C`, `--git-dir`, `GIT_DIR`, `GIT_WORK_TREE`, a `cd` there first) and a file edit into `MAIN`, and it refuses command shapes it cannot verify (see "Worktree isolation and a worker's Bash call"). Deny rules cannot do this: they match the text of a command, not where it would act.

The build run, the merge-queue tech lead and the `factory land` lander are therefore started `claude -p --worktree <name>` with `"worktree":{"baseRef":"head"}` added to their one `--settings`, beside the attribution-off settings (lean start or not: one flag), and with their working directory `MAIN`, when `WT` is `MAIN/.claude/worktrees/<name>`. `baseRef=head` is there so that a reopened worktree keeps its tip; it is kept on the documentation's word (a reopen resets a clean worktree to the default branch under the default `fresh` base), documented and not reproduced: the probe's P3 showed no reset without it. Under another path the start is as before (working directory `WT`, no flag) and the run prints `this session is not isolated to its worktree` to stderr. The session's own `pwd` is `WT` either way. The harness leaves the worktree locked after a `-p` run. The factory reads whether `WT` is locked before the run and, when the run ends, runs `git worktree unlock WT` only if it was not: a lock that was already there (a live lead's, whatever its reason) is never unlocked or re-locked. An unlock that fails for a reason other than "not locked" prints one line to stderr.

## Logs
All under `~/.claude/factory/`, JSON lines, append-only, mode 0600. Except where noted, a record carries `ts` (UTC, `2026-11-14T00:01:02Z`), `repo` (the main checkout's path), `slug`, `role` (`lead`, `dispatcher`, a subagent's type without the `factory:` prefix such as `coder`, or the same for a session started with `--agent`, as `factory land` starts the lander, `subagent` when it has none, else `other`; `feedback add` stores the `--role` it is given), `model`, `version` (the plugin's), `session`.

| Log | Files | Written by | Kept |
|---|---|---|---|
| events | `events-YYYY-MM.jsonl` | the plugin's hooks; `new`, `clean` | the current month and the 12 before it |
| retros | `retros-YYYY-MM.jsonl` | `factory retro` | forever |
| feedback | `feedback-YYYY-MM.jsonl` | hooks; `feedback add`, `decide`, `set` | `open` and `accepted` forever, `done` and `rejected` at least 12 months |
| task state | `tasks-YYYY-MM.jsonl` | `new`, `state`, `ack` | the current month and the 12 before it, and the newest record of every task that still has a worktree |
| firings | `firings-YYYY-MM.jsonl` | `watch`, `firing`, `miss` | the current month and the 12 before it, and every miss and every firing that is still open or was escalated, with its records |
| tech lead | `techlead-YYYY-MM.jsonl` | `factory tech-lead`; the lander's loop (an `unstarted` record) | the current month and the 12 before it |
| ops watch | `ops-YYYY-MM.jsonl` | `factory watch`'s looks: one record per look and one per gap of missed looks (see Watching production) | the current month and the 12 before it |
| kaizen review | `reviews-YYYY-MM.jsonl` | `factory review`: `skipped` for a skip, `started` then `ran` or `failed` for a run (see Kaizen review) | forever: a proposal may cite it |
| queue | `queue-YYYY-MM.jsonl` | the merge queue (`merge`, the lander's loop); `factory land` | the current month and the 12 before it |
| lead outbox | `outbox-YYYY-MM.jsonl` | `forward`, `factory lead`, the watch tick (see Messages) | the current month and the 12 before it |
| gh calls | `gh-YYYY-MM.jsonl` | every `gh` call that took over 2 s or failed: `ts`, `argv`, `cwd`, `seconds`, `rc`, `error` (the first stderr line; never the token). A `gh` call without a timeout is cut at 30 s. `isshoni kaizen` appends to the same file | pruned like the other logs: the current month and the 12 before it |

Unsuffixed `events.jsonl`, `retros.jsonl`, `feedback.jsonl`, `tasks.jsonl` and `firings.jsonl` from older versions are still read, as the oldest. Old files are deleted when a log's first record of a new month is written; the lines still needed (the Kept column) are first carried, unchanged, into the current month's file. What goes after 12 months: a task's records once its worktree is gone, and firings that cleared and were suppressed or never decided. A task's state is its record with the newest `ts`, whichever file holds it.

`factory log` prints records oldest file first, where `since <= ts < until`; a bound is a `ts` or a prefix of one, at least `YYYY-MM`.

**Events** add `event` (the hook's name, or `TaskStarted`, `TaskRemoved`) and:

| `event` | Fields |
|---|---|
| `SessionStart` | `source` |
| `SessionEnd` | `reason` |
| `UserPromptSubmit` | `from`: `human`, `subagent`, `session` or `notification` |
| `Stop` | `background_tasks` (a count) |
| `SubagentStart`, `SubagentStop` | `agent_id` |
| `Notification` | `notification_type`, `message` |
| `PermissionRequest` | `tool_name` |
| `PermissionDenied` | `tool_name`, `reason` |
| `PostToolUse` (`SendMessage`, `SubagentHandback`) | `tool_name`, `agent_id`; for `SendMessage` also `to` and `kind` (`QUESTION`, `BLOCKED`, `OVERTIME`, `SPLIT`, `DONE` or null); for a `QUESTION`, `BLOCKED` or `OVERTIME` also `summary`: the message's first line after the `KIND: <slug>` prefix (the next line when the first is only the prefix), cut to 200 characters and left out when empty. Nothing else of a message is stored |
| `TaskStarted` | `base`, `lead_model`, `models` (the agent roles' configured models at launch), `mode` (`team`; `single` or absent on tasks started before the team was the only way), `size` (only when the brief gave one) |
| `TaskRemoved` | |

**Feedback** is the outbox: issues agents report about the factory, and key decisions leads took without asking. An entry line adds `id`, `text`, `status: "open"`; a status line is only `id`, `ts`, `status` and optionally `pr`, and the latest one wins. `--since <ts>` lists the entries filed strictly after `<ts>`, compared with the entry's `ts` (the filing time, which a later `set` does not change): `YYYY-MM-DDTHH:MM:SSZ`, as `--json` prints it, or a date `YYYY-MM-DD` for everything from that day on; anything else exits 2. The last `ts` of one round is the next round's `--since`. Entries are filed from the section headed `Factory feedback` at the end of a subagent's report or a lead's `DONE:` message, one per list item (`none` files nothing); the same item filed twice is one entry. An entry whose text starts with `DECISION:` is a decision, any other an issue. The [kaizen review](#kaizen-review) reads the outbox, the retrospectives and the cost records as evidence and files its proposals as issues; the human decides there.

**Retros** add exactly these keys:
```json
{"defects": [{"caught_by": "tests|reviewer|lead|ci|human", "what": "...", "cause": "spec|brief|conflict|scope|code"}],
 "slowed": ["..."], "rules_missing": ["..."], "rules_dead_weight": ["..."], "brief_questions": ["..."]}
```
`cause` is optional (a lead on the old rule text omits it; any other key or value is refused): why the defect arose. `spec`: the spec was wrong or silent; `brief`: the brief was; `conflict`: a merge of the base; `scope`: the scope changed mid-task; `code`: the code missed what the spec said. It answers why a review round happened; bad: one cause over a third of the defects.

**Queue** (`queue`, one record per thing the merge queue or `factory land` did to a pull request) carries only `ts`, `repo`, `slug` (`null` for a pull request of no task), `pr` (`null` for a `land-*` step before a pull request exists), `head` (full SHA of the head the step acted on) and `step`, with these fields:

| `step` | When | Fields |
|---|---|---|
| `merged` | `merge`, and the lander's loop, after `gh pr merge` succeeded (never with `--dry-run`) | `approved_at`: ISO time of the approving review (`submitted_at`) or of the accepted `lgtm` comment, `null` when no approval was required or GitHub gave no time |
| `updated` | the loop merged the default branch into the branch and pushed | `tip`: the default branch's SHA merged in |
| `rerun` | the loop started a re-run of failed checks | `text`: the rerun line |
| `sent-back` | the loop returned the pull request to its lead | `kind`, `text` (the stop line), `told` (`tech lead`, `lead`, `dispatcher` or `human`), `files` (only for `conflict`: the conflicting files, may be empty) |
| `stopped` | the loop reported a stop to the dispatcher or the human | `kind`, `text`, `told`; for `not-ours` also `tests` (names) and `checks` |
| `unblocked` | a held pull request was released (`factory unblock`, or a merged pull request's `Unblocks:` line) | `by`: `word`, or `#<n>` of the fix |
| `land-updated` | `factory land` merged its base in | `base`: the target ref |
| `land-conflict` | that merge left unmerged files (a merge that failed otherwise writes nothing) | `base`, `files`: the unmerged files |

What each answers, and what a bad value looks like:
- `merged.approved_at`: splits hand-over to merge into waiting for the human (hand-over to approval) and waiting for the queue (approval to merge). Bad: approval to merge p90 over 15 min.
- `updated`, `rerun`, `stopped`, `sent-back`: what the queue attempted per pull request, not only what it merged. Bad: a `sent-back` whose next record for that pull request has the same `head` (it changed nothing). A tech lead run that changes nothing is a `resolved` `techlead` record with equal `head_before` and `head_after`.
- `sent-back.files`, `land-conflict.files`, `land-updated`: late conflicts per task and per file. Bad: over 0.2 conflicted base merges per merged pull request; one file in most of them.

All of these, and the retro `cause`, start on the day this merges: nothing earlier is backfilled (the old queue logged nothing; the gh log keeps only slow or failed calls). Pauses and prioritized landings are not in this log.

**Tech lead** (`techlead`, one record per come-back or build run) adds `kind` (`merge` for a come-back, `build` for a `factory build` run; a record without it is `merge`), `role` (`tech-lead`), `model`, `version`, `session` (the run's Claude session id, `null` when unstarted or unparsed), `pr`, `evidence`, `outcome` (`resolved`, `escalated`, `stopped`, `unstarted` or `paused`: a start that declared a pause and ran no model; `built`, `question` or `stopped` for a build run, whose `pr` is `null` and `evidence` is `build`), `reason` (why stopped or unstarted), `note` (the model's note), `noted` (whether the pull request comment was posted), `head_before`, `head_after` (full SHAs), `cost_usd` (`total_cost_usd` of the run, `null` when unpriced, never 0) and `seconds`.

**Task state** adds `state` and, from the hand-over on, `deliverable`. A task's state is its last record.

## Kaizen review
A fresh headless session reviews how the factory worked and proposes changes; the human decides. The dispatcher does not run it: it is in the day's work, it is one of the roles under review, and its context is the dearest place to read the records. The session's charter is `factory/roles/kaizen-review.md` (appended whole as its system prompt): the order of questions it asks of a problem (owner, authority, information, judgement, then a mechanism), what counts as evidence, and what it may publish.

It is a script-run session like the site manager's, not a factory task: a task needs a brief from the dispatcher, a worktree slot and a lead, tech lead and reviewer. The cost of that choice: no second model checks the report. Instead every figure in it must come from a script kept beside it (`scripts/`, with the output in `evidence/`), and the human reviews each proposal.

```
factory review          # decide, with no model call; when due and active, run in the foreground
factory review --run    # the detached form: what the watch tick starts, output in review.log in the store
```
`factory review` prints its decision in one line. The review covers the whole store, not one repository: one at a time, under the non-blocking store lock `review.lock`. Whichever repository's tick finds it due starts it, and the session's working directory is that repository's root.

**Due and activity.** `kaizen.review_hours` hours have passed since the last `reviews` record of any outcome (`ran`, `skipped`, `failed`), or there is none. A `started` record counts too, so a run that died (killed, or its folder could not be made) retries after the period, not every tick. It then needs activity: a record with `ts` later than the start of the last review that `ran`, in `tasks`, `feedback`, `retros`, `queue`, `techlead`, `comments` or `events`. `reviews` and `gh` are not counted (the review writes them), nor the outbox lines the review's own mirror writes (they carry `"by": "kaizen-review"`), nor `ops` and `firings` (a watch writes them on a timer while nothing happens: an idle weekend would review every hour). Pull request activity reaches the store through `queue`, `comments` and `tasks`. Due with no activity writes one `skipped` record (`reason: "no activity since <ts>"`) and stops: one skip per period, not one per tick. The decision reads stored records only. The watch tick (`review_tick`, beside the ops looks, before the watch lock) starts a detached `factory review --run` and returns at once, so a tick is never slowed by a review, and does nothing while the lock is held.

**Bounds.** 20 minutes (`REVIEW_TIMEOUT = 1200` s) and 3.00 USD (`REVIEW_BUDGET`, as `--max-budget-usd`) per run. A run that hits either is `failed` with that reason: what it wrote stays in its folder and nothing from it is posted. Worst case per day: 24 runs, 72 USD. `report.md` must exist, else the run is `failed`.

The settings are `kaizen.review_hours`, `kaizen.issues_repo` and `models.kaizen_review` (see Settings).

**The session.** `claude -p --permission-mode dontAsk --output-format json`, `SETTINGS_ISOLATION`, no plugin, agents or MCP server, no `SendMessage`; tools `Read`, `Grep`, `Glob`, `Bash`, `Write`. A permission rule limits `Write` to the review's folder, and `gh`, `git push`, `git commit`, `curl` and `factory` are denied in `Bash` (it reads the logs as files and must not change a state). What the flags cannot enforce: `Bash` itself (a `python3` script, say) could still write files elsewhere on the machine; the charter forbids it, and nothing else stops it. The session starts with the lock-down of `factory env` in its environment (`GH_TOKEN=unavailable`, the credential helper reset), so `gh` and `git` run with the environment as given have no GitHub credential. A command that changes its environment (`env -u GH_TOKEN gh ...`) or reads the store's `identity/` files (cached bot tokens, the key) still gets one; the charter forbids that too. The script's own `gh` calls run outside the session. The prompt holds the time now, `since` (the start of the last review that ran, else 24 hours ago), the store, the folder, the previous `report.md` and whether `input/issues.json` exists.

**Folder**, `deliverables/kaizen-review-<YYYYMMDDTHHMMSSZ>/` in the store, made by the script:
- `report.md`: what it looked at, checks of earlier proposals, each problem with its rung and evidence, what it proposed or left alone, what it did not look at. Stays on this machine.
- `scripts/`, `evidence/`: the scripts behind every figure and their output.
- `proposals/`: one file per item (below).
- `input/issues.json`: written by the script before the session starts, only when posting is on: every issue labelled `kaizen` in the target repository, open and closed, with number, title, body, state, labels and comments (`gh issue list --state all --label kaizen`, at most 200).

**The `reviews` log** (`reviews`; a review that is off or not due writes nothing, a skip writes `skipped`, a run writes `started` and then `ran` or `failed`): `ts` (the start; the same in a run's two records), `outcome` (`started`, `ran`, `skipped`, `failed`), `reason` (a skip or a failure), `folder` (also in `started`, written before the folder is made), `since`, `cost_usd` (`total_cost_usd` of the run; `null` when the output has none, shown as unpriced, never 0), `seconds`, `session`, `posted` (`[{"file", "issue", "kind"}]`) and `held` (`[{"file", "why"}]`); `started` carries only `ts`, `outcome` and `folder`. It is never pruned.

**A proposal** is a file in `proposals/`, front matter and fixed sections:
```
---
kind: proposal            # proposal | evidence | check
issue: 12                 # evidence and check only: an existing issue's number
title: Reviewer gets the spec's fact list   # proposal only, at most 80 characters
rung: information         # proposal only: owner | authority | information | judgement | mechanism
role: reviewer            # the role it changes
cites: [3fa9c1d2e4b6]     # outbox ids, may be empty
---
## Problem
## What the role lacked
## Proposal
## Evidence
## Number
```
A `proposal` has all five sections, non-empty. `evidence` has `## Evidence` only: new evidence for an open proposal. `check` has `## Number` only: the value now, the target and a verdict (`worked`, `not yet`, `did not work`) for an accepted proposal. The session never touches GitHub. The script holds a file (it stays in the folder, listed in `held` with the reason) that lacks a field or section, has an unknown `kind` or `rung`, or names an `issue` not in `input/issues.json`.

**Posting** is on only when `kaizen.issues_repo` is set. The script makes the labels `kaizen` and `kaizen:accepted` when absent, then posts a `proposal` as an issue (label `kaizen`, the five sections, a footer `Role: <role> · Rung: <rung> · Cites: <ids> · Review: <stamp>`) and an `evidence` or `check` as a comment on its issue. The `gh` calls act as the factory's App with a token for the target repository, never the working directory's and never another account: with no identity, nothing runs and the file is held. Every call has a timeout; one failure holds that file and the rest still go.

**Permission.** The App needs `Issues: Read and write` on the target. Without it, opening an issue and reading still work, but a comment, a label on an issue and a close are refused (`Resource not accessible by integration`, HTTP 403): the file is held with the exact refusal line and posts nothing else of it. The factory does not work around it.

**Public content.** Proposals become public issues, so before any post the script scans the title and body and holds the file when it finds: the home directory's path, any `/Users/<name>/` or `/home/<name>/` path, or a `~/` followed by a path character; the GitHub name (`name` or `owner/name`, whole words, any case) of any other repository in the store's records (every log that carries a `repo`, `firings` and `ops` included); a host or MCP server name from `ops.tools` or `hosts.json`; an IPv4 address. `why` names the kind of match, not the text. The script rewrites nothing; the human reads a held file locally. Limits: the scan knows names, not meaning. Directory basenames of other checkouts are not matched as bare words (one is an ordinary English word) and are caught only inside a path under a home directory (`$HOME`, `/Users/<name>/`, `/home/<name>/`, `~/`). Text paraphrased from production data is kept out by the session having no ops tools and by the charter, not by the scan.

**Decisions** are made on the issue, which is the one source of truth. Open with `kaizen`: proposed. The human adds `kaizen:accepted`: accepted. Closed without that label: rejected. Closed with it: done (the pull request that carries it says `Closes #N`). A label and not GitHub's close reason, because the default close button says "completed" and would read a rejection as done. The next run reads the states from `input/issues.json`: it checks each done proposal against its number and does not re-propose a rejected one without new evidence. The dispatcher lists `gh issue list --label kaizen:accepted --state open` and opens a task per issue; the review sends it nothing.

**Outbox mirror.** At the start of a run with posting on, after fetching the issues, the script sets the outbox entries cited in each issue's footer through the path of `factory feedback set`: accepted to `accepted`, done to `done`, rejected to `rejected`, only when the status differs; its outbox lines carry `"by": "kaizen-review"`, and `factory feedback` reads them like any other status line. It is derived: nothing reads the outbox to learn a proposal's state.

## Site manager
A job runs `factory watch` every 2 minutes (`WATCH_INTERVAL`), output appended to `~/.claude/factory/watch.log`. It follows the dispatcher's life; `factory schedule install|remove|status` are for manual control. Each tick does four things:

- **The cheap part (every tick).** With no task working, blocked or handed over whose worktree is still there, it does nothing and makes no `gh` call, so an idle repository costs nothing. Otherwise one `gh pr list` (20 s timeout; on a failure it prints `comments: <why>` and the tick goes on) reads the open pull requests with their reviews and comments, and that one snapshot (the `churning` criterion reads it too) serves two consumers in this order: the comment forwarder (`watch_comments`); and the draft flags (`sync_drafts`), when a task is handed over or a task's pull request is ready for review while its task is not. The draft sync builds its picture from the snapshot (one `claude agents` listing and local git per task, no further `gh pr list`), so a tick with k handed-over tasks makes 1 + (the number of their pull requests whose head matches, one `gh pr checks` each) `gh` calls, plus a `gh pr ready` per flag that changes: a green handed-over pull request turns ready within about two minutes. It is at most 30 GraphQL requests an hour per repository for the list.
- **Events and fact firings (every tick).** The fact firings in `FACTS` marked for every tick (see Facts and verdicts) and the events that wake the site manager (see What wakes it) run through the same dedupe, `fire()` and site manager path as the health pass.
- **`overrun` and `run-stopped` (every tick).** An open, undecided `overrun` firing (a lead's `factory overrun`) is sent to the site manager on every tick, not only the health pass, and so is a `run-stopped` firing (see Overruns and stopped runs). So an ask is answered within about two minutes, and a build run that ended `stopped` is looked at on the next tick.
- **Health (when 30 minutes, less 60 s of slack, have passed since the last health run, kept in `lander.json`).** Everything below: the session list, the fact firings that need `gh` or git (`base-merged`, `ci-red-default`, `ci-red-handover`, `merged-not-cleaned`), the pace check and the digest.
- **The lander's loop (last, after health and the digest).** While a task is handed over or paused, or the human's word stands, the tick runs `drain` (see Merging) until health is next due. It holds the lander lock; a tick that finds it held skips silently. The loop runs inside its tick, which holds the watch lock: the ticks that come due meanwhile are skipped (`watch: a tick is already running`). So the loop runs the whole tick again itself, at the top of a pass (beside the ops looks, before the pull request list), each time 2 minutes (`WATCH_INTERVAL`) have passed since the last began: the cheap part, the every-tick criteria, the site manager and the overrun answers are at most one pass late (a pass with a conflict run can last 30 minutes), not until health is next due. Each in-loop tick prints its `watch <repository>` stamp, and one that raises prints `watch: tick failed: <why>` and the loop goes on. `factory lander` runs no tick. Nothing ends a tick from outside: `health` says when one is stuck (see Shutdown and leftovers).

- **Label.** `com.claude.factory.watch.<repository directory name>-<8 hex of the sha256 of the main checkout's path>`: two folders with one name get two jobs. The job runs in the main checkout; each tick finds the dispatcher itself.
- **Backends**, chosen at run time: launchd on macOS (`~/Library/LaunchAgents/<label>.plist`); elsewhere a systemd user timer when `systemctl --user` works (`<label>.service` and `<label>.timer` under `$XDG_CONFIG_HOME/systemd/user`, `~/.config` by default); else one line in the user's crontab ending in `# <label>`; else `install` exits 2. `install` prints `installed <label> (<backend>)`, `remove` prints `removed <label>` or `nothing installed: <label>`, `status` prints whether the job is present and loaded. On systemd the timer stops when you log out of every session unless `loginctl enable-linger` is on; `install` says so when it is not.
- **PATH.** The job gets a minimal `PATH`, baked at install: the directories of `git`, `gh`, `claude` and the running Python, then the system directories. `install` fails with `<tool> is not on PATH` when one is missing. Move a tool and install again.
- **Start.** The plugin's hook (no model, no prompt) installs the job when the dispatcher session (registered, or in an old-style name working in the repository) starts, resumes or sends a prompt and there is none loaded. For a session that is not the dispatcher, in a main checkout without the job, that check costs about 0.2 s per prompt (`git worktree list`, the scheduler's status, `claude agents --json --all`). On startup and resume it replaces the job, so after a plugin update the job moves to the new copy at the dispatcher's next start or resume; the superseded copy stays on disk for 14 days. `factory dispatcher register` installs it at once.
- **Stop.** When a dispatcher session ends (a `/clear` is not an end, but gives the session a new id: run `/factory:dispatch` again) and no other live one of the repository remains, the hook removes the job. A crash fires no hook, so a health tick that finds no dispatcher session removes the job itself. Both keep the job while a task is declared handed-over, so that an approval still merges; the health tick removes it once none is. Such a tick starts no site manager; with live tasks it notifies once that the dispatcher is missing, and it keeps the job one more tick when it could not judge that.
- **Legacy.** On macOS `install` and `remove` also drop the job of the earlier label `com.claude.factory.watch.<repository directory name>` when its working directory is this repository.
- Install from the main checkout or the installed plugin: a job installed from a task worktree breaks when the worktree is removed.
- `remove` by hand lasts until the next prompt of a live dispatcher, which installs the job again.
- `tools/walk.sh` walks this whole life with the real scheduler, stub `claude` and `gh` and a throwaway repository; CI runs it on Linux (systemd, then cron), on macOS and in the container; a pull request that changes only `docs/`, `assets/` or a top-level `*.md` runs `test` alone and the other three checks report as skipped (which GitHub counts as passed). It installs a real job, so outside CI it wants `WALK=1`. `WALK_CRON=1` hides systemd so that cron is chosen; `WALK_DAEMON=1` leaves each cron tick to the cron daemon (the job's schedule becomes every minute) instead of running the job's line by hand.

`health` prints the fact firings current right now; it writes nothing, except that a slow or failed `gh` call is logged to `gh-YYYY-MM.jsonl` (any command does). The watch tick collects the events and the fact firings without running a model, logs each new firing, and only when an event happened starts one headless run (`models.site_manager`, Opus by default, about twice the Sonnet price; read-only investigation, at most 30 turns, $1.50 and 10 minutes; see Looking and messaging) under `factory/roles/site-manager.md`. `factory` starts every `claude` child (the lead, the site manager run, the lander run, `claude agents`, `claude rm`) without `ANTHROPIC_LOG` in its environment, since with `ANTHROPIC_LOG=debug` `claude` logs to the standard output that is read as JSON. The run gets the evidence in its prompt, may look further itself, and either messages the dispatcher (first line `ESCALATION: <repository directory name>`) or a task's lead, or suppresses the firing with a reason. Nothing is escalated twice while its condition lasts, with one exception: when a message to a lead was sent and the condition still holds at the first health run more than 30 minutes later (usually about an hour, as health runs are 30 minutes apart; `LEAD_GRACE_MINUTES`), the firing is cleared and fires again, with `; lead told at <time>: <reason>` appended to its `detail`, and that firing can only go to the dispatcher or be suppressed (the script does not record a lead message for it), so a lead that ignores its message is never a dead end; a suppression is looked at again after two hours. `dispatcher-missing` becomes a desktop notification instead (`notify-send` on Linux; without a notification service, or when it fails, a `notify: ...` line in the watch log) and holds everything else back until a dispatcher exists. Either way the firing is recorded as escalated by `watch`, so the human hears once.

**Facts and verdicts.** `factory/criteria.json` holds only the five digest findings (see Digest). No watch threshold exists in the script, the file or the settings. The criteria of the earlier watch became one of three things:

| Was | Becomes |
|---|---|
| `nearing-limit`, `past-limit`, `quiet`, `blocked-unanswered`, `handover-unacknowledged`, `busy-after-handover`, `review-loops`, `deep-stack`, `cost-outlier`, `lead-heavy`, `wrong-model` | **A fact handed over; the verdict is the site manager's.** No function, no firing, no threshold: the fact is in the task's row (below), and an entry of the reference file says what the old line was and how it scored. A number crossing a line is not a problem. |
| `overrun`, `run-stopped`, `collision`, `new-spec`, `churning`, `base-merged`, `ci-red-default`, `ci-red-handover`, `red-waiting`, `ended-undeclared`, `merged-not-cleaned` | **A fact that happened; still fired by the script, and it decides.** No threshold (`ended-undeclared` lost its 10 minutes). The script knows these better than a model (git, the logs, the session list), and their identity (a pair, a run number) is what decisions and outcomes hang on. Every tick: `overrun`, `run-stopped`, `collision`, `new-spec`, `churning` and `ended-undeclared` (a task declared `working` with no live lead session and no build run holding its lock; the session list is read only when a task is declared `working`). On the health pass, because they need `gh`: `base-merged`, `ci-red-default`, `ci-red-handover`, `red-waiting`, and `merged-not-cleaned`: one finding per task whose work is over (phase `merged`, declared settled or `closed`, or a report) that `clean` still keeps, the detail being `kept: <the reason>`; not for a task kept for a live or interactive session or for a task stacked on it (`base-merged` owns that wait). It clears when the task is gone. |
| `lgtm-blocked` | **The queue's own decision**, recorded by the lander as before, and a wake event; the site manager does not decide it and its entry does not exist. |
| `dispatcher-missing` | **A guard in the script**: a desktop notice, no model, as before. With no dispatcher there is nobody to tell. |
| the five digest findings | Not moved (see Digest). |

Nothing is passed on unjudged: no firing is `always`.

**The reference file.** `factory/roles/site-manager-cases.md` has one `## <entry>` section per thing worth noticing (the twelve of the first row above, the nine of the second, and `unlisted`), each with `What`, `Why it matters`, `What it has looked like` (the old line as experience, and what happened on 2026-11-14 and 15), `A good call` and `Score`. It is reference, not rules; it is appended to the system prompt after the role file. A review (`kaizen-review-finish`) and the human edit it by hand, from `factory firings` and the misses; nothing writes it. Its scores were counted from the stored firings of 2026-11-14 and 15.

**The picture.** On each look the prompt body is one object: `since`; `woken_by` (what woke it); `firings` (the facts that need a decision, each with its evidence, without `what`); `tasks` (one row per task in flight). A row carries, when not empty: `slug`, `phase`, `state`, `declared` (how long ago), `waits_on`, `paused`, `session`, `lead`, `pid`, `worktree`, `branch`, `base`, `stack` (when over 1), `size`, `elapsed`, `limit`, `extended_minutes`, `last_commit`, `last_activity`, `dirty`, `ahead`, `behind`, the pull request (`pr_url`, `pr_state`, `pr_draft`), `merged`, `reviews` (reviewer dispatches since the start), `runs` (build runs oldest first: `outcome`, `reason`, `cost_usd`, `minutes`), `models_off` (a role and model that differ from the configured one), `children` (for a handed-over task whose session is not finished: up to five child processes with ages), `transcripts` and `calls` (its own calls and the script's firings on the task from the last 24 hours, newest first, at most 10: `entry`, `decision`, `to`, `reason`, `decided`, `outcome`). The cost of the tasks (`cost_usd`, `lead_share_pct`, with `landed_median_usd` once) comes from the monitor, not the plugin: set `paths.monitor` in the settings to the path of `isshoni`. Without the setting, or when the monitor does not answer within its timeout, the cost is `unpriced: <why>`, never zero. The median is over this repository's tasks that have a merged pull request and a cost above 0; the monitor's price file sets the currency. `row["nearing"]` is a display mark for the Go reader (`NEARING_PERCENT`), not a criterion, and wakes nobody.

**What wakes it.** Each tick collects, from records only and with no model, what happened since the last look (the last record of the `looks` log; with none, one tick back):
- `task-started`: a `TaskStarted` event with role `dispatcher`, every task the dispatcher starts.
- `pr-opened`: a pull request in the tick's one `gh pr list` snapshot that the last look did not list (none before the first look).
- `pr-gone`: a pull request the last look listed that is no longer open and has no `merged` step in the `queue` log (merged or closed by hand).
- `queue`: every record of the `queue` log since: `merged`, `updated`, `sent-back`, `stopped`, `rerun`.
- `state`: every declaration by a lead of `blocked` or `handed-over`, with `waits_on`.
- the fact firings above that are new or due to be sent, and pending `overrun` asks.
- `pace`: on the health pass, when a task is declared `working` or `blocked` and the last look is at least 29 minutes old (`HEALTH_SECONDS`). Any look resets it.
A tick with at least one of these gathers the full picture and starts the site manager once (all its events share the run); a tick with none prints `nothing new` and gathers nothing more than before. With no dispatcher there is no run, and `overrun` asks are settled by the script as before.

**Not built.** A wake on every build run a lead starts or ends (33 ended on 2026-11-15; a stopped one wakes it through `run-stopped`, a built one through `pr-opened` or `state`), and on every subagent dispatch (273 that day). Checking the default branch's CI on every tick is not built either.

**The `looks` log.** After every site manager run of the watch job, usable or not, one record in `looks-YYYY-MM.jsonl`: `ts`, `repo`, `woken_by` (as sent), `firings` (ids), `tasks` (rows given), `calls` (decisions made), `cost_usd` (null when the run reported none), `seconds`, `run` (the session id), `model`, `prs` (the open pull request numbers of the snapshot) and `failed` (why, only when the run was not usable). A failed run still writes its record, so its events are not retried for ever; undecided firings come back by the rules above. The cost line on the standard output stays.

**His own calls.** A decision item has either an `id` (a firing it was given) or `entry`, `slug` and `detail`: a call the script did not fire. It is valid when `entry` is a heading of the reference file, `slug` is a task of the picture, `detail` and `reason` are not empty and the decision is `escalated` (to the dispatcher by default, or the lead) or `suppressed`, which is how "looked and did nothing" is recorded; at most one per entry and task in a run. A `to: lead` is refused when the task has no live lead or its `calls` already hold a lead call for the same entry. The script writes the call as a firing (`criterion` the entry, `subject` the slug) with its decision and a clearing, sends an escalated one itself (`ESCALATION` to the dispatcher with the id in the line, or `SITE MANAGER` to the lead), and scores it like any other. The entry `unlisted` is for what no entry names; a review turns repeated ones into entries.

**Score.** `factory firings` prints, before its totals line, one line per entry that has any record: `<entry>: fired N; escalated E (acted A, ignored I, no outcome O); to lead L; suppressed S; missed M; precision P`, with `; extended X`, `; told T` and `; paused N` after `suppressed` when not zero; `--json` carries the same under `summary.entries`. `factory miss <text> [--slug] [--firing] [--entry <name>]` lands a miss against an entry (`--entry` must be a heading of the reference file; with `--firing` alone it is that firing's entry; with neither it counts under `unlisted`).

**Known limit.** `base-merged`, `ci-red-default` and `ci-red-handover` need `gh` and stay on the health pass: a red default branch wakes the site manager on the pass that sees it, at most 29 minutes late. `ended-undeclared` needs no build run holding the task's lock: a lead gone during a build run is a fact in its row, not a firing, until the run ends. It also needs no session of the task with a process: an idle lead that still has its `pid` (waiting on its overrun ask, say) does not raise it. A lead that ends its turn without declaring and sits idle is therefore not raised while its process lives; the harness retires it after 60 idle minutes and the next tick raises the fact, so a silent stop is seen up to 60 minutes later.

**Cost (an estimate).** Counted from the stored records of this repository, with events bucketed by two-minute tick: under this design 2026-11-14 has 174 looks (173 ticks with an event, 1 pace look) where 24 site manager runs happened (2.02 USD), and 2026-11-15 up to 17:00Z has 69 looks where 16 runs happened (1.77 USD). Ticks with an event, by kind alone (they overlap): task started 71 and 19, pull request opened 83 and 17 (counted from the first hand-over naming it, the only record), queue 6 and 24, lead's block or hand-over 113 and 23, stopped build run 0 and 12, fact firing 19 and 7. What a look costs with the picture is not known from the store: the six Opus runs of 2026-11-15 averaged 0.17 USD on a few firings; at that figure the two days are about 30 and 12 USD, and the hard ceiling is 1.50 USD a look. The readings not built: every build run's end adds 2 looking ticks on 2026-11-15 (71), every subagent dispatch doubles them (329 and 142).

The dispatcher closes the loop: `firing <id> acted|ignored` on each escalation, `miss` for a problem that was not escalated (`--firing` when it had fired and was suppressed, `--entry` for the reference entry it belongs to). `firings` lists the log, then the score per entry (see Score), then precision `acted/(acted+ignored)` and recall `acted/(acted+missed)`. `extended N (kept K, overran O, no outcome)` is printed beside them, and the listing shows `minutes` and `until` for an extended firing as it shows `waits_on` for a paused one. Escalations to a lead are counted apart (`to lead` in the table's last line): `escalated`, `acted`, `ignored` and `no outcome` cover only those the dispatcher received.

`firings-YYYY-MM.jsonl` records carry only `ts`, `repo` and one of: a firing (`id`, `criterion`, `escalate`, `slug`, `subject`, `detail`, and for `collision` `files`); a decision (`id`, `decision`: `escalated`, `suppressed`, `paused`, `extended`, `closed` or `told`, `reason`, `by`: `site-manager` or `watch`; `waits_on` for `paused`, `tell` (task slugs) for `told`, `minutes` and `until` (ISO time) for `extended`, `superseded_by` (a slug, optional) for `closed`; from a site manager run also `looked`, `run`, and for an escalation `to`: `dispatcher` or `lead`; see Looking and messaging); an outcome (`id`, `outcome`: `acted`, `ignored`, or for an `extended` decision `kept` or `overran`, or for a `closed` one `stood` or `reopened`, or for a `told` one `acted`, `noise` or `collided`; a tech lead's outcome also carries `by`, `slug` and `note`; see Collisions); a delivery (`id`, `delivered`: a slug, `build_run`); a clearing (`id`, `cleared: true`); a miss (`miss`, `slug`, `firing`); a digest marker (`digest`: the slugs of the tasks the digest covered), which has no `id`.

### Across a sleep

A tick whose machine slept mid-run resumed at the wake, finished its site manager run and landed three pull requests (observed). It had not hung: it was the lander's loop, as designed, and its log lines were buffered until it ended (the stamp is now flushed). Nothing was found stuck forever, so nothing else is fixed. Every bound below is read from the code, not observed, except where it says so.

| | bound | clock | a sleep |
|---|---|---|---|
| the tick | the lock; its longest step outside the lander loop is a `run` of `WATCH_TIMEOUT` (10 m) | `time.monotonic` | the steps' timeouts count awake time: a sleep only delays them |
| the tick's lander loop | `state["health"] + HEALTH_SECONDS` (29 m) | `time.time` | the deadline passes asleep: the loop ends at its next check after the wake (observed: it landed three pull requests after waking) |
| a headless build run (`build_run`, `tech_lead_run`) | `BUILD_TIMEOUT` (90 m), `TECH_LEAD_TIMEOUT` (30 m), in `run` | `time.monotonic` | counts awake time: a sleep only delays it |
| `factory lander` by hand | no deadline: ends when nothing merged and nothing is in flight; each `wait` ends after `WATCH_INTERVAL` | `time.time` | a `wait` ends at its next check after the wake |
| the kaizen review (`review_run`) | `REVIEW_TIMEOUT` (20 m), in `run` | `time.monotonic` | counts awake time |
| the ops watch (`ops_tick`, `ops_look`) | `next_look` against now; a look's own `run` timeouts | `time.time` for when a look is due, `time.monotonic` for its steps | a look due during the sleep runs after the wake and records the looks missed |

The facts behind it, with their checks:

- On macOS `time.monotonic` does not advance while the machine sleeps: `python3 -c "import time; print(time.get_clock_info('monotonic'))"` names `mach_absolute_time()` (see the Python documentation of `time.monotonic` and `time.get_clock_info`; that `mach_absolute_time` stops during sleep is its documented behaviour, not measured here). On Linux `CLOCK_MONOTONIC` likewise excludes suspend. So a `run` timeout, which `subprocess` measures with `time.monotonic`, counts awake time.
- A `time.time()` deadline passes during the sleep.
- launchd starts no job while the machine sleeps, and one after the wake.
- The ops watch records the looks it missed (see Watching production).

After a real sleep the human checks two lines: `tail -n 3 ~/.claude/factory/watch.log` (a `watch <repository>` stamp newer than the wake) and `factory health` (no `watch:` line).

### Overruns and stopped runs
The site manager, not the dispatcher, decides when a task is over its limit or stuck. Two things reach it on every tick:
- a lead's `factory overrun '<text>'`: a firing (`overrun`, the ask as its `detail`; nothing evaluates it) that stays open until decided;
- the `run-stopped` fact (see Facts and verdicts).

Its prompt carries, besides the usual evidence, `runs` (the task's build runs, oldest first: `ts`, `outcome`, `reason`, `cost_usd`, `minutes`), `extended_minutes` (already granted), `extension_left_minutes` (what `limits.extension_minutes` still allows) and `limit_left_minutes` (whole minutes from now to the task's deadline, negative when it is past; null when the task has no start). It decides by `factory/roles/site-manager.md`, then `factory/roles/site-manager-cases.md` (the reference: the principles and dated cases for `overrun` are under that entry; no thresholds), which is appended to its system prompt.

| Criterion | Decisions it may make |
|---|---|
| `overrun` | `extended` with `minutes` within the allowance; `paused` with `waits_on` exactly `["human"]`; `escalated` to the dispatcher |
| `run-stopped` | `suppressed`; `escalated` to the lead or the dispatcher; `paused` on the human |
| `churning` | as under Merging |
| all others | as before; `extended` and a pause on the human are invalid and recorded nowhere |

The script applies a valid decision, in this order, and tells the lead and the dispatcher one line each (the model messages nobody for these):
- `extended`: logs the decision with `minutes`, `from` and `until`. `from` is the later of the time the decision is applied (when the record is written, after the site manager's run) and the task's deadline before it; `until` is `from` plus `minutes`, so an ask past the limit gives the lead the minutes from the decision and an ask before it keeps what was left. `status`, `overtime` and `nearing` then use `until` as the task's deadline (the limit shown is `until` minus the task's start). A record without `from` is an extension of the earlier rule (the minutes added to the old limit): its limit keeps that arithmetic. The lead is told `SITE MANAGER` / `extended <m> min, limit now <HH:MMZ>: <reason>`, the dispatcher the same without an action.
- `paused` on the human: declares the task `blocked`, `waits_on: ["human"]`, `paused`, role `site-manager`, with a `TaskPaused` event. `factory build` refuses (`paused: ... waits on human; factory state working once it is lifted`) until the lead declares `working`, which it does after the human's word; a run already under way is not stopped, and the release at the start of a drain skips such a row. The dispatcher gets `PAUSED:` and the lead the instruction to start no run and end its turn.
- `escalated` on an `overrun`: the model's own `ESCALATION:` message goes to the dispatcher; the lead is told `passed to the human: declare factory state blocked human and wait`.
- An `overrun` firing is cleared once decided, so a later ask is a new firing.

The line for the lead goes to its session whenever it has a process, an idle one included, and a retired one is brought back with it (see Messages); a lead that cannot be reached gets the dispatcher the line marked `(not delivered to its lead: <why>)` or `(its lead is gone: <why>)`. The firing records `told` (`lead`, `queued`, `dispatcher` or `nobody`).

An ask costs at most one run. When the run fails, there is no dispatcher, or the decision is missing or invalid (an extension beyond `limits.extension_minutes`, alone or summed with earlier ones, included), the script decides once: `escalated`, `by: watch`, reason `the site manager did not decide: <why>`, tells the lead as for an escalation and the dispatcher (else a desktop notice) `ESCALATION` / `overrun undecided, the human decides: <the ask>`.

**Outcome of an extension.** On the health pass, for each `extended` decision without an outcome: the task's `handed-over` declaration at or before `until` logs `kept`; otherwise `overran` once `until` has passed (or it was handed over later). `factory firing` does not take these. `factory firings` and `isshoni kaizen --json` count `extended`, `kept` and `overran` over the decisions with `from` only (see `isshoni.md`); those without it were scored against a limit counted from the old limit, and `factory firings` prints how many there are (`N before the limit counted from the decision, not scored`).

**Outcome of a close.** On the full pass, a `closed` decision without an outcome logs `reopened` when a later `tasks` record of that slug has another state (the close was the wrong call), else `stood` once the task's worktree is gone. `factory firings` counts them as it counts `extended`.

### Collisions
The script computes the facts (`collision`, `new-spec`: see Facts and verdicts); the site manager, reading the specs, the branches and the transcripts, decides by the principles and cases under `collision` in `site-manager-cases.md`: `told` or `suppressed` (or `escalated` to the dispatcher when two tasks build the same thing, which is the human's call). `told` carries `tell`, a non-empty list of slugs from among the open tasks the firing names, and a `reason` written for a tech lead: what the other task changed and where, and what to do. Anything else is invalid and the firing comes back. `told` is valid for these two criteria only, and the site manager messages nobody for it. File-level overlap alone is never a firing: the hot files are shared by almost every task. What changes the answer: a task started (its spec appears), a round committed (a head moved), a pull request opened (the tick snapshot), a pull request merged (the default branch moved); a merge-queue conflict stop wakes him as a `queue` event and settles `collided`.

- **Delivery.** A finding is pending for a slug when its firing is decided `told`, the slug is in `tell` and no `delivered` record names it. The next `factory build` for the slug appends each pending finding to the run's input, after the lead's note (` The site manager found (<id>): <reason>`) and logs `delivered`. A run under way is not interrupted, and no run is started for a finding: it is a forecast, where a queue conflict is real and blocks a merge. When findings arrived during a run, the lead's wake line ends ` <k> site manager finding(s) arrived during the run: the next build run gets them.`
- **Outcomes.** The build run's `findings` (`{id, outcome, note}`, for delivered ids only) are written by the script as `acted` or `noise`, `by` `tech-lead`; `noise` is not written over an existing outcome, `acted` not over `collided`. `collided` is written by the script on the full pass, beside the outcome of an extension: a `told` `collision` firing whose `queue` log holds a later conflict stop for a told slug naming one of the firing's files. `new-spec` firings carry no files and are never settled `collided`; the pair's later `collision` firing is.
- **Counts.** `factory firings` prints `told N (acted A, noise N, collided C, no outcome X, undelivered U)`. `undelivered` counts the `told` firings delivered to none of the slugs in `tell` (still pending for every one). `told` is not part of `escalated`, precision or recall. `isshoni kaizen` does not count it.
- **What the site manager may not do.** It changes no base (no command restacks a task in flight; a restack changes which pull request the human reviews) and pauses no working task for another (a pause refuses build runs and burns the lead's time limit on a guess about work not yet written). Pausing stays at the queue, where a conflict is real (`churning`). Only commits are compared: work not yet committed shows in `new-spec` alone.
- **Cost (an estimate).** On 2026-11-15, 20 tasks started (so at most 20 `new-spec` looks), 20 build runs committed and 19 pull requests merged (each can change a pair's answer, but a `collision` fires only for a pair that newly conflicts: two did that day). Firings found in one tick share one site manager run, bounded at 1.50 USD. A day like it is about 22 runs, at most 33 USD at the bound; what a run actually costs is not recorded anywhere today, so the real figure is unknown and lower. The script's own check costs no model.

### Looking and messaging
Before it decides, the site manager can look, read-only: `Read`, `Grep` and `Glob`; `factory status`, `health`, `log` and `firings`; the outbox as exactly `factory feedback` or `factory feedback --json` (any other `feedback` form can write); `factory clean --dry-run` (what would go, and why each other thing stays); the monitor's `sessions` listing; `ps` and `pgrep`; `gh pr view`, `checks` and `list`, `gh run view` and `list`; `claude agents --json --all`; and `SendMessage`. A firing about a task carries its worktree, its branch, its lead's session name (live, or retired by the harness; null when there is none), the session's pid and the paths of the lead's transcripts (a finding from the every-tick pass has no status row, so its `task` holds only the worktree, the lead and the pid), so it can tell a lead waiting on a long test from a leftover background command, or a deliberate probe from a wrong model. He reads his earlier calls from the rows' `calls`; `factory firings` and the other read commands run because the script puts its own directory first on his `PATH`.

It cannot write. It has no `Edit`, `Write`, `NotebookEdit`, `WebFetch` or `Agent` tool, `Bash` is limited to the commands above, which are read-only forms, and the run starts with `--setting-sources ""`, so it does not inherit allow rules from your user, project or local Claude Code settings: with them a `Bash(python3 *)` rule of yours let `python3 -c` write (`--restricted` would drop `Bash` altogether). Anything else is refused, not asked about. `git -C` and `git --no-pager` are refused too (a rule that allowed `git -C * log *` also let `git log --output=<file>` write), so no `git` rule exists: branch state comes from `task` (dirty, ahead, behind), from plain `git log|diff|show <task.branch>` in the repository (every worktree shares it) and from `Read` under `task.worktree`. The bounds are 30 turns, $1.50 and `WATCH_TIMEOUT` (10 minutes). A run that hits one ends without a usable answer; the `watch` log line names the reason (for example `error_max_turns`), nothing is recorded, and the undecided firings come back on the next health run. The role file tells it to decide with what it has after about 20 turns. A run that finishes usually costs a few cents (a few cents to about 11 cents, 5 to 10 turns, under 25 seconds, on staged firings).

**Closing a task.** A task that will never finish (its lead gone, its work replaced) is the site manager's to close: decision `closed`, on an `ended-undeclared` firing or as a call of its own on any entry, with `superseded_by` when another task took the work over. The script applies it through the same function as `factory close` and refuses a live task (below); a refusal is printed and not logged. It then cleans that one task (see Closed tasks) and tells the dispatcher itself, one line, with no model: `SITE MANAGER: <slug>: closed (<reason>[; superseded by <slug>]) and removed, no answer needed`, or, when `clean` kept the worktree, `ESCALATION: ... <firing id or entry> <slug>: closed (...); kept: <what would be lost>`, which the dispatcher passes to the human.

**Waking again.** A finding escalated to the dispatcher stays open. When it was acted on, or has no outcome yet, and is still true more than `RESURFACE_MINUTES` after the decision, the script clears the firing and fires it again with the detail ending `; escalated at <decided>, acted on, still true: <old reason>` (`no outcome` in place of `acted on` when none was recorded). An `ignored` or `noise` escalation is not sent again.

**Whom it messages.** The dispatcher, one message per run. A task's lead directly only when all hold: the firing is about that task and it has a lead session, live or retired; the lead can fix it alone with no decision to make (stop a leftover process it started, bring its branch up to date, answer a pull request comment); the site manager looked and the lead's transcript does not show it was already told or is acting; its `reason` is the message, one specific instruction with the evidence, which the script sends as `SITE MANAGER: <slug>: <reason>`, bringing a retired lead back (the model sends nothing to a lead itself); and the task's `calls` in its row show no earlier lead escalation for the same entry (then it goes to the dispatcher: "lead told at <time>, still there"). A lead wake costs a full context on the most expensive model, hence the rule. The script enforces the rest: a `to: lead` decision on a firing with no task or with no lead session is not recorded, so the firing comes back.

**What it logs.** A decision carries `looked` (what it inspected, one line each, self-reported), `run` (the session id of the run: its transcript is the record of what it actually did, at `~/.claude/projects/<working directory with / and . as -, e.g. -Users-me-code-repo>/<run>.jsonl`) and, for an escalation, `to` (`dispatcher` or `lead`). `factory firings --json` carries `looked`, `to` and `run`; the table shows a lead escalation as `escalated to lead`. To trace a wrong call: read the decision's `reason` and `looked`, then the transcript of `run`.

**Criteria.** Which are facts, which the queue's and which a guard: see Facts and verdicts above. Nothing is `always`.

**The live probe.** `factory/tests/live_site_manager.py` is not run by the tests (it costs money). It builds the real launch command in a scratch repository and a scratch `FACTORY_HOME`, tells the model to try 31 writes (the file tools, redirects, `tee`, `sed -i`, `git config`, `kill`, `gh pr merge`, `factory feedback decide`, a `Bash(touch *)` rule planted in the repository's settings, and others), then checks the effects itself: no file in the scratch directories created, changed or removed, the repository's `HEAD` (`git rev-parse`) and config unchanged, the test process alive, and, from shims that record the arguments of every `factory` and `gh` call, no `factory state`, `firing`, `feedback set|add|decide`, `gh pr merge|comment` or `gh api` call (the `gh` shim touches no pull request); and that `ps`, `factory log` and `Read` of a file outside the working directory do work. It also records, without requiring it, whether `tail` of a file outside the working directory is allowed (it is not). It prints a line per attempt and the cost (about $0.10), and exits nonzero on any effect. Claude Code ignores a project's allow rules in a directory you have not trusted, which would make the planted rule prove nothing, so run it as `PROBE_CWD=<a directory Claude Code trusts> python3 factory/tests/live_site_manager.py` (`--control` runs it without the isolation flag and must write). It refuses a `FACTORY_HOME` under the real `~/.claude` and fails if the real store's logs name its scratch directory. Run it by hand after changing the tool list, the flags or the Claude Code version.

**The build foreground proof.** `factory/tests/live_build_foreground.py` (`start <n> <dir>`, then `wait <dir>`; paid, never run by the tests) runs real `factory build` runs on a trivial task in scratch repositories and a scratch `FACTORY_HOME`, and passes only if each run has an answer (not `ended without an answer`), started at least two subagents and recorded no `Stop` event with background tasks; a run not `built` must show `denied` in its hand-over file (the known landing denial of `factory state working`), printed as `stopped_by=`. Build runs that end early are counted from `techlead-YYYY-MM.jsonl`: `kind` `build`, `outcome` `stopped`, and `reason` `ended without an answer` for the no-answer form.

### Digest
A digest answers where a task's money goes. It is a set of findings computed by a script from `isshoni anatomy --json` (the monitor's per-task cost anatomy), then worded and filtered by the same headless run as `watch` (`Job: digest`), which messages the dispatcher (first line `DIGEST: <repository directory name>`, then a `Tasks:` line naming the tasks landed since the last digest, then one line per finding it kept) or sends nothing. A finding is a criterion with `"job": "digest"` in `criteria.json`: it is logged as an ordinary firing, decided by the site manager, closed by the dispatcher with `factory firing <id> acted|ignored` and counted by `firings`. A finding describes one window, not a lasting condition, so the digest marks its firings cleared when it ends, and then writes the marker.

- **Window.** The tasks of this repository that have a merged pull request (`worktree-<slug>`) and a cost above 0, oldest merge first. The current ones merged after the last digest's marker (with no digest yet, the newest 5); the baseline is every one before them. With fewer than 5 in the baseline, or none current, a finding is `not evaluated`.
- **Cadence.** `watch` makes a digest when the last marker is at least 24 hours old (or there is none), the repository has `digest` entries, and at least 5 tasks have landed since the last one. So: at most one a day, none until 5 more have landed. The anatomy only moves when tasks land, a median needs 5 of them (the number the cost criteria use), and the reader's attention is the cost being managed. A tick inside the 24 hours costs nothing; one past them runs `isshoni anatomy --json` once (about 10 seconds on the author's machine) to count what landed, and a digest that is sent costs one run of the site manager's model (on Opus, its default, about twice what Sonnet costs; the $0.15 above was Sonnet). It does nothing when the tick has no dispatcher or fired `dispatcher-missing`. Without `paths.monitor` in the settings, or when the monitor fails, it prints one `digest skipped: <why>` line per due tick and records nothing. A marker is written when at least one finding was evaluated, even if none fired. If the run is unusable, no marker is written, the firings are cleared, the command exits 1 and the next due tick tries again.
- **`factory digest`** makes one now whatever the cadence (with no dispatcher to address it is skipped, printing the reason), and `--dry-run` prints the findings and the `not evaluated` list as `health --json` does, logging nothing and starting no model.

| Finding | Threshold | Fires when |
|---|---|---|
| `mix-shift` | 5 (points) | the share of total cost of one token class (`input`, `output`, `cache_write_5m`, `cache_write_1h`, `cache_read`), current against baseline, moved by at least that many points; the class that moved most |
| `dearest-task` | 1.5 (times) | the dearest current task cost more than that many times the baseline's median task; names the role that explains most of it |
| `role-growing` | 20 (percent) | a role in at least 3 current and 3 baseline tasks has a median context per call, or median number of own tool calls per task, that much above the baseline's |
| `version-shift` | 20 (percent) | at least 3 current tasks ran a plugin version no baseline task ran, and their median task cost, the lead's share of cost or the lead's median context moved by more than that, up or down |
| `lead-authoring` | 50 (percent) | the lead made a product-code or test write (`written.product` or `written.tests` calls above 0 in its anatomy block) in that percent or more of the current tasks; names them and compares with the baseline. Not evaluated with a monitor that reports no `written` |

To turn the digest off, delete the five `"job": "digest"` lines of `criteria.json`, or one of them to drop that finding. Without `paths.monitor` in the settings it is skipped. A sixth finding is one line in `criteria.json`, one function and one entry in `CRITERIA`.

## Merging
The lander is a script loop in `factory/lib/factory_core.py` (`drain`), with no model: it takes the pull requests that are ready to the default branch in order, and brings each up to date, when its turn comes, with a plain merge of the default branch. Whatever does not merge cleanly or is red goes back to a tech lead (see Tech lead), and to its lead only when there is none: the lander wants the pull requests green and judges nothing else. Two scripts:
- **`factory merge`** merges pull requests with no model. It merges only what is mechanical and stops at the first thing that is not. `factory merge <number>...` and `--all` (every open pull request whose task is handed over; the others print `#N skipped: <why>`; with none left, `nothing to merge`) are the caller vouching for the human's word. `--approved` makes GitHub's own records the gate: each pull request is merged only when it holds a valid approval, read at that moment. `--approved --all` merges every handed-over pull request that is approved and prints `#N skipped: <why>` (not approved, or a stale approval) for the others; only an approved one that then fails its merge stops the run. One command merges at most one pull request, so the next approved one stops `behind` (see the `behind` blocker). The lander calls the same `merge_one` for every merge.
- **`factory lander [<number>...]`** runs the loop in the foreground, with no deadline, and exits 0 when nothing among the pull requests it worked on is still stopped, else 1. Numbers are recorded as the human's word for an hour (`WORD_SECONDS`) first; each must be an open pull request (else exit 2, nothing recorded). One loop per repository at a time (`fcntl.flock` on `lander-<repository>-<8 hex>.lock` in `~/.claude/factory/`); when it is held, the command prints `a lander run is already going: it takes everything that is ready` (with numbers: ` (#65, #66 are now in its queue)`) and exits 0: the running loop reads the word on its next full pass. With an empty queue it prints `nothing ready`. **`factory lander --window <minutes>`** (1 to 720) records the human's word for every handed-over pull request, prints `merge window open until <UTC time>: ...` and returns: the next tick starts the loop. `--window 0` prints `merge window closed`. `--window` with numbers is exit 2.
- **The tick** (see Site manager) runs the same loop last, when a task is handed over or paused, or a word stands, until health is next due (`state["health"] + HEALTH_SECONDS`), running the whole tick again every 2 minutes meanwhile; the next tick continues, since everything the loop knows is on GitHub or in `lander.json`.

**The queue** is computed again on every full pass from a fresh `snapshot` (one `gh pr list`), by number:
- *Approved on GitHub* (gate: `merge_one` with `permission={}`): has an approving review or an `lgtm` (only a prefilter; `merge_one` decides), and its task is declared handed-over.
- *On the human's word* (gate: `permission=None`, as `factory merge <n>`): while the window is open, every open pull request whose task is handed over (drafts included); and each number given to `factory lander <n>...` whose word has not expired, whatever its task's state (a `handover` stop is reported).
- A pull request whose base branch is the head of another open pull request waits for it, silently. Once its base has merged it is updated like any other, its base is changed to the default branch in one pass, and it is merged in the next.

**The word** is `word-<repository>-<8 hex>.json` in `~/.claude/factory/`: `{"all": <epoch until>, "prs": {"<n>": <epoch until>}}`, written whole and atomically and only by `factory lander` (expired entries are dropped on each write and ignored on read). It is not in `settings`: the settings file is one per factory home (all repositories) and is configuration, while a window is per repository, transient and must expire. To close a window: `factory lander --window 0`. The word lets a pull request merge without GitHub's approval for its lifetime: whoever may run `factory lander` holds that power, as with `factory merge <n>`.

**The loop** (`drain(repo, fallback, tick=False, deadline=None)`) repeats full passes. A pass takes the snapshot (when it cannot be read, it prints `lander: <why>` and the loop ends; the next tick tries again), builds the picture of `merge_one` once (`gather`, `tasks`), and calls `merge_one(p, pr, False, False, permission)` for each queued pull request:
- *Merged*: prints `#N merged <url>`, runs `clean` and fast-forwards the main checkout as `factory merge` does, and starts a new full pass at once (the default branch moved).
- *`behind` or `conflict`*: first, read-only, `git merge-tree --write-tree --name-only <remote>/<default> <head>`: a conflict is a stop `conflict` (`conflicts with <default> in <files>`) at once, with no update and no CI run, whether or not another pull request is in flight. Otherwise, when no pull request is in flight and none was updated in this pass, it is updated (`update_branch`, below); else it waits for its turn.
- *Any other `(kind, reason)`* is a stop.
- *A handed-over pull request in no queue* (unapproved, no window) is only checked, read-only, for a conflict with the default branch (`git merge-tree`, after the fetch): files make the stop `conflict`, which goes back (to a tech lead, else its lead) like any other; nothing else is checked for it (no approval, no checks, no update, no CI run). Once per head by construction: the sent-back task is no longer handed over. GitHub's `mergeable` is not read for this.

**One update per merge, no cascade.** After a merge exactly one pull request is brought up to date: the next in order that merges cleanly. Every other waiting pull request is left as it is, however far behind, until its turn: nine waiting pull requests cost nine update pushes and nine CI runs, not forty-five. A second update for the same merge happens only when the one in flight failed (red, sent back) or left the queue. While one waits for CI, every other queued pull request is still evaluated on each pass, so a stop that does not depend on the tip (a red check, not handed over, no approval, a bad base, a conflict) is reported at once, and one that is already up to date and green merges ahead of its number. Updating the others during the wait would be wasted: each merge moves the default branch again, so it would be redone, and the merge commit GitHub will create cannot be known in advance, so nothing can be tested against it without breaking the invariant.

**`level(repo, task)`** fast-forwards the task's worktree to its own remote branch (`git fetch`, `git merge --ff-only <remote>/<branch>`, no push); the lead may be running, the worktree dirty, or the two diverged are reasons. A pass calls it once when `merge_one` says `handover` because the worktree's head is not the pull request's head (someone pressed "Update branch" on GitHub, or pushed from elsewhere) and asks `merge_one` again; a reason leaves the quiet `handover` stop standing.

**`update_branch(repo, task)`** is a plain merge in the task's worktree: it starts with `level` (its reason is a `handover` stop, nothing touched). Then `git merge --no-edit <remote>/<default>`; on a conflict the files are named (`git diff --name-only --diff-filter=U`), the merge is aborted and it is a stop `conflict`; clean, `git push <remote> HEAD:<branch>` (a refusal is a stop `other` with git's line; the merge commit is left in the worktree). No local tests, no overlap check, no comment on the pull request, no model. It prints `#N brought up to date, waiting for its checks`. If the same pull request is `behind` again while `<remote>/<default>` is at the tip it was last updated against (kept in memory for the run), it is a stop `other`, `still behind after the update`.

**Stops** go through one table (`STOP_POLICY`, `stop_policy`): the patience (how long the same stop, by number, head and kind, must last before it is reported), whether it is in flight (inside its patience it keeps the loop polling and holds back other updates) and who is told:

| stop | patience | in flight | told |
|---|---|---|---|
| `pending` | 1800 s | yes | dispatcher |
| `ci`, not "failed or cancelled checks" (no checks yet, unreadable) | 180 s | yes | dispatcher |
| `ci`, failed or cancelled checks | 0 | no | lead |
| `handover` (incl. a busy lead or a dirty worktree at the update) | 600 s | no | dispatcher |
| `conflict` | 0 | no | lead |
| `refused` | 1 s | no | dispatcher |
| the rest (`unapproved`, `stale`, `head-time`, `base`, `merge`, `fork`, `stack`, `other`) | 0 | no | dispatcher |

**Churning tasks.** A task the queue already sent back (`CHURN_SEND_BACKS = 1`, the rows `send_back` writes) whose pull request conflicts again, while another open task (`working` or `handed-over`, its branch not yet in the default branch) changes one of the conflicting files, would only be sent back again at the next merge. The `churning` criterion (`judgment`, every tick) carries that evidence (`churn`). The site manager decides `paused` (with `waits_on`: slugs from the firing), `suppressed` (the send-back proceeds) or `escalated`; `paused` is counted apart in `factory firings` ("paused N") and takes no outcome. The queue holds such a conflict in `waiting` for up to `CHURN_PATIENCE = 300` s until a `churning` decision exists since the task's last hand-over. Then the send-back runs as usual and its holder pauses its own task: the tech lead start (`cmd_tech_lead`) declares `blocked` with `waits_on` (a list) and `"paused": true`, writes a `TaskPaused` event and a tech lead record with outcome `paused`, and runs no model; without a tech lead the line to the lead says to run `factory state blocked <slugs> --paused`. `factory status` shows `paused` (`since`, `waits_on`) and `prioritized` (`since`) in each `--json` row and in the FLAGS column. At the start of every drain, for each row with `paused` true none of whose waited tasks is open any more (a task that vanished counts as landed), the script, once, records the task in `lander.json` `prioritized` (`TaskPrioritized` event) and starts a tech lead run (else tells the lead) to merge the default branch in and land. While a task is prioritized (at most `RELEASE_HOLD_MINUTES = 24`: on 2026-11-14 a send-back took at most 13.0 minutes to the next hand-over and a hand-over at most 10.6 to its merge) the queue serves only its pull request. The priority ends, with a `TaskPrioritizedEnd` event, when it merges (`merged`), is sent back for a stop other than a conflict (`sent-back`), the task leaves the open states (`gone`) or the hold runs out (`expired`; the dispatcher gets one line). `blocked-unanswered` fires for a pause like any block and names what it waits for; the pause is never lifted by it. A pause is released once, whatever happens to the hold (the row must be newer than the task's last `TaskPrioritized` event). `factory pauses` counts them. Known limit: the site manager decides between drains (the drain holds the watch lock), so when a drain is busy merging or waiting on checks the `CHURN_PATIENCE` 300 s can run out before a decision and the task is sent back as before.

A failed-checks stop first asks the function behind `factory rerun` (below) once: a re-run that started makes it the polling `pending`, otherwise its `no rerun` text joins the evidence for the lead. A stop is reported once per (number, head, kind): `lander.json` keeps `waiting` (`{"<n>": {head, kind, since}}`) for stops inside their patience, so `lgtm-blocked` does not fire on them, `health` (when health last ran), and `stopped` (`{"<n>": {head, kind, text, ts}}`) for the reported ones; records of pull requests that are no longer open, or whose stop is gone or changed, are dropped. A `handover` stop on a pull request already sent back at the same head (its task is working) stays quiet. Reporting prints `#N stopped <kind>: <one line> (told tech lead|lead|dispatcher|human)` and fires `lgtm-blocked` (subject `#<n>/<kind>`), then:
- *told tech lead* (the pull request goes back): the task is declared `working` and the pull request goes back to draft (so it leaves the queue until it is handed over again), then a tech lead run starts for it and nobody is messaged (see Tech lead).
- *told lead* (the fallback: no spec file, no worktree, a run already going, red checks at the head a tech lead resolved, or the process could not start; the reason is the `unstarted` record of the `techlead` log): the same, then one line is sent to the lead's session: `LANDER: <slug>: #N went back to you: <evidence>. Fix it on your branch (merge <remote>/<default> in), re-review what you change, and hand over again: it is then merged by itself.` The evidence is one line, `it conflicts with <default> in <files>` or `red checks: <name> <link>, ...` (from `gh pr checks <n> --json name,bucket,link`). A retired lead is brought back with the line (see Messages); one that could not be reached: the dispatcher gets `LANDER: <slug> (<why>): ...`, `<why>` as there; no live dispatcher: the human is notified.
- *told dispatcher*: `LANDER: #N stopped <kind>: <one line>`, else the human is notified.
- When a session was told, the firing is logged as escalated (`by` `lander`); `notify` logs its own. Lines go through `courier`, the one way into a live session.

**Red checks that are not the branch's (`not-ours`).** A failed-checks stop that no re-run ended (`rerun_line` refused) is judged once by `not_ours`, from reads only; anything unread, unnamed or untrue sends the pull request back as above. It is held when every failed check is an Actions run whose log names a failing test, no file defining one is changed by the branch (`git diff --name-only <fork> <head>`, exact file), and each of those files also defines a test that failed in attempt 1 of a run on an independent head within `NOT_OURS_HOURS = 24` (from `gh run list --limit 50`, failed or re-run runs of other branches, the newest `NOT_OURS_RUNS = 5`; independent: the merge-base with the branch is an ancestor of `<remote>/<default>`). A failure that also happens without the branch is the evidence; a rule on files alone would hold every real regression in an untouched test. The stop is `not-ours` (patience 0, told the dispatcher once per head, a `stopped` row with `tests` and `checks`, one pull request comment `Merge queue: held, not sent back: <line>`). Held means `lander.json` `stopped[<n>].kind` is `not-ours` and `<n>` is not in `unblocked`: the pull request stays ready and approved, goes to no lead or tech lead, and is not updated while its checks stay red (no log is fetched again). Pending or green checks (a re-run) end the hold; a conflict is sent back as usual. Two ways out: a merged pull request whose body has the line `Unblocks: #<n>[, #<m>]` (the loop reads it when something merges), or `factory unblock <n> [--by <text>]` (default `by`: `word`), which prints `#N unblocked: ...` and exits 1 for a pull request that is not open. Both record `unblocked[<n>]` (pruned when the pull request is no longer open) and an `unblocked` row; the queue then updates the branch as for any behind pull request, and red again goes back to its task, never held twice. A pull request named by a fix but not yet approved gets the entry and is updated when it enters the line. The site manager owns held pull requests: the `red-waiting` fact (full pass) fires for one held `HOLD_GRACE_MINUTES = 30` that no open pull request's `Unblocks:` line names, and the watch body carries `waiting` (`pr`, `slug`, `since`, `tests`, `named_by`, `null` when the list could not be read); `ci-red-handover` leaves them out, and it may run `factory unblock`. Limits: the first branch to meet a new flake has no evidence and is sent back as above; an unapproved pull request is not held and not updated until approved.

After a pass: if something merged, the next pass starts at once. Else, with something in flight, the loop waits: every `POLL` (20 s) it asks `checks_stop` for the in-flight pull requests only (one `gh` call each) until one is no longer pending or `WATCH_INTERVAL` has passed, then a full pass. Else it ends: what is stopped is retried by the next tick's pass, which is how a stop is "retried by itself" (the lead's turn ended, the check went green, the lead handed over again, a fresh approval). In a tick, the loop also ends at its deadline, and every `WATCH_INTERVAL` it runs the cheap part (comments, draft sync) on its own snapshot, so a long loop does not starve them.

**Observe it** in `~/.claude/factory/watch.log` (tick) or the terminal (by hand): `#N merged <url>`, `#N brought up to date, waiting for its checks`, `#N stopped <kind>: <line> (told ...)`, `lander: <why>` when the snapshot or the sessions cannot be read. **Stop it** by closing the window (`factory lander --window 0`); to turn merging on an approval off, remove the schedule (while a dispatcher session lives, its next prompt installs it again, so there is no lasting off switch short of ending the dispatcher).

**Limits.** A stopped pull request is retried every tick (2 minutes), not instantly. While the loop runs inside a tick, health is late by at most one pass. A clean textual merge can still break the combination: the checks on the updated head are the only guard, and a red one goes back (to a tech lead, else the lead). `factory land` still exists and is no longer used for merging. A by-hand loop and the tick's cheap part run side by side. A merge on the human's word (a window, or numbers) cannot pass a branch protection that requires an approving review: GitHub refuses the merge (a `merge` stop with its message, told to the dispatcher), so a window is for repositories whose protection does not require a review. For the lander's own update pushes to keep an approval, the protection must not dismiss stale reviews nor require approval of the most recent push (`approved_heads` holds that line instead). A pull request that is red and behind is updated once when its turn comes (one CI run) before it is sent back.

**The approval.** Two kinds count:
  - *An approving review.* Per login, the newest review that is not comment-only (`COMMENTED`, `PENDING`) is its verdict, so a later `CHANGES_REQUESTED` or a dismissal withdraws an approval and a later comment-only review does not. An `APPROVED` verdict counts when it is on one of the pull request's approved heads (below); one on another commit is a `stale` blocker unless GitHub rebased the pull request without changing its commits' diffs (*An approval survives a rebase by GitHub*, below). Of several approvals, one on an approved head is preferred, then the newest.
  - *An `lgtm` comment.* Its whole body, trimmed, in any case, is `lgtm`, and it was created after the branch last moved off the approved heads (GitHub's activity feed for the branch, 30 entries: the oldest of the consecutive newest pushes that left it on an approved head; the newest must be the head). Review bodies do not count. An `lgtm` can approve a pull request whose review is on an older commit; the `lgtm` rules then decide. An `lgtm` older than a push also holds when the pull request's commits at the head the `lgtm` saw (the newest push before it) and now are the same changes (below).
- **A draft is queued like any other pull request**, so the tick's draft sync cannot take an in-flight pull request out of the loop: under `--approved` hand-over plus green checks on an approved, up-to-date head is, and a draft that passes them is marked ready (`gh pr ready`) and merged, as with the human's word. The tick's draft sync can put a pull request back to draft while its checks are pending; that does not stop its merge.
- **Who may approve**, for both: a login whose GitHub `user.type` is `User` (a bot never), with `admin` or `write` permission on the repository, and not the pull request's author. The exception: an author's `lgtm` counts while `merging.lgtm_from_author` is `true` (the default); an author's review never does.
- **An approval survives a clean merge of the default branch.** `update_branch` brings a pull request up to date by pushing a merge of the default branch, which moves the head after the approval. `approved_heads` starts at the head (after the `git fetch` made for that pull request), and while a commit has exactly two parents, its second parent is an ancestor of `<remote>/<default>` (the pull request's own base is not asked: it can be retargeted after the approval), and `git merge-tree --write-tree` of the parents prints the commit's own tree, it steps to the first parent. The commits visited are the heads an approval may sit on. Any other commit on top (a conflict resolution, a new commit) makes the approval stale: the human approves again. If git cannot answer, the set is just the head.
- **An approval survives a rebase by GitHub.** When a lower member of a stack merges, GitHub rebases the members above it: the head changes, the review's `commit_id` stays on the old head, and an `lgtm` is older than the force push. `same_diff` compares the pull request's own commits (`pulls/<n>/commits`, N of them, the last must be the head) at the approved commit and at the head: from the newest, each commit is read with `gh api commits/<sha>` and its change is the list of `(filename, status, previous_filename, patch)` with every hunk header line (`@@ ...`) cut down to `@@`, since the line numbers and the heading after them depend on the base. The changes must be equal pair by pair, then the walk goes to the first parent of both. Then the base the approved commits sat on (the first parent of the Nth of them) must be an ancestor of `<remote>/<default>` (local `git merge-base --is-ancestor`, after the `git fetch` of that pull request): without it a dropped oldest commit would pass, since the commits left would still match one by one. For a review, the approved commit is its `commit_id`; for an `lgtm`, it is the head left by the newest push before the `lgtm`'s `created_at` (strictly older: a push in the same second cannot be shown to be earlier). It is tried only when the approval is not already on an approved head, and its result is a fresh approval needed unless the changes are equal. Every one of these is a `stale` stop and never an approval; each says the approved commit, the head now and what was found, except the two `lgtm` stops before any commit is known (no push older than the `lgtm`, a push with no readable time), which name only the head: GitHub cannot list the commits; the pull request has 0 or more than 20 commits; the listed head is not the pull request's head; a commit cannot be read; a walked commit is a merge or has no parent; a file of a commit has no patch (binary, too large, a pure rename, a mode change) or a commit lists 300 files or more; a commit differs, is added, reordered or squashed; the approved base is not on the default branch, or the fetch failed; the `lgtm` has no push older than itself in the 30 entries read, or a push in GitHub's log has no readable time. Limit: a merge of the default branch on top of a rebased head is a head with a merge commit, so it needs a fresh approval. Limit: a stack member above a member that GitHub rebased before it merged needs a fresh approval, because the commits it was approved on sat on the old, rewritten head of the lower member, which is on no branch; likewise when the lower member was merged by squash or rebase. What is rescued: a pull request based on the default branch that GitHub rebased, and a member whose lower neighbour merged unrewritten. Cost: at most 1 + 2N `gh api` calls per `same_diff`, run once for a stale review and once for a stale `lgtm`, so at most 2(1 + 2N) when a pull request has both and both are stale; only when its approval is not on an approved head, and nothing is cached between passes (a stack of three one-commit members, all rebased, is 9 calls a pass with a review alone; once approved on the head, 0). Not observed: what GitHub answers after an agent pushes on top of an approved member, and how GitHub rewrites a member with several commits; the tests show the rule's behaviour there with made-up commits only.

**Nothing technical tells the human's approval from one an agent posts when they share a login.** What is decided, per identity of the pull request's author:
- *The factory's App* (see Identity): the lead's pull requests are authored by the bot, so your approving review counts (GitHub does not let you approve your own pull request, which is why it could not with one account) and so does your `lgtm` (you are not the author). Nothing the bot posts counts: its comments and reviews have `user.type` `Bot`. A mechanism, and `merging.lgtm_from_author` has no effect on it.
- *A second account of its own* (a regular user with write access): it looks like the human. Set `merging.lgtm_from_author = false` in the settings once the factory has such an account; its `lgtm` stops counting while another user's still does.
- *Without an identity* (your own `gh` login, the fallback): `merging.lgtm_from_author` stays `true`, and the `lgtm` from the author rests on a rule written into every role file: no agent ever posts one, and none ever approves a pull request.

Per pull request, bottom-up through a stack (a pull request based on another selected one goes after it). Each check that fails is a blocker with a kind:

| Kind | Blocker |
|---|---|
| `fork` | its head is in another repository |
| `handover` | no task worktree has its head branch; or the task is not in phase `review`; or the worktree's head is not the pull request's head; or the task on its head branch recorded another pull request number (`task <slug> recorded #<n> as its pull request, not this one (opened by <login>)`) |
| `behind` | the invariant: a pull request is merged only when its head already contains the current tip of the default branch (`git fetch` for each pull request, never one fetch shared by a command) and its checks are green on exactly that head; otherwise `<remote>/<default branch>`'s tip is not an ancestor of its head. Both modes; in `--approved --all` a stop like any other. One command merges one pull request: whatever follows it is `behind` (not attempted, once a stop ends the run; in a dry run every pull request after the first that would merge prints `would stop`), because the merge moved the default branch. Several ready pull requests are therefore merged one at a time, each brought up to date by the lander when its turn comes and re-checked by CI first. A stacked pull request whose base merged is `behind` too until it holds the merge commit. If the repository later requires "branch up to date" in branch protection, GitHub enforces the same invariant and a refused merge (a `merge` stop with gh's message) is retried the same way. If git cannot answer it is `pending`. A stack's bottom is not held to it: GitHub decides at the call, and the script rebases the stack when GitHub refuses it as behind |
| `base` | its base is neither the default branch nor the head of a pull request merged into it |
| `ci` | no checks, a failed or cancelled check, or no passed check |
| `pending` | a check is still running; GitHub has not computed mergeability after 5 asks 3 seconds apart; the base's pull request cannot be read; `gh pr merge` was refused while a check had started again on the head (`GitHub refused the merge while a check ran again on this head: <name> (started <time>)`); the pass that changed its base from a merged branch to the default branch ended there (`its base was changed to <default> in this pass: it merges on the next one`) |
| `conflict` | it conflicts with its base (the lander's loop sends it back: to a tech lead, else its lead) |
| `unapproved` | (`--approved` only) no valid approval on GitHub |
| `stale` | the head changed after the approval (a review on a commit that is not an approved head, or an `lgtm` older than the last change off the approved heads) and the commits' diffs are not shown to be the same: a fresh one is needed; the reason names the approved commit, the head now and what was found |
| `head-time` | (`lgtm` only) the activity feed does not name the pull request's head, so when it changed cannot be told |
| `merge` | a `gh` step failed; when `gh pr merge` was refused and GitHub's `reviewDecision` is `REVIEW_REQUIRED` or `CHANGES_REQUESTED`, the line starts `GitHub does not allow the merge yet: <what> (reviewDecision <value>, mergeStateStatus <value>); `, `<what>` being `a review is still required` or `a reviewer requested changes`, then gh's own line; `, mergeStateStatus <value>` only when GitHub gives one |
| `refused` | `gh pr merge` was refused, no review requirement and no running check explains it: `GitHub refused the merge and nothing it shows explains why (reviewDecision <value>, mergeStateStatus <value>, checks passed or unreadable)`, `none` for an empty field, then gh's own line; patience 1 s, so the first one of a head waits for the next pass and a second at the same head is told once (`LANDER: #N stopped refused: ...`) |
| `stack` | a stack's bottom: its stack would be rebased first (dry run), the stack's base chain or `gh stack view` does not match its members, a rebase conflict, a diff that changed in the rebase, a remote head that moved, or a `gh stack` failure; the text starts `stack member #<m>: ` for a member other than the bottom (see GitHub stacks) |

Then it dissolves the GitHub stack the pull request is in (see Stacked tasks), changes the base of the pull request to the default branch when its base is a merged one (`gh pr edit --base`) and ends that pass with the `pending` stop `its base was changed to <default> in this pass: it merges on the next one`; the next pass reads the pull request again, checks its checks again, marks a draft ready (`gh pr ready`; only a fallback, `watch` has normally done it, see below) and merges with a merge commit, pinned to the head it checked (`gh pr merge --merge --match-head-commit`). The base change gets its own pass because it can restart a required check that listens to `edited`, and GitHub then refuses a merge made in the same pass (not reproduced in this repository, whose workflow does not listen to it). The wait tells nobody: a `waiting` record in `lander.json` within the 1800 s patience of `pending`, and no line in the log, in `factory status`, or to a lead, the dispatcher or the human. In a lander run the next pass comes after one `POLL` (20 s) when its checks are green, else when the restarted check ends; when the run ends first, the next tick's pass (`WATCH_INTERVAL`, 120 s). Merge commits keep branches stacked on it valid; squash would not. After any merge it runs `clean` and fast-forwards the main checkout (`git pull --ff-only <remote> <default>`) when it is on the default branch; a failure prints `main checkout not updated: <why>` and does not fail the merge (`clean` does not pull it).

Nothing is read before the first `gh pr merge`: GitHub alone knows all its requirements. Only after a refused merge `merge_one` reads `reviewDecision` and `mergeStateStatus` once, and its checks once when no review requirement is named, to put the refusal in words. The lander asks for the merge again on every pass of its loop (one refused call and one or two reads per pass), so the merge happens within one tick of the requirement being met, with no word to the factory. The dispatcher is told once per head (`LANDER: #N stopped merge: GitHub does not allow the merge yet: ...`), and `factory status` shows the row as `waiting on GitHub: <slug> <url>: <what is required>` instead of `waiting on the human`. Plain `factory merge <n>` prints the same reason and retries nothing. A required check can start again on the same head, and GitHub may refuse the merge made seconds later without naming it: when that run is already visible, the refusal is a `pending` stop that names the check, which the loop watches; otherwise `refused`, whose first occurrence at a head waits for the next pass (the merge is asked again) and whose second is told.

The draft flag of a task's pull request follows its recorded state: ready for review exactly when the task is handed over, its head is the pull request's head, and its checks pass (the test `merge` uses) or the pull request is held (`not-ours`: its checks are not read, and a held draft is made ready), otherwise a draft. `factory state working|blocked` and a landing that declares `working` put it back to draft at once (`gh pr ready --undo`, result ignored); every `watch` tick (the 2-minute one) sets the rest: a handed-over pull request turns ready up to one tick after its checks go green, and a ready one whose head moved or whose checks fail goes back to draft. The first tick after this rule existed sets every open task pull request from its recorded state (the migration). Pull requests from forks and without a task, and tasks that are settled or merged, are left alone. `status` agrees: a `review` row whose pull request is a draft shows `pr_draft` and prints `waiting on checks`, not `waiting on the human`, and the dashboard does not list it as waiting.

- `merge` prints `#N merged <url>`, or `#N stopped: <reason>` and `#M not attempted` for the rest; exit 0 when everything merged, 1 on a stop or a failed step, 2 for a number that is not an open pull request. `--dry-run` changes nothing, checks every pull request (the approval too) as if the earlier ones had merged, and prints `#N would merge` or `#N would stop: <reason>`; mergeability of a pull request whose base would first be changed is not checked, and its line reads `#N would merge (its base is changed to <default> first; it merges on the pass after that)`. A real `merge` of such a pull request changes its base, prints `#N stopped: its base was changed to <default> in this pass: it merges on the next one` and exits 1; run again, it merges.
- **`factory rerun <number>`** (the loop calls the same function, `rerun_line`, in process, once per pass for every failed-checks stop of a pull request in its queue; by hand it is the command). It is the only re-run the factory makes, and the decision is the script's, never a model's. The script decides; it prints one line, `#N rerun: <check>: <Test> (<file>) is outside what the branch changes and <check> is green on <base>; attempt 2 started` (exit 0) or `#N no rerun: <why>` (exit 1). A `rerun` line (exit 0) makes the pull request in flight (the stop becomes `pending` with that line; the loop watches the checks again). Any `no rerun` line is appended to the evidence that goes back to the lead; so a test that fails again after its re-run ends at `already re-run once; looks like a flake: ...`, and a pull request with only cancelled checks at `no failed check`. A command that fails (`git`, `gh`) is a `no rerun: <command> failed: <error>`, never a re-run on missing evidence. With several failed runs every run is decided first, then they are re-run one by one; a refusal after one started is a `rerun` line that also carries it. The steps, each a stop with its own reason: (0) any check still `pending` stops with `checks are still running` (GitHub refuses to re-run an incomplete run); (1) the pull request is open and has a check in bucket `fail` (`gh pr checks --json name,bucket,link`) whose link is a GitHub Actions run (`/actions/runs/<id>/`); (2) the failing tests are named from `gh run view <id> --log-failed` after the log's `job<TAB>step<TAB>timestamp` prefix: Go `--- FAIL: Test...` (a subtest names its parent) and unittest `FAIL: test... (` or `ERROR: test... (`; none named stops; (3) after a fetch, `git grep` finds where each test is defined on `<remote>/<head branch>`; a test is the task's own when a file defining it, or a file in the same directory, is changed by the branch (`git diff --name-only <merge-base with the base> <head>`), and the first own test stops with `<Test> (<file>) is in what the branch changes` (the file named is the one that matched the branch's changes); (4) each failed check has a check run of the same name with conclusion `success` on the base's tip (`gh api repos/{owner}/{repo}/commits/<sha>/check-runs`); (5) `gh run view <id> --json attempt` is 1, else `already re-run once; looks like a flake: ...`; (6) `gh run rerun <id> --failed`, and any refusal prints `the App may not re-run checks; looks like a flake: <Test> (<file>). From your own terminal: gh run rerun <id> --failed (<refusal>)`; (7) a comment on the pull request says what was re-run and why. The words `looks like a flake` appear only when steps 1 to 4 passed: the dispatcher opens a task for the named test from them. What it does not catch: a flake the task itself introduced in a test far from its files passes on the one re-run; a real failure in a test far from the task's files costs one wasted CI cycle and then stops; a failure with no test name (a build error, the walk scripts) is never re-run.
  On a pull request held at its current head `factory rerun` skips the three flake conditions (3, 4 and 5: in what the branch changes, green on base, already re-run once; the queue's own in-process call never does), so the App-refusal line says `looks like a flake` with them skipped, the success line is `#N rerun: <checks>: attempt 2 started on the human's word`, and it writes a `rerun` row with `by: "word"` and comments `Re-ran the failed jobs of <checks> on the human's word (by factory rerun).`. Only the dispatcher on the human's word, or the human, runs it: not the tech lead or the site manager.
- **Moving to the new behaviour.** The installed schedule keeps its old interval until it is installed again: `factory schedule install` from the main checkout (or a dispatcher's next start or resume, which replaces the job). Installing the schedule again while a loop runs kills it; the next tick continues.
- `clean` keeps the worktree the running plugin lives in: leads started by it load their plugin from there.

## Comments on a pull request
Each `watch` tick notices new reviews, plain comments and (for a pull request with a new review) comments on lines, on the open pull requests of tasks, and forwards what **the human** wrote to the task's lead, verbatim.
- **The human** is a `User` account (an App with write access is not one) whose association is `OWNER`, `MEMBER` or `COLLABORATOR` and whose repository permission is `admin` or `write`, from GitHub's records, never from comment text. A bot, and anyone else, is logged and not forwarded; third-party tools and other authors are not handled yet. An `APPROVED` review, an `lgtm` comment (the merge path owns them) and a `COMMENTED` review with no body (its line comments are the content) are logged, not forwarded.
- **Forwarding**: one batch file per task per tick, `~/.claude/factory/comments/<slug>-<UTC time>.md`, the comments quoted in fenced blocks, marked as data. A headless run on `models.courier` (Haiku by default; `claude -p`, about $0.01 and 3 s; it sees the recipient's name and one line, carried as marked data, never comment text) sends `PR COMMENTS: <slug>: <k> new from the human on #<n>: read <path>` to the lead's session. A lead the harness retired is brought back with the line (see Messages). When the lead cannot be reached, the dispatcher gets it once, as `PR COMMENTS: <slug> (not delivered to its lead: <why>): ...` or `(its lead is gone: <why>)`; failing that, a desktop notice names the file. The batch file is the durable copy.
- **Visual work** uses this and nothing else. The first build run of a task with something to look at ends at a rough, reviewed pass: its draft pull request is open and the tech lead posts the screenshot in a comment, again after each pass that changes what is seen. The human comments there when they wish (a draft is watched like any other pull request); no frame goes through the dispatcher and nobody waits. The images live in commits on a side branch `shots/<slug>`, never merged, and are linked by commit SHA from `raw.githubusercontent.com`, because GitHub has no API for comment attachments and an image on the task's branch would enter the default branch's history. The branch is not deleted: the links die with it. Screenshots are public with the repository: no other repository's name, no home path, nothing about the owner's server.
- **How soon**: one tick, the watch interval. **Cost**: no GitHub call without a task working, blocked or handed over; one `gh pr list` per tick; one more call per pull request with a new review; one courier run (`models.courier`) per batch; nothing on a quiet day.
- **Where**: `comments-YYYY-MM.jsonl` logs every new item once (`ts`, `repo`, `slug`, `pr`, `id`, `url`, `kind`, `author`, `association`, `author_kind`, `decision`, `to`, `batch`; no text). What was seen is in `comments-<repo>-<hash>.json` in the store. The first run after install records what is there and forwards nothing.
- **Limits**: an edited comment is not seen again; `gh pr list` returns at most the first 100 reviews and comments of a pull request; a pull request with no task worktree is ignored.
- **A hostile comment** can cause a log line and nothing else: only an author with write access is ever forwarded, and no comment text reaches a prompt or the session of a lead directly (the lead reads the file, which says it is data).

## Setup and uninstall
Four entry points, side by side; the remote ones are `bin/isshoni host add` and `host remove` with their arguments left out, which then ask for what is missing (given the arguments, they ask nothing):

| | `make` (in the clone) | command |
|---|---|---|
| this machine, set up | `make wizard` | `factory wizard` |
| a server, set up | `make wizard-remote` | `bin/isshoni host add` ([container.md](container.md)) |
| this machine, remove | `make uninstall` | `factory uninstall` |
| a server, remove | `make uninstall-remote` | `bin/isshoni host remove` |

Both targets take `ARGS="..."`. The rest of this section is the local pair.

`factory wizard` (or `make wizard`, which takes `ARGS="..."`) walks the steps below in order and can be rerun: every run evaluates every step from the top, skips what is done and prints one line for each (`done:`, `did:`, `skipped:`, `needs you:`). A required step that cannot be completed stops the run, prints what to do and `Then run the wizard again.` and exits 1; an optional step that is declined or cannot run prints one line and the run goes on. It exits 0 when every required step is done and no step failed, else 1. Without a clone (only the installed plugin) the dashboard and cost steps are `skipped`.

| Flag | Meaning |
|---|---|
| `--yes` | accept every offer without asking. Without it an offer prints `question [y/N]` and reads one line from stdin; anything but `y` or `yes` is no, and so is end of input: no answer is never consent, so a non-interactive run (no terminal on stdin) declines every offer unless it has `--yes` |
| `--list` | print each step and its state, change nothing; it runs only the read-only commands `gh auth status`, `gh extension list`, `claude auth status` and `claude plugin list --json`, and calls no network API. It ends with a `hosts:` block: one line per server recorded in `hosts.json` (`name  target  repositories`) or `none`, and the pointer to `bin/isshoni host status` for their live state |
| `--owner`, `--name` | the GitHub App step: see Identity |

1. **dependencies** (required): `git`, `gh`, `claude` and `openssl` on `PATH`, Python 3.11+, `gh auth status` succeeding and `claude auth status` saying `loggedIn`. It installs nothing; it lists everything missing at once with what to do.
2. **dashboard** (optional, clone only): `bin/isshoni-tui` exists. Offers `make build`; needs Go.
3. **plugin** (required): `factory@factory` is in `claude plugin list`. Otherwise adds the marketplace `andreiciobotar/isshoni` (when no marketplace named `factory` exists) and installs the plugin. A `factory` marketplace from another repository is never replaced: it stops and says so.
4. **settings** (required): `settings.toml` exists and is valid. Missing, it is written atomically as the shipped, commented file (an old `settings.json` is copied into the TOML instead, and left in place). An existing file that does not parse or validate is never overwritten: it stops with the error and the path.
5. **cost criteria** (optional, clone only): `paths.monitor` names an existing file. Offers to set it to `<clone>/bin/isshoni`, keeping every other key (unknown ones too); a `paths.monitor` that points at a missing file is replaced and the line says what it pointed at. Run from a task worktree it is skipped: that path disappears with the worktree.
6. **gh stack** (optional): `gh extension list` has `github/gh-stack`. Otherwise offers `gh extension install github/gh-stack`, which shows and manages from the terminal the stacks the lander forms; the factory works without it, and a no is asked again on the next run. It needs `gh` 2.0+ (an older one is skipped with what to upgrade, and nothing is installed); the extension itself needs Git 2.36+. A failed install is printed, the run goes on and exits 1.
7. **GitHub App** (optional): see Identity. A failure here is printed, the run goes on to the summary and exits 1.

The summary lists each step's state and says that the site manager starts with the dispatcher session and stops with it (the plugin's hook installs and removes its job), so nothing is installed for it. A live dispatcher session installs that job again and recreates the home with its logs, so end dispatcher sessions before uninstalling. When every required step is done it prints the command to start working, and when the run changed nothing, `Nothing to do: everything is set up.` A last line points to `make wizard-remote` for a server (without a clone, it says a server needs one).

`factory uninstall` (or `make uninstall`) removes what the wizard and the factory put on the machine. `--list` says what each step would remove and does nothing; `--yes` confirms every step. Each step says what it found and what will be lost, then asks, then acts; a step with nothing to remove says so, and running it twice is safe. It deletes only on positive evidence that the thing is the factory's; everything else is kept and named in the final list. In order:

1. **schedules**: the watch jobs of this home, for every repository (launchd, systemd or cron). Under another `FACTORY_HOME` a job is this home's when it records that `FACTORY_HOME`; otherwise when it records none. A job of another home, or a file that is not a factory job, stays.
2. **GitHub App**: uninstalls the App's installation (`DELETE /app/installations/<id>` as the App; `404` is "already uninstalled"), then prints and opens the App's settings page: only you can delete the App itself (Advanced, Delete GitHub App). A failed call is reported and the run goes on. While `hosts.json` lists a server, the App is kept: nothing is deleted or opened, and it names the hosts and the way on (`make uninstall-remote` for each, then `make uninstall` again). The copy of the identity on a server (`"copy": true` in its `app.json`) never removes the App either: it belongs to the machine that ran `host add`. An unreadable `hosts.json` fails this step and the home step, removing nothing of them.
3. **plugin**: `claude plugin uninstall factory@factory` and `claude plugin marketplace remove factory`, the plugin (user scope) when installed, then the marketplace `factory`, whenever that marketplace is `andreiciobotar/isshoni`; a `factory` marketplace from another source is kept with the plugin.
4. **home**: the factory's own names in `FACTORY_HOME` (settings, logs, specs, deliverables, `identity/`, `dashboard/` with the keys of the dashboard over SSH, `watch.log`), each path named before it asks. While servers are recorded, `identity/` and `hosts.json` stay (they are what the servers' copies and `host remove` rest on); once none is, a second `make uninstall` removes them too. Anything else is kept and listed, and the directory is removed only when it is then empty.
5. **dashboard binary** (clone only): `bin/isshoni-tui`.

The home is removed only by its known names; under a `FACTORY_HOME` other than `~/.claude/factory` a directory holding anything else is left whole and named, since a mis-set variable must not delete a stranger's files. It exits 0 unless a step failed, and ends with what it left: Claude Code's own transcripts and settings (`~/.claude/projects`), your repositories with their task worktrees and `worktree-*` branches (`factory clean` or `git worktree remove`, before the plugin is gone), the clone, git, `gh` and its stack extension (`gh extension remove stack`), Go and Claude Code, the App on GitHub until you delete it, and whatever a step declined or kept.

## More than one machine
This machine and each server added with `isshoni host add` are separate installs. They share one thing, the GitHub App's identity (one bot, one installation); the rest is per machine:

| Shared | Per machine |
|---|---|
| the GitHub App: one bot, one installation (the server holds a copy of the key) | the Claude login, the settings and the cap, the repositories and worktrees, the tasks and their declared state, the logs, the Kaizen numbers and the dashboard |

The same repository on two machines is supported with one rule: **a slug is used on one machine only.**
- What holds: each machine acts only on pull requests whose head branch has a task worktree on that machine and, once the task has recorded its pull request's number, whose number is the recorded one (the draft and ready flags, `merge`, the lander's loop, the comment forwarder, `land`, `clean`), and `new` refuses a slug whose branch or pull request already exists on the remote.
- What follows: the cap counts a machine's own worktrees, so up to cap times the number of machines tasks run at once; every machine's site manager reports the same repository-wide findings, such as a red default branch.
- The limit: the same slug started on both machines before either pushed (leads push when they land) is not detected. The second push is refused, never forced; until then the second machine's draft sync and comment forwarder treat the first machine's pull request as theirs. Use different slugs, or give each machine its own repositories, which is the advised setup.

**The recorded number.** A task's pull request number is kept in the branch's git config, `branch.<branch>.factoryPr` (`git branch -D` removes it with the task). It is written by the first `built` run that finds the open pull request at the worktree's head, and by `factory state handed-over <url>` when `<url>` (whose last part must be digits) is the open pull request on the task's branch at the worktree's head, replacing an older value; a hand-over that cannot record it says so on stderr and still declares. A pull request on the task's branch with another number is treated as having no task: no draft flag, comment, tech lead, push or merge, and `factory land` stops and names both numbers. Read it with `git config branch.worktree-<slug>.factoryPr`; undo it with `git config --unset branch.worktree-<slug>.factoryPr`. Each process reads it once, when it starts.

## Identity
`factory wizard [--owner <account>] [--name <app name>]` (or `make wizard`) offers, as its last step, a GitHub App of its own for the factory. Once it is installed, the factory acts on GitHub as that App (see How the identity is used); with no identity stored, or an App stored but not installed, every command acts with your `gh` login, and `factory status` says which. It needs `openssl` on the `PATH` (it signs the App's JWT) and a browser.

First run, with nothing stored:
1. The owner is `--owner`, else your own account (`gh api user`); when that cannot be read it exits 1 naming `--owner`. Pass `--owner` for an organization (`make wizard ARGS="--owner NAME"`). GitHub says whether it is a user or an organization; the App is created under it. The offer is a question first ("Give the factory its own GitHub identity ... Two confirmations in your browser."); no answer is no.
2. The wizard starts a small web server on `127.0.0.1` (a port the OS picks), prints its address and opens it. The page sends GitHub an App manifest named `isshoni-lander-<owner>` cut to 34 characters (an App name is unique across GitHub and 34 characters at most; `--name` sets another, and one longer than 34 exits 2 instead of being cut; you can edit the name on GitHub's confirmation page, the wizard reads the real slug back). **Confirmation one**: create the App. GitHub redirects back to the wizard, which exchanges the code for the App's credentials. It waits 10 minutes, then exits 1 with nothing stored (GitHub creates the App when you confirm, so if you did, delete it on your apps settings page before running again; a failed exchange says the same). Over ssh, forward the printed port (`ssh -L PORT:127.0.0.1:PORT`).
3. The private key and `app.json` are stored at once. **Confirmation two**: install the App on the repositories you choose, on the page the wizard opens; it first says to choose "Only select repositories" and pick the ones the factory works in, because with "All repositories" the bot can write to every repository of the owner. It polls for 10 minutes; on timeout the App stays stored and the next run resumes here.
4. It signs a JWT, mints an installation token, lists the repositories the token reads, looks up the bot user, and prints the App, the bot login, the repositories and how to remove it (`factory uninstall`, or `make uninstall` in the clone). With "All repositories" it prints the count instead of the names, a `WARNING:` line naming the installation page where to narrow it, and that the tokens the factory hands out reach only one repository either way (see How the identity is used). The token is never printed or stored.

Permissions the App asks for, and why:

| Permission | Level | Why |
| --- | --- | --- |
| Contents | write | push a task branch; merge a pull request (the merge endpoint is under Contents) |
| Pull requests | write | open, edit, mark ready and comment on pull requests |
| Checks, Commit statuses | read | `gh pr checks` |
| Actions | write | re-run the failed jobs of a check once when the failure is not the task's (`factory rerun`); health reads CI on the default branch (`gh run list`) |
| Metadata | read | implicit |

Actions: write also lets the bot re-run a whole run or one job, cancel and force-cancel a run, delete a run or its logs, approve a fork pull request's run, dispatch a workflow (`workflow_dispatch`), enable or disable a workflow, delete artifacts and caches, and set the OIDC subject template; it does not let it change workflow files. An App installed before this level was asked keeps `read` until you change it: `factory wizard` prints `WARNING: the installed App lacks actions: write ...` with the two URLs (the App's permissions page, then the installation page where you accept the new permission); everything but the re-run works without it.

Left out on purpose: `workflows` (so the bot cannot change CI: a branch touching `.github/workflows/` must be pushed by you, see below; with it, a confused lead could push a workflow that reads every repository secret and mints a write token, merging its own pull request: it would remove your merge gate) and `issues`. No webhook is active.

Files, in `~/.claude/factory/identity/` (mode 0700):
- `key.pem` (0600): the App's private key. Never printed or logged.
- `app.json` (0600): `app_id`, `slug`, `client_id`, `html_url`, `owner`, `owner_type`, and once verified `installation_id`, `installation_url`, `repository_selection` (`all` or `selected`, refreshed on every run), `bot_login`, `bot_id`, `bot_email` (`<bot_id>+<slug>[bot]@users.noreply.github.com`).

Rerun with an identity stored: it never creates a second App, `--owner` naming another account exits 1 (one identity per machine), and `--name` exits 1 (the wizard does not rename). A `key.pem` without `app.json` exits 1 before any call, naming the `rm -r` to run. It sets looser modes back to 0600/0700 and says so; reports a missing `key.pem` (exit 1); reports when GitHub no longer knows the App or its key was revoked (exit 1, files untouched); opens the install page when the App is not installed; exits 1 when the installation sees no repositories, naming the page where to choose some; otherwise verifies, refreshes `app.json` (slug, URL, bot login, id and email come from GitHub's answer) and prints the report, exit 0. A failure that means the App is broken (key missing, App gone) prints the undo lines.

To rename the App, change its name on its GitHub settings page (there is no API for it), then run `make wizard` (or `factory wizard`): it reads the new slug from GitHub, records it with the bot's login and email, and prints `renamed: <old slug> -> <new slug>`. The App id, its key and the installation stay; `factory env` does not need the wizard, since no token depends on the name. Commits already made under the old name keep it in git and stay attributed to the bot on GitHub (same account id). Running leads use the new name at their next command (see below).

Headless machine: on Linux without `DISPLAY` or `WAYLAND_DISPLAY` the wizard does not open a browser (it would start a text browser in the terminal); it only prints the URL. GitHub redirects the browser to `127.0.0.1`, so opening that URL on another machine works only with the port forwarded (`ssh -L PORT:127.0.0.1:PORT`). Otherwise run the wizard on your laptop, then copy the directory (`scp -rp ~/.claude/factory/identity HOST:.claude/factory/`, or mount it into the container) and run `factory wizard` there: it verifies and prints the report.

### How the identity is used
An identity stored by an earlier wizard has no `repository_selection`: run `factory wizard` again to record it (and after narrowing the installation on GitHub).

Who acts as the App: lead sessions and their subagents (pushes, fetches, `gh`, and commits authored and committed as `<bot_login> <bot_email>`), and the script's own `gh` calls (`status`, `new`, `health`, `watch`, `merge`, `digest`, `land`; `land`'s `git fetch`, `merge` and `push` also act as the App). Only in a repository whose `origin` is on GitHub and belongs to the App's owner (the accepted forms are `https://[user@]github.com/<owner>/<repo>[.git][/]`, `git@github.com:<owner>/<repo>[.git]` and `ssh://git@github.com/<owner>/<repo>[.git]`, the host in any case; any other form, an ssh port included, means no identity and your login is used): elsewhere, or in a repository of another owner, there is no acting identity (`factory env` prints nothing, `gh` gets no token, `status` says so) and the `gh` login is used. Not the dispatcher's own shell or your terminal; `eval "$(factory env)"` gives any shell in such a repository the same identity.

Mechanism. `factory env` prints these exports (every value shell-quoted; when stdout is a terminal `GH_TOKEN` is shown as `***`, so `eval "$(factory env)"` keeps working and a bare run leaks nothing):

| Variable | Value |
| --- | --- |
| `GH_TOKEN` | an installation token |
| `GIT_AUTHOR_NAME`, `GIT_COMMITTER_NAME` | the bot login |
| `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_EMAIL` | the bot email |
| `GIT_TERMINAL_PROMPT` | `0` |
| `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n`, `GIT_CONFIG_VALUE_n` | four config entries: an empty `credential.https://github.com.helper` (drops every helper configured before, such as the keychain or `gh auth git-credential`), then a helper that answers `x-access-token` and `$GH_TOKEN` (read from the environment when git calls it; the token is not in the config), and `url.https://github.com/.insteadOf` for `git@github.com:` and `ssh://git@github.com/` (ssh remotes of github.com are used over https) |

The plugin's `SessionStart` hook (`factory hook`) appends one line, `eval "$(<path of factory> env)"`, to the file named by `CLAUDE_ENV_FILE`, which Claude Code runs as shell code before every Bash command. It does so for a lead session (a session in a task worktree, not a subagent's start), once (the line is not added twice), whether or not an identity is stored: running the wizard takes effect in running leads at their next command, and removing the identity undoes it. The dispatcher and any session outside a task worktree get no line. "A task worktree" is read from the path alone: any session whose project directory is `<repository>/.claude/worktrees/<name>` (a name not starting with `agent-`), in any repository where the plugin is enabled, whether or not `factory new` made it; the exports then apply when that repository's `origin` belongs to the App's owner and the App can reach it. When the owner matches but the installation does not cover the repository, git and gh fail in that session (`GH_TOKEN=unavailable`) rather than fall back to you. So with the App installed on all repositories, worktree sessions in your other repositories also commit and push as the bot, while sessions in a main checkout stay you. The script's own `gh` calls get `GH_TOKEN` in the child's environment; its `git` calls are local except `new`'s `ls-remote` and `land`'s fetches, merge and push, which run with the exports of `factory env` (see Landing without the lead).

Tokens last one hour at GitHub and are scoped to the repository the command runs in: the mint asks for `repositories: [<name of origin>]`, so the token reaches that repository only, whatever the installation covers. A repository the installation does not cover is refused by GitHub (422): the message says `the App is not installed on <owner>/<name>: add it at <installation url>`, and `factory env` fails closed as for any mint failure. The token is cached per repository in `identity/token-<name>.json` (0600) and minted again when under 15 minutes remain, so every Bash command starts with at least 15 minutes, which is more than a foreground command may run (10 minutes). Limits: a background command that outlives its token; a session started before plugin 0.5.0 has no hook line (restart the lead); `GIT_CONFIG_*` variables set by the caller are replaced; only `github.com`.

Secrets. The token is in the environment of the lead's shell commands: an agent can read it. It reaches only the repository the command runs in, with the permissions in the table, and it expires. The identity is a default, not a boundary: the dispatcher session still acts with your login, and a lead's shell can still reach your own `gh` login or keychain by unsetting the variables, so the rule that no agent posts `lgtm` or approves a pull request stays. The key never leaves `identity/`, is read only by `openssl` when a token is minted, and no role is told where it is.

Failure. When an identity applies (installed, and this repository on GitHub under the App's owner) but anything goes wrong finding it or minting the token (a refused mint, GitHub 422 for a repository the installation does not cover, a corrupt or malformed `app.json`), `factory env` prints one line with the reason on stderr, exits 1, and still prints the lock-down: `GH_TOKEN=unavailable`, `GIT_TERMINAL_PROMPT=0` and the four `GIT_CONFIG_*` entries (so `git` cannot reach your credential helper or your ssh key for github.com), plus the bot's author and committer variables when the identity itself could be read. Each command then shows the reason and `git` and `gh` fail with an authentication error; in a lead session they never fall back to your login. A corrupt or malformed `app.json` locks down every repository where `env` runs, not only the App owner's, because the owner cannot be read. When no identity applies, it prints nothing.

`.github/workflows/`: GitHub refuses the App's push of a branch whose own commits change a workflow file, with a message that holds ``without `workflows` permission``. The push is tried and the refusal recognised by that text (no check predicts it). It normally comes at the task's first landing: the lander stops `denied`, the lead (who knew from planning, by its rules) sends `BLOCKED:` with the command, and the dispatcher passes you one line. `factory land` stops `denied` the same way. The one command, from your own terminal: `git -C <main checkout>/.claude/worktrees/<slug> push -u origin HEAD`, never a force; then tell the dispatcher, and the lander opens or updates the pull request. A merge that only brings the base's workflow changes into a branch is accepted (probed 2026-11-14 on a real repository as the App), so a task that does not itself touch workflows never meets the refusal. Workflow changes are rare (1 of about 45 pull requests on 2026-11-14).

Checked with a real App, read-only: a token minted for one repository reaches that repository only although the installation covered all (another repository of the owner answers 404); `gh pr view --json statusCheckRollup,reviews`, `gh pr list`, `gh pr checks`, `gh run list`, the `collaborators/<login>/permission` and `activity` reads, and GraphQL `viewer` (the bot) all answer; the credential helper authenticates `git push --dry-run`.

Proven as the App: `gh pr create`, `gh pr ready` and `gh pr ready --undo` (both exit 0 when the flag already has that value). Not yet proven, the first real task will show: `gh pr edit --base` and `gh pr merge --match-head-commit` as the App; a real push and the bot showing as author on GitHub; that the lander's later push of an already pushed head succeeds; branch protection that restricts who may push or merge (the App must be allowed there).

Undo: `factory uninstall` uninstalls the App and removes `identity/`; you delete the App itself (`https://github.com/settings/apps/<slug>/advanced`, or `https://github.com/organizations/<owner>/settings/apps/<slug>/advanced`; no API deletes an App).

## Shutdown and leftovers
`run()` in `factory/lib/factory_core.py` is the only place a child starts, and it owns the child's lifetime.

| Constant | Seconds | Applies to |
|---|---|---|
| `RUN_TIMEOUT` | 120 | every call that names no timeout (the other `claude plugin` calls, `git`, `claude agents`, `claude rm`, `launchctl`, `systemctl`, `crontab`, `openssl`, `ps`, `lsof`, the launch of a lead) |
| `NETWORK_TIMEOUT` | 300 | `git` through the App (`pull`, `fetch`, `merge`, `push`) and `claude plugin marketplace add` and `install` |
| `GH_TIMEOUT` | 30 | `gh`, and `factory new`'s `git ls-remote` and `git fetch` (`act_git`), unless the caller names one (`PR_TIMEOUT` 10, `NOTICE_TIMEOUT` 20, the head-branch lookups 10) |
| `SETUP_TIMEOUT` | 90 | the repository's `factory.setup` command, run by `factory new` in a worktree it made |
| `MONITOR_TIMEOUT` | 120 | the monitor's `isshoni` |
| `COMMENT_TIMEOUT` | 120 | the courier run (`claude -p`) |
| `WATCH_TIMEOUT` | 600 | the site manager run (`claude -p`) |
| `OPS_TICK_TIMEOUT` | 300 | one look of an ops watch (`claude -p`) |
| `LAND_TEST_TIMEOUT` | 1800 | the test command before a push, and `make build` in the wizard |
| `LAND_TIMEOUT` | 1800 | the lander of `factory land` (`claude -p`) |

Nothing waits for a human through `run()`, so no call has "no limit". A timeout returns `(124, "", "timed out")`.

- **Process groups.** The four long runs (the site manager, the courier, the lander of `factory land`, the test command) pass `group=True`: the child starts in a process group of its own, and a timeout kills that group with SIGKILL, so a `claude -p` run's own children go with it. Every other child stays in the script's own group (the dashboard starts `factory status --json` in a group of its own and kills it as a whole), and only the child itself is killed on a timeout.
- **Signals.** `factory` run as a command handles SIGTERM, SIGHUP and SIGINT: it kills the group of every live `group=True` child, then exits with 128 plus the signal (143, 129, 130). A signal that arrives while a child is starting is held until the child is known, so that child is killed too. The exit is `sys.exit`, so `finally` blocks and context managers run, and the kernel releases the locks. SIGKILL cannot be handled: the timeout lived in the dead script, so a long run goes on until it ends on its own and no timeout applies. `children` in a task row covers lead sessions only, not site manager or lander runs.
- **One tick at a time.** `watch` holds a non-blocking `flock` on `watch-<repository>-<8 hex>.lock` in the store for the whole tick, loop included. The file's mtime is the age of the last tick: each tick, the in-loop ones too, sets it when it begins (`os.utime`); nothing else writes the file, and `health` reads it without moving it; a held lock is reported by `health` only after `TICK_LATE + LAND_TIMEOUT` (see Shutdown and leftovers). A tick that finds it held prints `watch: a tick is already running` and exits 0 (cron starts one every two minutes; launchd and systemd do not start a second instance of a running job). The kernel drops the lock when the holder dies, so there is no stale lock. The lander's lock (`lander-...lock`) is the same helper with another name; the tick's loop and `factory lander` hold it.
- **`children`** in the row of a handed-over task lists what keeps its live session busy (up to five processes from one `ps`, with their ages). A hand-over (a `state` event) wakes the site manager, who reads it; no criterion fires on it. A subagent that waits without a process (for example on a refused hand-back) cannot be seen from outside; the row then has no `children`.
- **`health`** prints up to four more lines, only when the count is not zero, and removes nothing: `N subagent worktrees (agent-*) older than 24 h: <names, at most 5>` (age is the worktree directory's mtime), `N finished job directories older than 24 h under ~/.claude/jobs (X MB)` (a directory whose `state.json` says `done` or `stopped` and whose mtime is older than 24 h) and `N entries in <store> the factory does not write: <names, at most 5>`. When the watch lock file of the repository exists (a repository that never ran `watch` has none; whether a schedule is installed is not asked: off macOS that would cost a subprocess per `health`, `systemctl` or `crontab`; on macOS launchd's check is a file check) and its mtime is older than `TICK_LATE` (`WATCH_TIMEOUT + 2 * WATCH_INTERVAL` = 840 s: one full site manager run and two intervals), it tries the lock without blocking and drops it, and prints one more line: `watch: no tick has begun for <N>m and none is running: the schedule is not starting them (factory schedule shows it; a machine that just woke runs one within 2m)` when the lock is free, and, when it is held, only once the mtime is older than `TICK_LATE + LAND_TIMEOUT` (840 s + 30 m = 44 m, since the lander's loop runs a tick each pass and a pass with a conflict run takes up to 30 m per pull request): `watch: the last tick began <N>m ago and is still running (one begins every 2m; a pass that resolves a conflict can take 30m per pull request): if it is not landing, it is stuck; ask the human to end it (pgrep -fl 'factory watch')`. A held lock between the two ages prints nothing. A repository whose schedule was removed keeps its lock file, so it gets the line for a free lock.

### Closed tasks
A task declared `closed` is cleaned by a third rule, after the guards that apply to every task (uncommitted or untracked files, a session, something stacked on it, a detached HEAD, a nested worktree), which stay first. `clean` removes it only when all hold; otherwise it keeps it with the first failing line:
- its pull request is not `open` and not `unknown` (`closed, but its pull request is <state>`; the factory never closes a pull request);
- no process has its working directory or an open file in it (`closed, but pid <pid> (<command>) uses it`, or `closed, but cannot list open files: <error>`);
- every commit reachable from its branch head is reachable from the default base, from the branch of another task that is not itself `closed`, or from a branch the remote holds now. The remote is asked (`git ls-remote --heads`), never read from remote-tracking refs, which go stale. Otherwise `closed, but cannot ask <remote> which commits it holds: <error>`, `closed, but cannot tell which commits <remote> holds here: <error>`, `closed, but cannot tell which commits it holds: <error>`, or `closed, but <n> commit(s) are in neither <base>, a live task branch nor <remote>: <sha7> <subject>[; ...]` (five named, then `and <k> more`). That line names what would be lost, and it is what reaches the human.

Removal is the steps above, except that the branch goes with `git update-ref -d refs/heads/<branch> <the head judged>`: its commits may live in another task's branch, which `git branch -d` refuses, and a branch that moved stays. Nothing on the remote is deleted and no pull request closed. Unpushed or unmerged work is deleted by no path.

**What "live" means** for `close`: sessions cannot be listed or one is unplaced; a session of the task is interactive, unfinished, or has a `pid` (an idle lead with a process is live); a build or tech lead run holds its lock; a process has its working directory or an open file in the worktree, or `lsof` cannot say. Each refusal names which.

`factory close` exits 1 on a refusal (nothing written) or a failed removal step, 0 when the task is closed and removed or kept. A failure after the declare (sessions cannot be listed again before removing) is a keep: `kept <slug>: <why>`, and the site manager's close escalates it to the dispatcher with `kept: <why>`.

### What `clean` does after the tasks
Three steps, in this order. Nothing here changes the exit code: a kept leftover is not a failure. `lsof` is required for them (the container image has it); it lists open files of your own processes only, so a process of another user is not seen.

1. **Dead subagent worktrees** (`agent-*`, see below). `clean` removes one only when every check holds; the first that fails prints `kept <name>: <why>`. They are the script's, not a judgement: `clean` runs after every merge and removes each one it can prove dead; what it keeps holds work or is younger than 24 h. The site manager never closes or removes them: when `factory clean --dry-run` shows one kept for work that is in no branch, he escalates that line so the human decides.
   - its directory's mtime is older than 24 h (`younger than 24 h`);
   - it has a branch (`detached HEAD, no branch to judge`);
   - it is not locked (`locked (<reason>); if nothing uses it, run: git worktree unlock <path>`);
   - no other worktree is registered inside it (`another worktree is registered inside it: <path>`);
   - `git status --porcelain` in it exits 0 and prints nothing (`uncommitted changes`, `cannot read git status`);
   - its branch is merged by content: for the default base, then the branch of each live task, `git merge-tree --write-tree <target> <branch>` exits 0 and prints the tree the target already has, so merging would change nothing. That covers an ancestor, a cherry-pick, a squash and a merge through a lead's branch, and also a branch that undid its own work. Files git ignores (`__pycache__/`, build output) are not content: they go with the worktree. Otherwise `branch <b> has work that is in neither <base> nor a live task branch` (or `cannot tell whether <b> is merged: <error>`);
   - no session of `claude agents` works in it (`session <id> works in it`);
   - no process has its working directory or an open file in it, from one `lsof -w -F pcn` per run (`pid <pid> (<command>) uses it`; `cannot list open files: <error>` when `lsof` is missing, times out or prints nothing).

   Removal is `git worktree remove <path>` (never `--force`; a refusal prints `kept <name>: git worktree remove: <error>`), then `git update-ref -d refs/heads/<branch> <commit>`, which deletes the branch only while it still points at the commit that was judged (`git branch -d` refuses a branch merged only by content; `-D` checks nothing). A branch that cannot be deleted prints `kept branch <branch>: <error>`. The output is `removed <name> (its work is in <target>)`, or `would remove ...` with `--dry-run`.
2. **Finished job directories** older than 24 h are never deleted; they belong to Claude Code. Each prints `kept job <id>: belongs to Claude Code; ` and one of `pid <pid> (<command>) has files open in it`, `no process has files open in it, try: claude rm <id>` or `cannot list open files: <error>`.
3. **Strangers in the store**: each entry directly under `~/.claude/factory` that is neither a name `uninstall` removes nor another name the factory writes (`cache/`, `comments/`, `gh-`, `comments-` and `outbox-` month logs, every per-repository `<name>-<repository>-<8 hex>.json` or `.lock` with its `.tmp` file) prints `kept <path>: not a file the factory writes`. Nothing in the store is removed.

### What belongs to Claude Code
`clean` removes dead subagent worktrees as above; the rest it only reports, and removing it is by hand.
- A background session holds a lock on its worktree (`git worktree list --porcelain` shows `locked claude session <name> (pid N ...)`); the lock stays when the process has exited. `factory status` then prints `if nothing uses it, run: git worktree unlock <path>`; `factory clean` keeps a locked worktree.
- A session's state directory `~/.claude/jobs/<id>` (`state.json`, `timeline.jsonl`, `tmp/`) is removed by `claude rm`. While a process the session started still writes to `tmp/`, the removal fails with `ENOTEMPTY`; `factory clean` calls `claude rm <session>` for a task's session, prints a failure and does not retry. `health` counts the finished directories older than 24 h, and `clean` lists them (step 2 above).
- A subagent started with worktree isolation gets `.claude/worktrees/agent-<id>`, which Claude Code removes only when it is unchanged. The factory does not list these as tasks, rejects task slugs that start `agent-`, and `health` counts those older than 24 h. `clean` removes the dead ones (step 1 above); a kept one is removed by hand with `git worktree remove <path>` once you have looked at it, and a stale lock is never broken by `clean`.
- A session with a live background command counts as busy: `factory clean` and the lander's merge refuse it. the `children` of the task's row name the process.

## Where the code lives
`factory/bin/factory` is the entry point: it puts `factory/lib` on `sys.path`, imports the modules and runs `main`. `factory/lib/factory_core.py` holds most of the code. A group of commands that the core does not call lives in its own module, `factory/lib/factory_<name>.py`; the first is `factory_setup.py` (`wizard`, `uninstall`). Three rules:
- A module starts with `import factory_core as core` and reaches every core name as `core.name`, never `from factory_core import name`.
- The core never imports or names a module.
- A module's commands register with `@core.command` when it is imported, and the entry point's import list is the one place that names modules.

Tests load the entry point once (`test_factory.py`) and share its `factory_core` as `factory`: patch a core name on `factory`, and a name that lives in a module on that module (`factory_setup.clone`), where it is defined. Python writes `factory/lib/__pycache__` on first run; git ignores it, and a read-only copy works without it.

## Known limits
- The recorded pull request number (see More than one machine): a clash already present at the first record is recorded; before a task's first record the branch name decides, as before; a replaced pull request is not the task's until `factory state handed-over <new url>`, and until then `factory land` stops and says so; the url must equal GitHub's `url` exactly.
- The courier is a model: a line is delivered when it replies `sent`, and nothing checks the tool call. The line is carried between two marker lines as data for the other session, and can be free text from `factory lead`.
- A live lead whose courier fails after sending some lines may get those lines again on retry. `forward` from a detached run and the tick's drain are not locked against each other, so a line may rarely be delivered twice.
- A lead the harness retired (see Messages): a task whose lead cannot be brought back is closed by the site manager or the human (see Closed tasks), not by the outbox; nothing keeps sessions from retiring, bounds build runs, records session ids in the store or covers the dispatcher's own retirement; a lead with no process and nothing pending is left alone (if its task is declared `working`, that is `ended-undeclared`'s); lines that reached the dispatcher before the outbox are not replayed; a line `factory lead` queues waits for the next tick; the drain runs at the start of every tick, the lander loop's too; a tick that hangs stops it.
- `factory.lastTest` (the last test command handed over, written by `factory state handed-over`) stays in the repository's git config after `factory uninstall`; remove it with `git config --unset factory.lastTest`. The `branch.<b>.factoryTest` and `factoryGolden` keys go with their branches.
- Nothing caps what a lead spends; the time limit is checked by the lead between subagent runs.
- A message that a base moved still wakes a lead that is working: it starts a build run. A handed-over task is landed by `factory land` without its lead; what the lander may do rests on its rules and its tool list, not on a mechanism: Bash can do anything the session may, and the scripted path trusts the session list to tell a lead that is running. When a stacked task's base was squash-merged by hand, the merge brings the base's old commits back as conflicts: `land` stops on a conflict, and the lead sorts it out (the factory merges with merge commits, so its own stacks merge clean).
- The Kaizen page and the dashboard show only the machine they run on (see More than one machine).
- A worktree made by hand under a slug used before inherits that slug's last declared state.
- A store nobody writes to is never pruned. A month file and `watch.log` have no size limit.
- The monitor adds up the cost of a reused slug, so a task started under an old slug looks dearer than it is. A model the monitor has no price for understates the cost.
- Merging: a refused merge is told once per head, so a requirement that changes at the same head (a review required, then changes requested) is not told again, and `factory status` keeps showing the first. Only `REVIEW_REQUIRED` and `CHANGES_REQUESTED` are put in words; code owners and rulesets are not named: the line says nothing it shows explains the refusal, followed by GitHub's raw text. GitHub's refusal text, and the value of `reviewDecision` where no review rule applies, were not observed. Without an identity (the author's own account) the author's `lgtm` rests on a rule, not a mechanism (see Merging). The check that started again is named only when its run is already visible when the lander looks; otherwise the line says nothing explains the refusal. A `CHANGES_REQUESTED` review by a different login does not block a merge. The author comparison and the bot test rest on GitHub's `user.type` and login. Checks are not rerun after a base change (the next pass reads them again), and GitHub does not test the merge result: mergeable means no conflict. A pull request with no task worktree is a `handover` stop; the human merges it. At most 100 open pull requests are seen. An `lgtm` during a running check is the lander's to wait for. Lander runs are serialised by a lock; a plain `factory merge` is not, so when it and a lander merge at once the second `gh pr merge` fails and is reported.
- The site manager has no thresholds, only the facts in the rows and the reference; `last_activity` reads file times, so a lead waiting on a long command looks quiet; a run that dies after sending may escalate the same firing again next tick. A site manager run is read as one JSON document on `claude`'s standard output. The site manager can read anything you can read (any file, any pull request your `gh` login sees), and what it reads (transcripts, pull request comments, command lines) is untrusted text that it is told to treat as evidence. Its `looked` list is its own account; `run`, the id of its session, is the truth.
- Two repositories whose directories share a name share a spec folder and an old-style dispatcher name.
- Identity: the private key itself can mint a token for any repository of the installation, so a narrow installation ("Only select repositories") is still the real boundary, not the scoping of the tokens handed out; during a GitHub outage each lead command waits for the mint attempt (up to 30 s) once the cached token is within 15 minutes of expiry (a cached token that has not expired is used when the mint fails); one per machine; `workflows` is not granted; only `github.com`; a background command can outlive its token; a lead started before plugin 0.5.0 has no hook line; `GIT_CONFIG_*` set by the caller is replaced. See How the identity is used, including what only a real run proves.
